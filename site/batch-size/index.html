Measured study · one RTX 5090 desktop · 12 models partly in system RAM, 6 that fit on the card

llama.cpp batch size: ten big models read long prompts 2.5 to 7.3 times faster on one RTX 5090

On one RTX 5090 desktop, a bigger micro-batch (how many prompt tokens llama.cpp reads in one pass) made reading a long prompt the server had not seen, mostly 48,000 tokens, 2.5 to 7.3 times faster than the default on ten of the twelve models whose expert weights sit in system RAM.

In short
  • If part of your model sits in system RAM, read the prompt in bigger chunks (-b 4096 -ub 2048, then -b 4096 -ub 4096, then -b 8192 -ub 8192), and stop at the first that fails. Look for an inherited small value too: two models that had inherited -ub 128 read 17.5 and 19.9 times faster once it was raised. How to tune your own
  • Find each model's own limit at the window you actually use, and test it with real text. Bigger chunks take more graphics-card memory, and one setting that read 150,153 tokens correctly and passed 110 other prompts crashed the server on a single 3,007-token prompt. The crash
  • If the whole model fits on the card, expect less. Five of six such models read 3 to 34.5 percent faster, the sixth slower, and all six kept the default. Models on the card

By Grant Williams · Published 26 September 2026

01

What to do

Two settings decide how llama.cpp reads a prompt. --batch-size (-b) is the most prompt tokens the server hands the model in one step; --ubatch-size (-ub), the micro-batch, is the most tokens that go through the model's layers in one pass. At the build most of these models ran, the defaults are 2048 and 512. Keep -b at least as large as -ub. Each value you try is one long read; with the stress test, Qwen3-235B took 35 minutes in all and Qwen3.5-397B 34.

  1. Check where the weights live. Most of a mixture-of-experts model's weights are “experts”, of which each token uses only a few; when the file is bigger than the card, they usually stay in system RAM. If any do (-cmoe, --n-cpu-moe, --fit, or a file bigger than your card), this is worth doing.
  2. Build one long read you can check. A long prompt (we used 48,000 tokens) with a short code planted in the middle and a question asking for it; temperature 0; a document the server has not seen; max_tokens big enough for a thinking model (we used 900; why). Read timings.prompt_per_second from the response, and look for the code in the answer, not only in the reasoning. Time the second read after a start too (why).
  3. Step up one value at a time. Your current setting, then -b 4096 -ub 2048, -b 4096 -ub 4096, -b 8192 -ub 8192. Stop at the first value that fails to load, drops the connection mid-read (here, the sign of running out of card memory), loses the code, or reads slower than the one before.
  4. Decide whether the gain is worth its cost. The stop rule finds the fastest value that works, not the one to keep. Here every model with experts in RAM uses a bigger value at the window it was swept at (131,072 for most), where reading got at least twice as fast; none of the six on the card does. At the largest windows some models keep the default or a smaller value, and the two-machine setup kept the default (settings at the larger windows).
  5. Watch card memory during the read, not just after load. Our peaks ran up to 465 MiB above the load reading. Leave room for anything else on the card.
  6. Re-run the winner at the window you actually use, with a long read. The window (context size) is how many tokens the server can hold. At double the window the same setting took 2,178 to 5,167 MiB more card, and one model that loaded -ub 4096 at 131,072 could not load it at 196,608 (settings at the larger windows).
  7. Test it with real text. Forty to sixty prompts of real mixed text sized around one and two micro-batches, plus repetitive input (logs, tables, ledgers), a small max_tokens, and a restart after any crash, keeping the prompt that caused it. Replay any prompt that ever crashed a server.
  8. Check that the setting reached the server. llama-server's progress lines advance in steps of -b (512 on Laguna's inherited -b 512, 2,048 at the default, 4,096 at -b 4096); at our log level the micro-batch itself was not printed.
  9. Judge writing speed on a real reply. Writing the reply (decode) goes one token at a time, and the micro-batch does not enter into it; an answer of 11 to 100 tokens is not a speaking speed.
  10. If you often edit or regenerate the last message, each edit re-reads about one micro-batch on some models (the cost); a normal next turn does not.
02

Against an inherited -ub 128, 17.5 and 19.9 times (MiniMax M2.7 on a 3,658-token read, Laguna S 2.1 on 24,071 tokens). Why it helps when experts sit in system RAM

During prompt reading, when an operation's weights live in system RAM and the batch is large enough, llama.cpp hands it to the graphics card, carrying those weights across for that pass. The trip costs about the same for 512 tokens as for 8,192, so a bigger micro-batch pays it fewer times: a 48,000-token prompt is 94 micro-batches at the default and 12 at 4096 (arithmetic). This is our reading of the code; we did not instrument the transfer. The cost is card memory, for a working buffer sized to one micro-batch: on MiniMax M3 split across two machines (20 September) it asked for 19,785.25 MiB at -ub 4096 (with two different splits) and exactly half at 2048; all three requests were refused.

At a full window, same file and build

DeepSeek V4 Flash Q8 at a 262,144-token window, every expert in RAM: on 15 September at the default it read 150,475 tokens in 2,062.2 seconds (72.97 t/s), all three planted codes returned; on 20 September at -b 8192 -ub 8192 it read 150,324 tokens in 313.2 seconds (480.0 t/s), its one code returned: 6.6 times the reading rate. More than the batch differed: two different synthetic ledgers, thinking off on the earlier request, other launch flags (both set temperature 0), and the earlier read was a later request after a 220-second load, the later one a first request.

03

Each model has its own limit

No single value was safe for every model. The limit depends on the model, how it is split between card and RAM, and its window, and the failure can come at load or mid-read.

  • At load. -ub 8192 failed on Qwen3.8-Flash-Next (131,072 window, 20 September; a 16,171.13 MiB buffer refused) and, on 21 September, GLM-5.3-Flash (15,424.89), Qwen3.5-397B (3,712.25), Qwen3.5-122B (3,264.25) and Qwen3-235B (2,752.23). Qwen3.8-27B, on the card, failed at -ub 4096 (1,568.13).
  • Mid-read. Inkling-Small at -ub 8192 loaded at 18,130 MiB, then 8,203 tokens into the read asked for 29,242.27 MiB, was refused, and died. The client saw only a dropped connection.
  • Where 8192 worked. DeepSeek V4 Flash Q8, Laguna S 2.1 at 32,768 tokens, Mistral Small 4, and Ornith-1.5-35B (7,393.7 t/s, but a 30,087 MiB peak, so it uses 4096).
  • The window moves the limit. At 262,144 instead of 131,072 the same setting took 2,178 to 5,167 MiB more card after load: Ling at -ub 4096 8,107 to 10,285 MiB, Inkling-Small at 2048 13,183 to 17,281, DeepSeek at 8192 22,089 to 26,023, Flash-Next at 2048 21,394 to 26,561. MiniMax M2.7 at its 196,608 window could not load 4096 (a 2,916.16 MiB buffer refused) or 2048; only 1024 loaded.

Settings at the larger windows

  • MiniMax M2.7 at 196,608: -b 4096 -ub 1024, every expert layer in RAM, 8-bit cache. Loaded at 31,709 MiB, peak 31,907. It read 20,039 tokens at 167.9 t/s, 47,933 at 181.2 and 189,491 at 155.9 (the last in 1,215.4 seconds), returning all three planted codes, with thinking on. Its 40-prompt stress test, on prompts of 534 to 11,160 tokens, ran without a crash, but all 40 answers are recorded empty, so it checked only that the server stayed up.
  • GLM-5.3-Flash at 262,144: -ub 1024. Its 131,072 setting, -ub 4096, did not load there (a 13,281.37 MiB buffer refused). -ub 2048 read 20,065 to 230,039 tokens at 206.0 to 250.3 t/s, all three codes on the deepest, but peaked at 31,951 MiB, 656 below the card's total; 1024 peaked at 29,261 and read 20,065 and 47,992 tokens at 135.1 and 142.6, and nothing longer. The script uses 1024 for 2,690 MiB more room and, its comment says, to stay off -ub 2048, the value that crashes in llama.cpp report #28282; our reads at 2048 did not crash. At 131,072 the same probe read 47,992 tokens at 404.9 t/s. Its stress test ran without a crash, with 36 of 40 answers empty.
  • Ornith-1.5-35B at 262,144: -b 2048 -ub 2048. A 229,090-token document took 71.7 seconds against 151.8 at 2048 / 512, three codes back each time (256K page).
  • Qwen3.5-122B at 262,144: 512. -ub 1024 took 310.0 seconds against 510.6, but peaked at 31,785 MiB, 822 below the card's total of 32,607 that day (Qwen3.8-27B at 256K package).
  • Unmeasured above the swept window: Qwen3.5-397B and Mistral Small 4 return to the default above 131,072; Laguna S 2.1 drops from 8192 to 4096 above 32,768.

Two files of one model need two values. DeepSeek V4 Flash IQ3, with 7 of its 43 expert layers on the card, uses -ub 4096; the Q8 file uses 8192. At 262,144 the IQ3 file read 48,024 tokens at 426.5 t/s at 2048 and 690.9 at 4096, and 150,103 tokens at 632.1 at 4096 (149,898 at 403.8 at 2048), code returned each time.

04

One correct read does not make a setting safe

On 20 September, Ling-3.0-flash at -b 4096 -ub 4096 read 47,992 tokens at 1,140.4 t/s with the code correct, at 131,072. Loaded at its 262,144 window, the server died on its first request:

CUDA error: an illegal memory access was encountered

On 21 September, through its own script at 262,144 and -ub 4096, five reads on one load (3,005, 2,991, 19,962, 48,084 and 150,153 tokens, the three long ones at 1,067.6 to 1,173.9 t/s) were all correct. Then a fresh load got the exact 3,007-token ledger from the 20 September check as its first request, and died the same way. At 2048, 1024 and 512 that prompt passed (444.0, 325.7 and 201.5 t/s). By hand, with the model's exact launch flags, we narrowed it down:

  • Not the window: it crashed at 4096 with windows of 262,144, 131,072 and 65,536, and at 3072 with 262,144, the only window tried there.
  • Not the length alone: ledgers of nine other sizes, 1,760 to 4,001 tokens, passed at 4096, as did real code at exactly 3,006, 3,007 and 3,008 tokens and five other lengths.
  • Rare: 60 prompts of real mixed text and 50 random ledgers of 2,134 to 6,541 tokens, 110 in all, passed at 4096 and at 2048.

Ling now uses -b 4096 -ub 2048: 727.7 t/s on 47,986 tokens and 694.6 on 149,711, code correct, 8,824 MiB at peak, crash prompt passed. The other eleven models with experts in RAM then got the crash prompt and 40 prompts of real text: twelve runs (DeepSeek's two files separately), 40 of 40 each, no crash, the code returned on every replay. The six models on the card were not stress-tested. A clean stress test is not a proof: forty prompts per setting found nothing here, and the Ling fault passed 110.

We did not find the cause. The closest public report is llama.cpp issue #28282, still open on 26 September: an illegal memory access during a long prompt read on GLM-5.3-Flash at -ub 2048, same GPU family, with 512 or 128 as the workaround. It is a different model, and no shared cause is shown. Our GLM-5.3-Flash at 4096, on its own build, read 3,019 to 48,168 tokens and passed its 40 stress prompts without it (the stress log does not print the micro-batch).

repro_ling_crash.py in the package rebuilds the same request against any running server. The crashes here come from the logs, not from that script.

05

Small values nobody had measured

Laguna S 2.1's start script, written in July, set --batch-size 512 --ubatch-size 128, with no reason recorded, a micro-batch a quarter of llama.cpp's default. A 24,071-token read took 333.2 seconds at 72.2 t/s. At 2048 it read 698.4 t/s, at 4096 1,070.5 and at 8192 1,434.0 (16.8 seconds), code correct each time; the shipped script with no override read 24,013 tokens at 1,406.5. Decode on its 12-token answer fell from 18.40 to 16.50 t/s (15.32 in that run), the one kept value whose decode moved more than 7 percent. The script lets llama.cpp choose the placement (--fit on, 4,096 MiB kept free); we suspect the bigger buffer pushed some experts back to RAM, but the logs do not record the placement.

MiniMax M2.7 was first tried with -cmoe -ub 128, the same pair of flags as the MiniMax M3 script, again with no reason recorded. One 3,658-token prompt read 32.3 t/s at 128, 100.8 at the default 512, 184.7 at 1024, 324.3 at 2048 and 564.0 at 4096. At 43,909 tokens, 4096 read 640.2 t/s with every expert layer in RAM and 656.5 with 59 of 62, the split it now uses; at 128 that read would take about 22.7 minutes (arithmetic, not run). The installed script returned 3 of 3 codes in a 43,679-token document, passed its stress test and returned the code on the crash prompt.

07

A thinking model with a small budget returns an empty answer

Our first 48,000-token check on DeepSeek V4 Flash set max_tokens to 64. Every setting, the default included, came back empty: the model spent all 64 tokens reasoning. After a settings change that looks exactly like corruption; here it was the budget. At 900 the same reads used 70 to 79 tokens and returned the code. It happened once at 900 too: GLM-4.7-Flash at 2048 spent all 900 tokens reasoning, with the code in its reasoning and an empty answer, while 1024 and 4096 answered in 433 and 488 tokens.

08

Editing the last message re-reads one micro-batch

For models whose cache cannot be rolled back token by token, or that use sliding-window attention (DeepSeek V4 Flash does: deepseek4.attention.sliding_window = 128), llama-server keeps restore points 4 + n_ubatch tokens and 4 tokens before the end of every prompt. Measured on DeepSeek V4 Flash IQ3 split across two machines (below), 262,144 window. For each document, three requests: the cold read; the same document with a different last question (about 200 words asked for); and a real next turn, sending back the first request, the reply as returned, and a short new question.

09

Two machines: the one setup that kept the default

DeepSeek V4 Flash IQ3 split across the desktop and an ASUS ROG Flow Z13 laptop over Thunderbolt with llama.cpp's RPC backend (one model spread over two machines), 262,144 window (layers 0 to 7 on the desktop's card, 8 to 17 with their experts in the desktop's RAM, 18 to 42 on the laptop). At 512: 161.8 t/s on a 2,998-token read, 102.5 on 48,024 tokens (468.4 seconds). At 2048: 224.9 and 117.0 (410.5 seconds), 14 percent faster at 48,000 tokens. At 4096: 250.5 on the short read; on the long one, after 40,960 tokens, the desktop logged the laptop's worker as crashed (“Remote RPC server crashed or returned malformed response”); the laptop's log of that moment is not in our records. We kept 512: the split read 150,103 tokens in 2,922.9 seconds (51.4 t/s), code correct, and decoded 12.05 t/s on a reply of about 400 tokens at 48,000 and 7.85 at 150,000. The IQ3 file on the desktop alone at 4096 read the same tokens in 237.5 seconds.

10

Limits

  • One machine, one request at a time. 188 GiB of RAM, one CPU, and a RAM-to-card link we did not measure; the gain depends on how fast weights cross, so a different card or link will move it.
  • The builds of that week. Seven llama.cpp commits, three of them forks or a pull-request branch. Defaults change. Public report states are as of 26 September 2026.
  • Reading speed, not answer quality. The check is a planted code (one, or three in the longest documents), and the stress tests looked for crashes, not answers. Most decode figures come from answers of 11 to 100 tokens.
  • Single runs. The untuned DeepSeek 48,000-token read measured 72.3 t/s in one run and 83.3 in another with the same flags, after loads of 3 minutes 55 seconds and 3 seconds; we use 83.3, the less flattering baseline. Flags were copied by hand at 131,072 on 20 September and run through each model's own script on 21 September; Ling's ratio spans both passes, GLM-5.3-Flash's two read lengths.
  • First requests and half windows. Most main-table reads were a load's first request, with the page cache not recorded. Three are at half the window their scripts use; Inkling-Small's long reads at 262,144 were not re-measured.
11

Corrections and updates

  • Two inherited micro-batches nobody had measured. Laguna S 2.1 ran at -ub 128 from July to 21 September, and MiniMax M2.7 was first judged at -cmoe -ub 128. Measured, those values cost a factor of 19.9 and 17.5 in reading.
  • “Confirmed” at the served window. After 20 September, three start scripts carried the comment “Confirmed to LOAD and answer at the full served window (ctx 262144)”. The run cited for Ling's -ub 4096 (10,285 MiB) died on its first request: the comment took its card figure from the load line of a result file that also records the crash, and the script used 4096 until the afternoon of 21 September. The runs cited for Inkling-Small and Qwen3.8-Flash-Next at 2048 (17,281 and 26,561 MiB) did load and answer, but each was one 3,000-token read, the comments gave reading speeds from 131,072 only, and Flash-Next's 45.4 t/s at 262,144 appeared in neither. Both comments were corrected on 26 September.
  • An “experts on the card” test that moved no experts. Our records said moving DeepSeek V4 Flash's experts onto the card was measured and bought nothing (255.1 against 260.8 t/s). Those runs used --n-cpu-moe 50 on a 43-layer model, so every expert stayed in RAM and card use fell by 468 to 567 MiB; they measured the q8_0 cache. The same records called the reports behind both refusals open: #25382 had been closed as completed on 7 July, before any of these runs, and #25582 as not planned on 5 September.
  • A speaking figure that was an 11-token answer. We chose -ub 2048 on Qwen3-235B over 4096 partly because an 11-token answer decoded 12 percent slower at 4096 (7.20 against 8.18 t/s). That is not a speaking measurement. The other reason stands: at 4096 the card peaked at 31,053 MiB. 4096 read 944.2 t/s. The same kind of figure is part of why Gemma 4 26B-A4B kept the default.
  • Labels in our own test files. Result files of runs with no override say “llama.cpp default 512” even when the script set -ub 128 (Laguna) or 4096 (Ling's crash run), and the M2.7 console printed “FIT” for two window settings that failed to load. The server logs are right; the package README lists each case.
  • Update, 26 September 2026. Measurements added at the larger windows: Qwen3.8-Flash-Next with its page cache recorded, MiniMax M2.7 at 196,608, and GLM-5.3-Flash, Ornith-1.5-35B and Qwen3.5-122B at 262,144. Before this, four scripts returned to the default above 131,072, unmeasured. Settings at the larger windows are in section 03.

How this was measured

Every figure is measured on this machine on the date given, unless it is marked arithmetic.

MachineOne NVIDIA GeForce RTX 5090 (32 GB), 188 GiB of system RAM. --threads 24 --threads-batch 24, --parallel 1, flash attention on or auto, one model at a time.
The readA synthetic ledger of near-identical numbered lines, seed 20260920, within 2 percent of 48,000 tokens (24,000 on Laguna S 2.1), one code at half depth and the question “quote the sealed reference exactly. Answer with the code only.” Temperature 0, max_tokens 900, a freshly loaded server, nothing in the prompt cache. Speeds are the server's own timings.prompt_per_second and predicted_per_second. From 21 September a non-empty answer had to contain the code; an empty one passed for reading speed if the code was in the reasoning.
Dates15 September: the DeepSeek depth baseline (a separate study). 19 September: MiniMax M2.7. 20 September: flags copied by hand at 131,072; Laguna could not start, as the copied --n-gpu-layers 999 put all 64,771.15 MiB on the card. 21 September: the rest through their own start scripts, the stress tests and the two-machine runs. 26 September: the larger-window runs, page cache read with mincore (the page-cache reader).
Stress testA fresh load whose first request was Ling's 3,007-token crash prompt, then 40 prompts of real code and text from llama.cpp's source tree, max_tokens 32.
Card memoryRaw nvidia-smi MiB, desktop included: once after load on 20 September, peak during the read (sampled every 2 to 5 seconds) on 21 September.
Scripts beforeOf 25 start scripts, 20 left both settings at the defaults; one set -b 64 -ub 32, two -ub 128, two above the default.
Source linesAt d3146f2b5: defaults common/common.h lines 451 and 452; weights carried to the card ggml/src/ggml-backend.cpp lines 966 to 975, the CUDA backend taking any batch of at least 32 tokens (ggml-cuda.cu lines 5536 to 5539 and 5710); restore points tools/server/server-context.cpp lines 3465 to 3472 and 3559 to 3565.
