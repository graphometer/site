Guide · one RTX 5090 desktop; one laptop comparison

Estimating Inkling 975B's speed from bytes per token

On one RTX 5090 desktop, a calculation put Inkling 975B's writing speed at 5.2 to 5.7 tokens a second; one short prose reply, on a setup reading weights from the drive, ran at 3.43, so the estimate had the right scale but was too high for that run.

In short
  • Estimate a giant model's speed before downloading. "Bytes per token" here means the expert weights the model has to read for each token (word piece) it writes. Divide a rate from a model already timed on your machine by it. Steps and a worked example
  • Treat the answer as a budget, not a promise. It leaves out costs such as attention and reads from the drive. What we found
  • Adding a laptop did not make it write faster in this test. With one run each, this way of splitting the model was slower on each matched prompt type: 3.13 against 3.43 on short prose. Why

01

What to do before a big download

  1. Get the exact tensor list (the named weight arrays) for the compressed file you want, from a published header dump or the header bytes of every shard (file part). A parameter count or average bit width cannot show which tensors got higher precision.
  2. Decide which parts go where. Count the weights of the selected experts that sit in system RAM, plus shared experts, attention or output head if they also stay on the CPU.
  3. Work out a rate from the anchor, a model already timed on your own machine: its bytes per token times its recorded prose speed. Match build, threads, --n-cpu-moe (layers whose experts stay on the CPU side), compression and draft settings. Keep first-request and warm (second-request) figures separate.
  4. Divide that rate (bytes a second) by the target's bytes per token. If even that looks too slow, extra model capacity does not solve the writing speed. If acceptable, still do a real run.

Worked example, with this page's figures

  • Inkling 975B's expert budget (steps 1 and 2): 6,006,472,704 bytes/token
  • Effective rate from three other models' prose runs here (step 3): 31.044 to 34.263 GB/s
  • Predicted decode (writing speed), rate divided by budget (step 4): 5.168 to 5.704 tokens/s
  • Rounded estimate: 5.2 to 5.7 tokens/s (arithmetic)

Both tools are in the page's data folder: a header reader and a calculator that recomputes this page. Neither starts a model.

02

What we found

Inkling 975B is a mixture-of-experts model: it uses only a few of its expert blocks for each token. The worked example above gives 5.2 to 5.7 tokens a second. "Arithmetic" means calculated, not timed; "server-reported" is the speed the server printed. Inkling 975B's own runs, on the desktop alone and with a laptop added (the pair):

The code word was hidden in the prompt. On this build the printed rate is (completed tokens minus one) / eval seconds. Dividing the completed token count itself by eval seconds gives a different rate; the desktop tool call then falls inside the prediction band.

The desktop's top value, 4.98, is an 18-token tool call. The key prose comparison is 3.43 versus 3.13, sampled replies to the same prompt. The calculation gets the scale right, a low single-digit speed, but not the short-prose speed; it leaves out costs such as kernels (the low-level maths code), attention or reads that have to go to the drive, and the runs do not split the gap among them.

03

How the estimate works

File size tells you whether a model fits; bytes used per step, how fast it writes. Count each tensor at its actual quantization (compression level): IQ1_S does not mean every tensor costs one bit per weight.

  • B = sum over CPU expert layers of (bytes of the routed expert banks x selected experts / total experts)
  • R = B_anchor x measured tokens per second
  • predicted tokens per second = R / B_target

B is bytes per token; the routed expert banks are the stored weights of the experts a token can be sent to. R is inferred from the anchor's complete reply, not a measurement of RAM traffic. The estimate ignores cache reuse, computation and attention.

DeepSeek's first reply, the same 166 words and 209 tokens, ran at 2.07 t/s (measured). The estimate uses the second, warm reply, which reused a prompt prefix.

Qwen used speculative decoding, where a drafter guesses tokens ahead (90 of 106 drafted tokens accepted per reply), so its product is only a proxy; removing it leaves the range unchanged. The range depends on configuration: the batch-size sweep's Qwen figure, 16.41 t/s (measured, 21 September), was a 17-character code-word reply after a long prompt.

06

Why the second machine did not add speed

Splitting changes where expert work runs, not the bytes a token needs: 3,647,766,528 bytes per token on the desktop and 2,358,706,176 on the laptop (arithmetic), the same budget in sum. Roughly, time for one token on the pair is desktop expert bytes / desktop effective rate + laptop expert bytes / laptop effective rate + dependent transfers, attention and other work. Each layer waits for the one before, so bandwidths do not simply add. Transfers and the laptop's memory speed were not measured, so this does not prove cable latency alone caused the slowdown, or that every split would lose. More in Two boxes.

07

Limits

  • The rate is not a portable RAM rating. It depends on build, threads, placement, kernels, cache state and draft branch. Downloads ran during the anchor runs; this was not a controlled bandwidth experiment.
  • Checked after the fact. Reconstructed from recorded runs, not tested in advance; not a proven hardware upper bound. File bytes stand in for the bytes actually moved; repacking, dequantization, caches and speculation change real traffic.
  • Short replies only. Attention and cache costs grow with long prompts and are not in the estimate; no sustained essay speed or prompt-reading time.
  • One run per placement, with no breakdown of computation, paging or remote time.
  • Speed only. Nothing here ranks answers or predicts other giant models.
