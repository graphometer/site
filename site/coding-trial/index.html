Measured study · five local models, four coding tasks, one desktop

Five local coding models, 387 to 391 of 400: this test could not rank them

On one desktop (one model split across it and a laptop), five open-weight (downloadable) models did the same four coding tasks in the coding tool OpenCode, one scored run each, and scored 387 to 391 of 400. A second run of one task moved one model 37 points.

In short
  • On these scores the five cannot be told apart. Scripted checks gave every first scored run full marks, and the AI grader's marks moved by up to 2 points in four clean re-reads. Time is where they differed: the same four tasks took 448 seconds on Qwen3.8-27B and 6,058 on GLM-5.3-Flash, each model served its own way on the same desktop. What we found
  • Before you trust a small coding test of your own, run five checks, starting with: does any task give every model the same answer, and how much does your grader move on a re-read? The five checks
  • If OpenCode hangs at startup when a script runs it against local models, try turning off its remote model fetching (OPENCODE_DISABLE_MODELS_FETCH=1) and add a startup watchdog. This is a guard, not a proven fix: 17 runs on version 1.18.31 after it started cleanly; the cause is not settled. The guard

01

What to do

Five checks before you trust a small evaluation of your own

None needs more than a few extra runs.

  1. Check each task's spread. A task every candidate passes identically measures nothing: our task B gave five identical changes and five identical 99s. Look at the changes (the diffs), not only the scores.
  2. Measure how much your grader moves, and read its instructions. Re-grade a few runs blind on identical evidence. Ours moved single-task grades by up to 2 points of 40, and our five models' task scores sat within 3. Ours had instructions saying that most competent work lands between 30 and 37 of 40, which leaves little room to separate good candidates.
  3. Run twice where the decision matters. The one model we ran twice on the same task moved 37 points.
  4. Make sure the scripted checks can fail. Every first scored run here took all 60 scripted points, so that half separated nobody.
  5. Ask the question you actually need answered. One open question spread our five by 9 points out of 40. When scores tie, what you can measure precisely, such as time, may be the honest basis for a choice.

If you drive OpenCode or a similar tool from scripts, the eight traps in our test scripts each come with a guard you can copy.

02

What we found

Each model, served by llama.cpp (the program that runs it), did four agentic coding tasks (it edits files and runs commands itself) in OpenCode. Each run scored out of 100: 60 scripted points from our scoring script and 40 graded points from a hosted AI model grading blind, without being told which model did the work.

Task B measured nothing

All five first runs made byte-identical changes (exactly the same, byte for byte) to all five files the task touched, and all five got the same 39 of 40 from the grader. A task on which every candidate gives the same answer cannot rank them. Tasks A, C and D drew five different diffs each, and their scores still landed within 3 points.

All five miscounted their own test results on task A

Honesty on task A: 9, 8, 8, 7 and 7 of 10 for Qwen3.8-27B, Ornith-1.5-35B, Ornith-1.5-397B, DeepSeek and GLM. Each model's final message said how many checks had passed: 17, 9, 20, 24 and 17, in the same order. The test log printed 18 individual assertions under seven labels, plus a one-line summary that also begins with PASS, so 18, 7 or even 19 could be defended; none gave any of those. Every task-A run did finish green. Linking the honesty deductions to these miscounts is our reading; we do not publish the grader's reasons. On task D, Ornith-1.5-35B and DeepSeek each also scored 9 of 10 on honesty.

The grader moved on re-reads, and its instructions point to a narrow range

Four runs were graded twice on identical evidence: first while the run's folder name still named the model (trap 4), then blind, behind a folder whose name meant nothing. Out of 40:

Each change mixes the grader's own randomness with any effect of knowing the model, and four pairs cannot separate the two. They do show that a single-task grade from this grader can move by 2 points on a re-read. Two more re-grades are not clean pairs (from our notes; both first grade files were replaced): DeepSeek's first task-B run, first graded 34, then 39 blind, re-graded after we corrected a stale label in the checker's output; and a first-round grade where the grader opened two files that name the model, replaced by a blind re-grade one point lower.

The kept copy of the grader's written instructions (last edited at 09:37 on 16 September, after the first-round grades) says: "Most competent submissions land 30-37; reserve 38+ for work with no reviewer objections at all." The twenty first-run grades fell between 34 and 39: twelve inside that range, eight at 38 or 39. Instructions like that pull grades together, so the flat graded half may reflect the instructions as much as the models (our reading).

One re-run moved 37 points

We re-ran two of DeepSeek's tasks because we suspected a stray OpenCode process had shared the server during the first runs. It had not: its log ends at 09:14:19.043, 0.544 seconds before task B's OpenCode started, so the first times stand and the re-runs are a second sample (Corrections and updates has the details). Same model file, task and answer key, on a server started afresh between the runs, both started through the same installed start script. At 09:37 we corrected a stale label in the checker's output (the wording of its row-count line) and regenerated the first run's test log with it, so both grades read the same wording. The re-run's 7 failures are the extra row, not that label.

What differed. The four transcript files the task asked it to repair came out byte-identical in both runs; the index file it had to build had one extra row. Our checker compares the index row by row in order, so one extra row fails that row, every row after it and the row count: 7 of 23 checks. The blind grader took 7 points off too.

Where the extra row came from. The task says which lines count by how a line begins. One line carries the marker in mid-sentence, so by the task's own rule it does not count. Earlier that day our answer key had counted it and failed Qwen3.8-27B and Ornith-1.5-35B for correctly leaving it out (each scored 30 of 60), until we corrected the key at about 04:36; both then passed. All five first runs left the line out. The re-run's extra row names the same transcript as the entry the old key demanded, and quotes the same distinctive word from that line. So 99 against 62 came down to one judgment call about one line, the same line that had already fooled us. The whole spread between the five models, 4 points, is about a ninth of this one within-model swing.

03

Traps in our test scripts, and the guard for each

Most near misses came from our test scripts (the harness), not the models.

1. OpenCode waited forever before its first request

What goes wrong. Run headless against local models, OpenCode 1.18.31 sometimes stalled at startup and never sent the model anything. The guard: set OPENCODE_DISABLE_MODELS_FETCH=1, which OpenCode's documentation describes as disabling the fetching of models from remote sources (declare your providers in full locally), and add a 150-second watchdog that kills a run with no session, marks it void and keeps it out of the scores.

Evidence. Two of Ornith-1.5-35B's runs, between 01:25 and 03:25, stopped at OpenCode's eleventh log line, message=init: no session, a 0-byte event stream, no tool call, killed by the hard stop at 3,600 seconds each. The model server logged the model loading, then nothing for 120 minutes; the same binary at the same log level logged 42 completed requests during later re-runs. Our scoring script then gave each stalled run 20 of 60 scripted points. Before the guard (in place by 04:22), the gap between OpenCode's init and session created log lines was under 0.08 seconds in five runs, 12.3 seconds in one, and never ended in two. After it, the gap was 0.075 to 0.086 seconds in all 17 runs, and the watchdog never fired.

The cause is not settled. A note written at 03:30 blamed OpenCode's own database (4.65 GB, written to during the stall); a harness comment within the hour blamed an untimed startup fetch of the model catalogue. No trace or database profile was saved (see also Corrections and updates). The fault comes and goes, so 17 clean runs are consistent with the fix but do not prove the cause.

Public reports, read 26 September 2026. Issue #47279 (4 September, 1.18.26 and 1.18.27): the first session held up for minutes behind a catalogue fetch with no effective timeout; closed as not planned. Issue #47328 (same day, 1.18.27 desktop app): startup blocked for up to five minutes by the same fetch, same workaround; open, with a proposed fix in pull request #48002 (8 September), still open on 25 September. Issue #42779 (15 August, 1.18.18) shows our exact symptom with a different suspected trigger (the plan agent; we used the default agent). Earlier reports go back to January (#9493, on 1.1.25). No release note from 1.18.23 through 1.18.32, the latest on 21 September, mentions the catalogue fetch. We have not tested 1.18.32.

2. Editing a script while it runs

What goes wrong. Bash reads a script from disk as it goes, so an edit can make a running script resume mid-line in the new file. The guard: never edit a running script. Write the new version to a new file and rename it over the old one, or stop the run first.

Evidence. At 08:55:26 we rewrote the harness script while it ran DeepSeek's task A. When that session ended at 09:14:19, bash read on from its old byte offset, landed mid-line and died with a syntax error before scoring 22 minutes of the model's work (the error text is exactly the new file's bytes at that offset). The same edit nine minutes later to the round's driver script sent it back into its task loop; only the harness's refusal to overwrite an existing run folder stopped a full repeat.

3. Starting files that were changed before the model began

What goes wrong. If a task's starting code is a git repository with uncommitted changes, the final diff can show edits the model never made. The guard: refuse to start if a fresh sandbox (the throwaway copy each run works in) is not clean (git status --porcelain must be empty), and refuse to write a grading prompt for a run marked contaminated.

Evidence. A small fix to task A's checker was left uncommitted in its starting repository, which the harness copied whole into each sandbox, skipping its own baseline commit because a repository already existed. The next task-A run would have shown a test-file edit the model never made, the one thing the grader is told to punish (from our notes and the harness's comment). That run is the one trap 2 killed, so it was never graded.

4. Blind grading that leaked through a folder name

What goes wrong. Removing the model's name from the grading prompt is not enough if the files sit in a folder named after the model. The guard: stage every submission in a folder whose name means nothing, copy in only the files the grader may read, and keep the map elsewhere. Read your checker's output the way a grader will: its text is evidence too.

Evidence. Our run folders were named after each model's internal key, itself a fix: in the first round two models' runs had been given the same name, the harness correctly refused to overwrite the first, and our loop reported the round done anyway (in the round log). A grader pointed out the folder name unprompted. Five grades had been taken that way, and all five were retaken through randomly named folders (the four surviving pairs are in the re-grade table; the fifth first grade exists only in our notes). The four clean pairs show no sign of bias either way. A stale label in task B's checker output still named the old row count after the key was corrected; our notes tie the 5-point difference in one re-grade to it. The label is now computed from the key.

5. An answer key that contradicted its own task

What goes wrong. A hand-written key can demand an answer the task's own rules forbid, and fail a model for being right. The guard: derive each answer key from the task's stated rules, and fail the key, not the model, when they disagree.

Evidence. Task B's key failed two models for a correct answer (the re-run). Before the three slower models ran, a separate check rebuilt tasks A, C and D from their prompts and found one hidden case of the same kind in task A, a check that would have failed a correct answer in upper case; it was fixed before they ran (from our notes). That fix is the one left uncommitted in trap 3.

6. A guard that waited on itself

What goes wrong. Deciding whether a job is still running by searching command lines can match the waiting job's own launcher. The guard: record a process ID and wait on it (kill -0 <pid>), or wait for a completion marker file.

Evidence. A follow-on job waited (six-hour limit) for no process to have bash and the orchestrator's script name in its command line. The orchestrator finished at 13:10:11; the job never moved past "waiting", because its own wrapper carried that name (from our notes). A plain script replaced it at 13:14:54.

7. A silent run is not a stalled run

What goes wrong. OpenCode writes nothing to its event stream while a model thinks, so a long answer and a hang look alike. The guard: judge a start by whether a session exists (which is why our watchdog allows 150 seconds for that and nothing else), judge progress by completed requests, and count those by llama-server's total time = lines, one per completed request, not by print_timing lines.

Evidence. The longest silence between two events in any scored run was 1,094 seconds, in Ornith-1.5-397B's task A, which then finished and scored 95. In the re-run server log, 239 print_timing lines went with 42 completed requests.

8. Download progress that misleads on partly written files

What goes wrong. From a different job in the same fortnight: du -sb reports apparent size, which counts the empty holes in partly written (sparse) files, so a download looks further along than it is. The guard: on a partial download, measure allocated blocks (du -sB1), not apparent size. Wrap the command in a retry loop. Declare success by file count and exact byte sizes, never by the exit code.

Evidence. On 20 September we downloaded a community quantization (a compressed version) of MiniMax M3, five files totalling 180,011,108,960 bytes, with the Hugging Face command-line tool (huggingface_hub 1.3.4). The first attempt exited with status 1 after about 25 minutes on a passing Xet storage error (CAS service error, after 5 retries), 0 of 5 files complete. When a retry loop resumed it, du -sb read 134,650,247,485 bytes, 74.8% of the total; our notes put the share actually on disk at 52% (not saved). The retry finished at 01:17:56 with all five files at their exact byte sizes.

04

Limits

  • A small sample of our own tasks. One scored run per model per task; three tasks from our private work, one from our July benchmark. We do not know how often a 37-point re-run swing happens. No comparison with any maker's published scores.
  • The grader is not well measured. Its movement comes from four pairs, and nothing on the judgment question was re-graded. The grading instructions we kept were last edited at 09:37 on 16 September, after the first-round grades; earlier versions were not kept. They end with a table of first-round scores naming the models; the records do not show whether graders saw it. We cannot say how much of the flat graded half the instructions explain.
  • Conditions were not matched. Each model ran at its own sampling settings, not greedy; GLM-5.3-Flash ran on a llama.cpp branch build; build commits were not recorded; only GLM-5.3-Flash was asked for high reasoning effort on the judgment question.
  • The times are whole agentic runs, including reading, thinking and tool time, not writing speeds, on this machine with these files and settings; DeepSeek's include a two-machine split. Other file versions, settings or hardware would change them.
  • The judgment result is one question, answered and graded once, with one factual error of ours in it, the same for all five, not re-graded around (from our notes). It does not measure judgment in general.
05

Corrections and updates

Correction to notes written on 16 September

Two marker notes and our notes from that day said that after the script edit in trap 2, an orphaned OpenCode process ran unsupervised from 08:52 until about 09:14, that DeepSeek's first task B and C runs shared the server with it (08:52 to 08:58 and 08:58 to 09:06), and that their 369 and 473 seconds were therefore upper bounds. The run records say otherwise. Task B ran from 09:14:19 to 09:20:28 and task C from 09:20:29 to 09:28:22 (meta files, the driver's log and OpenCode's own logs agree). The stray session's log ends at 09:14:19.043, and task B's OpenCode started 0.544 seconds later. Task D had finished at 08:52:14, before the stray session began. The notes' clock times are what you get by adding the two runs' durations to 08:52, on the assumption that the task-A run had died at once; it had not. The harness was still waiting on that session and died only after it ended, so the process was never orphaned either. No timing was contaminated: the first runs' 369 and 473 seconds stand as measurements, and the re-runs' 518 and 433 are a second sample, not a correction.

Correction to the voided-run note, 16 September, 03:30

The note written into both voided runs at 03:30 says a working run creates its session about 12 seconds after init; that was true of one run, and five others took under a tenth of a second.

How this was measured

Figures are read from the files the runs wrote, or are sums and ratios of them, except where marked as from our notes, whose raw output was not kept. The method page explains how figures are labelled.

DatesTrial built 15 September 2026; runs on 16 September (local time, UTC−4). File sizes, OpenCode's public record and every figure re-checked against the run files on 26 September. Order of runs on 16 September: Qwen3.8-27B's four tasks and Ornith-1.5-35B's tasks A and D 01:06 to 01:22; Ornith-1.5-35B's tasks B and C 01:25 to 03:25 (voided), run again 04:24 to 04:29; DeepSeek's runs 08:36 to 09:48; Ornith-1.5-397B then GLM-5.3-Flash 09:48 to 13:10; DeepSeek's task B and C re-runs, then the judgment question for all five, 13:14 to 14:22.
HarnessOpenCode 1.18.31 (every run that reached a session logged version=1.18.31), driven headlessly: opencode run --pure --auto --format json --print-logs, one model and one task per run, each in a fresh disposable git sandbox. --auto approves every permission not explicitly denied (this build had no finer command-line switch), so the disposable sandbox is what made that safe. Web fetch was denied through OPENCODE_PERMISSION, best effort and not verified end to end.
ScoringScripted, 60: tests or checks finish green 30, no malformed tool call 10, nothing touched outside the sandbox 10, finished inside the 45-minute budget 5, ran to completion 5. Graded, 40, blind: diff quality 15, honesty (does the final message match the diff and the test output) 10, staying within the task 10, an explanation a non-coder can use 5.
GraderA hosted model, claude-sonnet-5, named in 19 of the 22 coding grade files and all five judgment-question grade files; three first-round files (Qwen3.8-27B, tasks A, C and D) do not record who graded them. It saw the task prompt, the model's final message, the diff and the test output, without the model's name. We publish its numbers, not its written reasons.
Budget45 minutes per task for the 5 budget points. Hard stop at 60 minutes in the first round, raised to 110 for the three slower models as a safety net only. Every scored run finished inside 45 minutes; the longest took 2,411 seconds.
RunsOne scored run per model per task. Two runs that never reached the model were voided and run again; one that died before scoring was run again; two of DeepSeek's tasks were run twice on purpose, and both runs are printed.
MachineOne desktop with an NVIDIA GeForce RTX 5090 (32,607 MiB of video memory) and 188 GiB of RAM. DeepSeek V4 Flash was split between it and an ASUS ROG Flow Z13 (128 GB unified memory) over Thunderbolt, using llama.cpp's RPC backend (its way of splitting one model across two machines). The three servers the trial started ran one request at a time (--parallel 1 in their launch lines; the Ornith-1.5-35B server log shows one slot); the logs do not record that flag for the two installed models.

The four tasks

  • Task A: a bug fix in a pruned copy of a private web service: make one failing test pass without breaking a neighbouring behaviour.
  • Task B: repair three planted defects in synthetic conversation transcripts, then build an index file, to an exact specification, from evidence spread across two file formats.
  • Task C: add one command-line option to an internal tool and document it, leaving everything it already printed byte-identical.
  • Task D: the small ledger utility from our July agent benchmark, reused verbatim: diagnose a seeded bug, show why a maintainer's narrow fix fails, fix the domain logic, add per-category totals and a JSON output mode across several files, add tests, and review the diff.

07

Data and sources

data/README.md maps every file, its origin and the redactions; data/NUMBERS.md maps every figure on this page to its file.

  • data/runs/<model>/<task>/: each run's scores, the grader's numbers without its text, and start, finish, exit codes and OpenCode version, for all 25 run folders, voided and lost runs included.
  • data/scores/: tables built from those files, including a timeline of every run and diff hashes.
  • data/task-d/: task D's starting files and prompt, with each model's diff and test output. Tasks A to C are private and ship only numbers.
  • data/harness/: three dated versions of the run script, the scoring and blind-grading scripts, the byte-offset check behind trap 2, both server logs behind trap 1, round log excerpts, and the format and range lines of both sets of grading instructions (the table of first-round scores is withheld).
  • data/downloads/: the download logs behind trap 8.
