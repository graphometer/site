Model field card · one RTX 5090 desktop, alone and with a 128 GB laptop

DeepSeek V4 Flash 0731: one desktop or two machines? Here, the desktop alone was faster for long prompts

In tests on 21 September with the same 3-bit file, one RTX 5090 desktop answered a 48,024-token request in 75.2 seconds and the desktop plus a laptop took 416.4 at best; the two setups also differed in prompt chunk size and in where the model’s layers sat.

In short
  • Run the 3-bit file on the desktop alone and read the prompt in bigger chunks (-b 4096 -ub 4096). It took in the 48,024-token prompt at 690.9 tokens a second (measured 21 September, before the thread pinning below). The settings, side by side
  • Match the chunk size to the file. The larger 8-bit file did best with even bigger chunks (-b 8192 -ub 8192). On that file they sped up reading the prompt, not writing the answer. The desktop results
  • If you split it across two machines anyway, keep the chunks at 2,048 or smaller (-b 2048). With 4,096 the long request failed, with “Remote RPC server crashed” in the log. The split results

01

What to do

DeepSeek V4 Flash 0731 is the 31 July 2026 release. It is a mixture-of-experts model: each token (a piece of text) uses a few of many expert sections, which can be held in system RAM or on the graphics card. The 3-bit and 8-bit files are compressed copies of its weights; the 3-bit file stores less per weight and is smaller. llama.cpp is the program that runs the model. -b (batch) and -ub (micro-batch) set how many prompt tokens it reads at a time.

Single requests, 24 threads, before the thread pinning and llama.cpp change described below. Times count the whole request on an already loaded server.

Use the 3-bit file on the desktop alone, reading 4,096 prompt tokens at a time. The download is UD-IQ3_XXS; flags --n-cpu-moe 36 -b 4096 -ub 4096 --no-repack, where --n-cpu-moe 36 sets how many layers keep their experts in system RAM.

For the larger 8-bit file, put all experts in system RAM and read 8,192 at a time. File UD-Q8_K_XL, flags -cmoe -b 8192 -ub 8192 --no-repack. Keep each chunk size with its file, and keep --no-repack; removing it was not tested.

Pin the threads and use mainline llama.cpp. Pinning makes the program’s threads run on chosen CPU cores; mainline is the project’s main code. Cores 0 to 7 with taskset, 8 threads, and GOMP_SPINCOUNT=10000000. Both made the desktop faster in tests: pinning in writing speed about 96,000 tokens deep (spin setting not tested alone), mainline in 8-bit prompt speed. The gains

On two machines, the setting kept on 21 September was -b 2048 -ub 512. -b 2048 -ub 2048 also completed and was faster; -b 4096 -ub 4096 failed once. Single requests. The split results

02

What we found

The desktop alone, tuned (20 and 21 September)

Each test, run with 24 threads before the 29 September thread pinning, was one request at temperature zero: a made-up ledger with a code word hidden at its midpoint to repeat, up to 900 generated tokens. Prompt speed is how fast the model takes in the prompt; writing speed is how fast it generates, hidden reasoning included.

The window is the most text the server holds at once. The visible answer was 17 characters; 8-bit reasoning text was 216 to 332 characters; timed generation was 70 to 106 tokens on the 8-bit file and 59 to 86 on the 3-bit desktop. The slow 8-bit row records only -cmoe; its progress interval supports a batch of 2,048, but the micro-batch is not recorded.

Each returned the exact code. The 3-bit desktop's 48,024-token request took 75.2 seconds (21 September, before the thread pinning); the 150,103-token prompt was read in 237,469.00 ms and the whole request took 244.8 seconds, on an already loaded server, not counting weight loading or the agent-framework waits further down.

Bigger chunks cost card memory: 8-bit use at load rose from 17,063 to 22,089 MiB at the 131,072 window, a difference of 5,026 MiB calculated, and was 26,023 MiB at 262,144. The 3-bit desktop peaked at 28,930 MiB and finished 40 of 40 mixed public-text stress prompts without a crash; the longest was 9,135 tokens.

The two-machine split, re-tuned (21 September)

Same 3-bit file, 262,144 window, no draft; 8 whole layers on the card, 10 expert sets in desktop RAM, 25 whole layers on the laptop.

  • -b 2048 -ub 512 (kept): prompt speed 161.8 tokens a second on 2,998 tokens and 102.5 on 48,024; writing on those short answers (67 and 69 tokens) 14.76 and 12.04. The 48,024-token request took 474.2 seconds.
  • -ub 2048: prompt speed 224.9 and 117.0, 14.1% faster at the longer depth calculated. The 48,024-token request returned the exact code in 416.4 seconds.
  • -b 4096 -ub 4096: the 48K request failed after 40,960 tokens with “Remote RPC server crashed” measured failure. -ub 512 was kept because of the laptop GPU hang at 4096, not because 2048 failed.
  • 150,103 tokens (-ub 512): 2,922.9 seconds to read (48.7 minutes calculated), writing at 7.66, 2,933.8 seconds for the whole request. The older 15.9 to 17.1 split band came from short tests at a 131,072-token window, not this run.

What the next turn costs

At the split's 48K depth a real follow-up processed 238 tokens in 5.4 seconds at -ub 512, or 228 in 5.0 seconds at -ub 2048. Swapping the last question instead went back roughly one micro-batch: 533 tokens in 10.0 seconds versus 2,065 in 28.2 seconds. An edited or regenerated last turn can pay that; an ordinary follow-up need not.

The 15 September full-window runs

At a 262,144-token window with no batch flags, the desktop 8-bit file read 150,475 tokens in 2,062,226.61 ms at 72.97 tokens a second. On 20 September, with -b 8192 -ub 8192, it read 150,324 tokens in 313,172.17 ms at 480.00. Same binary path in both records, but the 20 September record names no build, and prompts and tests differ: not a one-change comparison.

At the same window the 3-bit split read 230,835 tokens in 6,580,695.01 ms at 35.08 (109.7 minutes calculated), wrote a 25-token answer at 6.49, found 3 of 3 codes and peaked at 25,824 MiB. At a 131,072-token window it read 120,305 tokens at 58.70. Both split runs: no batch flags, 24 threads, the 8 / 10 / 25 placement.

Two other 8-bit settings, tried together, that did not earn a change

--n-cpu-moe 50 together with a compressed attention cache (--cache-type-k q8_0 --cache-type-v q8_0) read a 16,011-token prompt at 82.41 versus 81.64 tokens a second at the default batch, and 255.12 versus 260.82 at -b 4096 -ub 2048 (20 September). This was one combined test, not a test of either flag alone. The model has only 43 blocks, so 50 does not show experts moved onto the card. The test allowed 8 generated tokens and checked no answer. Nothing was changed.

llama.cpp reports, read 26 September 2026: quantized K-cache corruption is closed; the follow-up cache report and garbled output with CUDA experts are closed as not planned. Closure does not show these builds were fixed.

On a short 8-bit turn on 12 September, the first visible word came after 60.5 seconds (including reading the framework's system prompt), then 15.0 tokens a second: a small prompt, so faster than the band above.

The earlier draft-model comparison

A draft model is a small companion that guesses the next few tokens for the large model to check. On 13 September, with up to 8 draft tokens allowed, guesses were accepted at 61.4%, 62.8% and 63.9% on the 3-bit file and 68.0%, 84.6% and 69.4% on the 4-bit file (short turn, 8,000-token test, fresh-prompt test). Mean accepted runs were 2.82 to 3.75 tokens. At the 8,000-token test the best 4-bit setup wrote at 19.25 tokens a second with the draft against 12.78 without, 51% more; the 3-bit file 18.12 against 16.15, 12% more calculated.

Placement changed too, so this is not the draft alone: whole layers moved off the card (4-bit from 5, 14 and 24 to 2, 13 and 28; 3-bit from 8, 10 and 25 to 4, 14 and 25: card layers, expert sets in desktop RAM, laptop layers). Prompt speed fell from 184.6 to 148.8 on the 3-bit file and 145.4 to 121.9 on the 4-bit file.

The 4-bit draft preset loaded DeepSeek's own draft model natively: maximum draft length 6, minimum 0, probability floor 0.50. On 15 September it wrote near 19.6 tokens a second and gave up prompt speed to do it.

Recall and tool calls at depth

On 14 September, through an agent framework on the 3-bit split, about 48,000 tokens of seeded history became a 52,928-token prompt; the model found 3 of 3 hidden codes and wrote a file through a tool, and did both again at 102,478 tokens. First visible content came after 543.65 and 1,537.75 seconds, both including framework setup. It took three attempts: the first failed its time limits; the second holds the 48K and 96K checks but failed another; the third reran the short checks and passed. No single attempt holds every part.

The 4-bit draft preset passed only the short tool-and-recall checks (15 September); its direct tool-schema call took 5.8 seconds.

The 3-bit run's eight attention-cache buffers sum to 892.25 MiB at a 131,072-token window; doubled for 256K, about 1,785 MiB calculated, not run.

Starting from a long history (cold wake)

Cold wake: the wait while the server rereads the whole history. On the desktop alone on 13 September, first visible content after a 102,480-token history took 1,396.6 seconds (23.3 minutes calculated) at about 73.4 tokens a second, with 3 of 3 codes found. On two machines the nearest equivalent is the 102,478-token check above, at 66.6 tokens a second; the table's 184.6 (a 7,841-token prompt) does not extend to 100,000 tokens.

A saved slot (the server's stored copy of the history) did not survive a restart: it was not put back, and the next request read 102,846 prompt tokens again, first content after 797.57 seconds. The record marks it FAIL. The model file records attention.sliding_window = 128, the mechanism behind that full re-read, described in the warm-wake study.

DeepSeek V4.1 Flash, parked in September

On 14 September the 4.1 version ran on the desktop through a community llama.cpp port that keeps a small expert cache on the card, a second tier in system memory (sizes below) and streams the rest from a drive. It could not complete a tool call through an agent framework; a direct tool call worked with thinking off only. It was parked. A later batch-setting attempt on this port failed to create a model context.

03

Limits

  • Setups, not machine count, and one model family. The 3-bit rows share a file but compare separately tuned setups on different machines; the older rows also change the file. The wider comparison is on the two-box study.
  • No answer quality. Speed, memory, recall and tool plumbing only; the 40 of 40 stress run is a crash check, and nothing shows 4-bit answers beat 3-bit.
  • Writing speeds count hidden reasoning. The chat template reported thinking on; our setup lists a per-request off switch stated, untested here.
  • The window was not filled. The deepest new 3-bit prompt is 150,103 of 262,144 tokens, and the compressed attention cache was never checked for correct answers.
  • No long-context result for the two-machine 4-bit preset. Its check covered the short tests only, and its files were deleted on 11 October, so it will not be re-run.
04

Corrections and updates

Update, 25 October 2026: three changes

The desktop alone is still the setting we use. Two changes made it faster. On 29 September we added the thread-pinning bundle (cores 0 to 7 with taskset, 8 threads, GOMP_SPINCOUNT=10000000; the spin setting was not run on its own). On a letter written about 96,000 tokens deep, writing speed rose from 8.88 to 12.57 tokens a second on the 8-bit file and from 12.92 to 17.45 on the 3-bit file. On 11 October we moved to mainline llama.cpp: on an 18,000-token request at the 262,144 window, the 8-bit file read at 505.7 tokens a second against 457.4 on the older build, and wrote at the same rate (12.96 against 12.88). The third change is a removal: on 11 October we deleted the two-machine 4-bit files, so the two-machine preset is history, not an installed setting. The October roster (the site's list of October runs) has the runs.

Update, 26 September 2026

The earlier recommendation led with the two-machine 4-bit file and its draft model. Tuning how much prompt text is processed in each batch changed the whole-turn result: the desktop now finishes the measured long-prompt requests sooner. The 4-bit split with a draft was not re-tuned in the new sweep.

How this was measured

Desktop: NVIDIA GeForce RTX 5090 with 32,607 MiB of VRAM, Intel Core Ultra 9 285K, 188 GiB of RAM. Second machine: ASUS ROG Flow Z13 with 128 GB of unified memory, on Thunderbolt, running a worker built from the same source commit as the desktop host. One model process and one request at a time. Measured 12 to 21 September 2026; later runs 29 September, 11 October and 18 October.

ModelDeepSeek; released 31 July 2026 (repository creation date, read at revision 7872f01b), MIT license, read in full at that revision vendor; the GGUF header also records mit. The model card says it ships with a speculative decoding module attached vendor.
Shape43 blocks, 284.33 billion parameters, 256 experts, 6 used per token plus 1 shared (3-bit GGUF header). No active-parameter figure: the model card states none, and the header lacks the expert width one would need.
Windows131,072 tokens for the 12 to 15 September runs and the 20 September 8-bit runs at 48,073 tokens; 262,144 for the 15 September full-window sweep, the 20 September 8-bit run at 150,324 tokens and the 21 September 3-bit runs. Trained window in the header: 1,048,576.

Data and sources

The package under data/ holds the model card and LICENSE (data/vendor/), GGUF header, run records and scripts, with private names and addresses replaced and nothing measured changed. data/README.md maps every file, lists the redactions and opens with the places where the package looks as if it argues with the page. data/NUMBERS.md maps each figure to a file and a field.

If a number on this page disagrees with a file in its package, the file is right and the page is wrong.
