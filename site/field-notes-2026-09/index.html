Field notes · 12 to 21 September 2026 · RTX 5090 desktop, two entries also used a laptop · eleven entries

September field notes: eleven local AI tests on one RTX 5090

On one RTX 5090 desktop, a launch setting copied from another model's start script made MiniMax M2.7 look too slow to use; with it fixed, the model found all three hidden test codes in a 103,931-token prompt in 251.2 seconds, in one run through the same agent software that had timed out before.

In short
  • If a model reads long prompts far slower than it should, check its micro-batch size (-ub, how many prompt tokens llama.cpp reads at a time; the default is 512). MiniMax M2.7 read the same 3,658-token prompt at 32.3 tokens a second at -ub 128 and at 564.0 at -ub 4096. What to do
  • If llama.cpp refuses the Ollama-library copy of Qwen3.6-27B with expected 4, got 3, use the upstream file. The Ollama-library copy is missing one trailing zero in its header; the upstream file loads. The file check
  • MiniMax M2.7 starts every turn by thinking, and none of the switches we tried closed that. With a 900-token output limit one answer came back empty; with 4,096 it answered. MiniMax M2.7

By Grant Williams · Published 26 September 2026

01

What to do

  1. Check the micro-batch size on a model that reads slowly (-ub or --ubatch-size in the launch line); it was the cause for MiniMax M2.7, while GLM-4.7-Flash and Gemma-4-31B gained at most 19.5 and 3.6 percent. Ours carried -ub 128, copied from MiniMax M3's start script with no recorded reason. A larger micro-batch needs more card memory, so at a very long window it may not load. The batch-size study has the full ladders.
  2. Give MiniMax M2.7 room to think. A 900-token output budget returned no answer text; 4,096 gave a coherent answer. --reasoning-budget 0 does not stop the thinking. Measure your own floor; the Empty Answer study shows how.
  3. To run Qwen3.8-Flash-Next past 262,144 tokens, set the rope-scaling flags (settings that stretch the model past its trained length), or the card pays for a window the server will not use (details).
  4. For Ling-3.0-flash, read in bigger chunks, but not the biggest (-b 4096 -ub 2048, the setting that now ships here). -ub 4096 was faster but one prompt crashed the server (details).
02

MiniMax M2.7: a copied setting, not the model, was slow

What went wrong. On 13 September, through an agent framework at a 131,072-token window (how much text the model holds at once), the 48,000-token test (53,581 prompt tokens) took 1,682.9 seconds, about 28 minutes, and the 96,000-token test returned no answer before the turn ended at 1,800.4 seconds. We closed the model as too slow. The cause was -ub 128 in our launch line; llama.cpp's default is 512.

The fix, 19 September, at a 131,072 window with an 8-bit cache and -b 4096: one 3,658-token prompt read at 32.3 tokens a second at -ub 128 and at 564.0 at -ub 4096, with every expert (the parts of the model that run only for some tokens) in system memory. At 43,909 tokens and -ub 4096, prompt reading ran at 640.2 tokens a second with every expert layer in system memory, 656.5 with the experts of 59 of the 62 layers there, and 666.1 at 58 of 62 with 30,695 MiB on the card; those are prompt-reading rates, and the whole requests, each ending in a short answer, took 72.1, 70.1 and 69.1 seconds. The launch script now installed for this model uses the 59-of-62 placement (where each layer's experts are kept). At that placement, a prompt seeded to the 96,000-token target, 85,763 tokens as the server counted them, was read in 145.48 seconds, 589.5 tokens a second; the whole request, including a 16-token answer, took 147.49 seconds.

The same agent framework, 21 September: the 48,000-token test took 122.1 seconds at 53,584 prompt tokens and the 96,000-token test 251.2 seconds at 103,931, with all three codes found on both and the tool call passed.

Writing speed was not what changed: 32-token answers came out at 9.9 to 10.2 tokens a second after the 3,658-token prompt at micro-batches from 128 to 2,048, and at 9.0 to 10.0 after 43,909 tokens at 4,096; through the framework, 8.0 on 13 September and 8.6 and 7.2 on 21 September, on completions of 160, 180 and 182 tokens. These are short answers, not prose writing speeds.

The native 196,608-token window fits on the card only at a smaller micro-batch: with every expert in system memory, -ub 4096 failed to load, -ub 2048 aborted and -ub 1024 loaded with 31,560 MiB on the card. Only the 3,658-token prompt was run there (188.8 tokens a second).

A warm session survives a real server restart (19 September): 85,778 tokens saved and restored, 1 token counted as new work, a 2.19-second restore, then a 2.17-second request (warm-wake study). On 21 September the installed launch script repeated it: 1 prompt token evaluated (136.8 ms), 16 answer tokens, 1.97 seconds total, stop count 42,898 tokens.

Thinking, measured 13 and 15 September, before the launch fix

The chat template starts the model inside a thought block on every turn and offers no switch to close it. The default, enable_thinking: false, thinking: false and reasoning_effort: "low", each at 65,536 (f16 cache) and 131,072 (8-bit cache): eight calls, and every one produced a reasoning block. Every turn of the 21 September re-run also streamed its reasoning first.

With --reasoning-budget 0 the model still wrote 1,734 and 3,003 characters of thought on two prompts, and the second hit its 600-token cap with zero visible characters, stop reason length; a budget of 256 gave answers and well-formed tool calls.

Given a 900-token output budget, the first coherence test returned finish=length, 900 completion tokens, 0 characters of content and 4,034 characters of reasoning: the whole budget went on thinking. That is the finding of our Empty Answer study; it concerns the output budget, not the launch setting. Given 4,096 tokens the model answered coherently, with well-formed tool calls.

Memory

The file header (read 13 September) gives 248 KiB of cache per token (2 times 8 key-value heads times 128 dimensions times 2 bytes times 62 blocks), so 131,072 tokens at f16 is 31.0 GiB, too much for a 31.8 GiB card beside the weights; that window needs an 8-bit cache. arithmetic Measured, 65,536 at f16 took 21,232 MiB and 131,072 at 8-bit 22,240 MiB, because both hold about 15.5 GiB of cache. This arithmetic describes the memory bill, not the speed.

03

MiniMax M3: the old file had no sparse attention

The file we had, Unsloth's UD-IQ3_XXS, predates llama.cpp's support for this model's sparse attention: it has zero indexer tensors (the parts sparse attention needs) among its 948, so every M3 number we had came from a dense fallback. On it, at -b 4096, reading a 3,658-token prompt scaled with the micro-batch: 22.6 tokens a second at 128, then 67.7, 123.1, 221.3 and 393.8 at 512, 1,024, 2,048 and 4,096.

On the correct file, bartowski's Q2_K_L, at a 131,072 window, -ub 2048 and an 8-bit cache: prompt reading at 147.5 tokens a second on 3,658 tokens; a 58,307-token recall prompt took 300.2 seconds for the whole request, including 165 generated tokens, all three codes found; writing at 8.9 on an 82-token answer and 9.0 on a forced 128-token generation. At the 196,608 window (-ub 512): 72.6 on 3,658 tokens, and the same recall took 856.3 seconds, including 207 generated tokens, 3 of 3 again.

A 262,144-token window with the sparse attention engaged fits only at -ub 128: the compute buffer alone asks for 19,619 MiB at -ub 2048, and the allocation fails at every micro-batch from 2,048 down to 256, and at 128 it loads with 31,525 MiB on the card and reads a 3,658-token prompt at 24.2 tokens a second. We treat 256K as not viable for this model here. Split across the desktop and a laptop, bartowski's larger IQ3_XXS build (167.6 GiB) loaded at -ub 1024, read the 3,658-token prompt at 17.58 tokens a second; writing was not measured (two-box study).

04

GLM-4.7-Flash: fast writing, slower reading on long prompts

The fastest writer in the 12 September sweep. At 131,072 context, all on the card with an f16 cache: 223.65 tokens a second writing and 4,447.44 reading a 20,221-token prompt, the hidden code found, 24,814 MiB, loaded in 21.2 seconds. At its ceiling of 202,752 tokens it read a 189,931-token prompt at 819.70 (28,702 MiB, 28,765 at peak; loaded in 22.2 seconds; 227.43 writing on a short turn; the 29-token three-code answer at 70.48). Reading falls from 4,447 to 820, which is why this page gives a prompt size with every reading rate.

A larger micro-batch read a ~48,000-token prompt at most 19.5 percent faster (2,594.6 to 3,100.2 tokens a second), at a setting whose visible answer came back empty, the code only in its reasoning, and was not adopted.

05

Gemma-4-26B: fast reading at a full 262,144 window

At 131,072 context: 211.07 writing and 10,593.27 reading on a 21,690-token prompt, the hidden code found, 20,646 MiB. At 262,144 it read a 230,855-token prompt at 3,799.69 tokens a second and found all three codes; it wrote at 202.64 on a short turn and the 33-token three-code answer at 121.36; loaded in 23.2 seconds (table).

A larger micro-batch read a ~48,000-token prompt faster, from 8,972.3 tokens a second at the default to a best of 12,063.4 at -ub 2048, with the 17-character code answer written slower (153.8 against 163.7). At -ub 4096 it read slower, 11,811, and wrote that answer at 148.4. It was not adopted.

06

Gemma-4-31B: fills the card; speed is flat from 64K to 128K

At 131,072 context: 73.68 writing, 3,166.30 reading on a 21,690-token prompt, 29,844 MiB on the card with 2,763 MiB free. At 65,536: 73.73 writing, 3,175.57 reading, 24,660 MiB with 7,947 free. Both found the hidden code. A larger micro-batch read a ~48,000-token prompt at most 3.6 percent faster (2,687.5 to 2,784.5 tokens a second) and was not adopted.

07

Ling-3.0-flash: a long window for very little memory

A 124-billion-parameter mixture-of-experts by its maker's count stated. Only 8 of its 43 blocks hold an attention cache, in a compressed form, so context is cheap: 9 KiB of cache per token, 0.56 GiB at 65,536, 1.13 GiB at 131,072 and 2.25 GiB at its native 262,144, 27 times less per token than MiniMax M2.7's 248 KiB. arithmetic In the 13 September agent-framework check, at a 131,072 window at the default micro-batch, it held 6,941 MiB, found all three codes on both tests and made its tool calls; the first read reached first content after 506.68 seconds on a 103,807-token prompt (history seeded to about 95,913 tokens), and a warm turn on that history after 0.96 seconds (2.0 seconds for the turn). At 262,144, loaded in 103.8 seconds, the whole model held 8,314 MiB (table).

The batch-size sweep changed its reading. With -b 4096 -ub 2048, the setting that now ships, it read 727.7 tokens a second on 47,986 tokens and 694.6 on 149,711 at the 262,144 window (21 September, 8,824 MiB at peak), against 238.2 on 47,992 tokens at the default micro-batch at a 131,072 window (20 September). The windows differ. On one window, 262,144, a 3,007-token read went from 201.5 at -ub 512 to 444.0 at -ub 2048, about 2.2 times.

A faster setting was withdrawn. At -ub 4096 it read 1,173.9 on 48,084 tokens and 1,067.6 on 150,153, but one 3,007-token prompt crashes the server with a CUDA illegal memory access, at the 262,144 window. The same prompt passed at 2,048, 1,024 and 512, and 60 code and prose prompts and 50 ledger prompts (a ledger is a long test document holding hidden codes) ran with zero crashes at either setting. The crash log and a reproducer ship in the package.

It has a real thinking off-switch, three in the template: enable_thinking: false, thinking_option: "off", or the phrase "detailed thinking off" in a system message. The opposite of MiniMax M2.7.

08

Qwen3.8-Flash-Next: found the codes past its trained window with rope-scaling flags

At 131,072 context, with the experts in system memory: 11,366 MiB, 22.50 writing, 195.84 reading on a 21,740-token prompt, the hidden code found, about 2 seconds to load warm; its 65,536 preset holds 9,670 MiB and reads 246.9 on a 2,624-token prompt. At 262,144 it loaded in 52.4 seconds, read a 230,803-token prompt in about 23 minutes and found all three codes; it wrote at 25.33 on a short turn and the 32-token three-code answer at 13.58 (table).

With the rope-scaling flags set, recall held at three of three hidden codes out to 459,911 tokens, 1.75 times the trained 262,144, with time the limit: 19.8 minutes at f16 and 262,144 (the q8_0 twin 19.4), then 31.2 and 44.6 minutes at q8_0 at 393,216 and 524,288. At 262,144 the q8_0 cache gave the same recall with 22,019 MiB at peak against 25,226 at f16. This is retrieval, not reasoning across the window: the integration question, a follow-up (526 tokens) asked with the ledger cached, fails against a 5,974-token ledger and against every longer one.

The trap: ask for 524,288 without the rope flags and the server caps the slot (its memory for one conversation) at 262,144, while the card still pays for the big window: 23,816 MiB, the same as a genuine 524,288 window (23,814), against 15,394 on a plain 262,144 load (that server loaded; its probe timed out at 600 seconds).

09

Qwen3.6-27B: one trailing zero decided whether it runs

Two model files labelled Qwen3.6-27B exist on this machine. The one distributed through Ollama's model library declares its rope sections as [11, 11, 10], and every llama.cpp build here refuses it, expected 4, got 3, in under a second. The upstream file, Unsloth's UD-Q4_K_XL, declares [11, 11, 10, 0] and loaded processor-only in 6.39 seconds. This is an interaction between a file variant and a loader's array-length requirement, not an accusation against either project.

10

Qwen3-32B: memory predicted to within two MiB

Its header gives 256 KiB of cache per token at f16, so at 32,768 context (its served rung; the file's own ceiling is 40,960) the prediction was 18.81 GiB of weights plus 8.0 GiB of cache plus 1.04 GiB of compute buffers, 28,518 MiB. The measurement was 28,520 MiB. arithmetic confirmed. The same arithmetic says a 131,072 window fits only with a 4-bit cache, 27.8 GiB in total; f16 and 8-bit do not fit; that window was not run.

In the agent-framework check, with thinking off it passed, tool call included; with thinking on it failed, the tool call not emitted. One run each; we do not generalise it.

11

Llama 4 Maverick: split across two machines

At 167.21 GiB by its header and never served from one machine here, it loaded split across the desktop and the laptop at 131,072 context and wrote at 13.09 tokens a second on a short 51-token reply: a capacity demonstration on a model deleted the next day (two-box study).

13

Limits

  • Speed, memory and recall only. Nothing here measures model quality or ranks models.
  • Most entries rest on one run each, one run per setting or one call per test.
  • Reading rates belong to their prompt sizes and windows. The batch-sweep figures are ~48,000-token prompts, not comparable to the 12 September sweep's ~21,000-token prompts, and speeds through the agent framework are not directly comparable to direct tests.
  • Short answers are not prose writing speeds. Several writing rates come from a hidden code or an answer of a few dozen tokens.
  • MiniMax M2.7's thinking and budget findings date from 13 to 15 September and were not re-run after the launch fix. At its native 196,608 window only a 3,658-token prompt has been run.
14

Corrections and updates

"MiniMax M2.7 is slow." Our first records called this model slow, explained it with the model's cache arithmetic, and closed it on that basis. The speed was our own launch line, -ub 128, inherited from MiniMax M3's start script with no recorded reason; the cache arithmetic only ever described the memory bill. The "why it is slow" reasoning is gone, the wall times that depended on the flag are withdrawn or dated, and the MiniMax M2.7 entry carries the re-measurements.

The timeout that looked like a recall miss. Our test script left error: null when a turn ran out of time without an answer and counted the recall as 0 of 3, so a timeout and a genuine miss looked identical. MiniMax M2.7's 96,000-token test was one, written down as "l128 recall 0/3" (1,800.4 seconds, no answer events), and that record reached this page before we caught it. The same week, a separate run on another model that produced only reasoning and no visible text was also scored 0 of 3, and on a third the script wrote 987.9 tokens a second next to a pass by dividing by a missing first-content time; that run had 326 completion tokens, so it was not an empty answer. The script was fixed before the 21 September re-run: a turn with no answer is now recorded as UNANSWERED. The summary in the package keeps its original values; CORRECTION.md annotates them.

The 700-to-900 note. A working note of ours advised giving MiniMax M2.7 "700 to 900 output tokens or the answer comes back empty". 900 is exactly the budget that returned zero characters; the note was corrected in place the same night (2026-09-13).

The "~40 t/s" verdict. The 15 September budget test's verdict paragraph reports reading at about 40 tokens a second, which does not follow from the log lines in the same record; we do not print it, and the probe log ships unchanged.

The unfinished run. An earlier record of ours, written while the 256K sweep was still running, shows the Qwen3.8-Flash-Next run as unfinished at 192,512 of about 230,000 tokens. The run completed that evening and its entry prints the completed measurement. When two of our records disagree, the log is the number we print.

How this was measured

One NVIDIA GeForce RTX 5090 with 32,607 MiB of graphics memory, an Intel Core Ultra 9 285K and 188 GiB of RAM, 12 to 21 September 2026; an ASUS ROG Flow Z13 laptop joined over Thunderbolt for the two-machine runs. llama.cpp served one model at a time, one request at a time. Card memory is the raw nvidia-smi figure in MiB. Figures are measured unless labelled arithmetic (from a file header) or stated (the maker's figure), as defined on the method page. A hidden code is a test word planted in a long prompt.
