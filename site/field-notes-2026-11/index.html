November field notes: eight traps running AI models at home

What went wrong on our desktop and laptop, what it cost, how we caught it, and one check you can run yourself.

This page is for anyone who runs AI models on their own computer. If you read only one entry, read the first: a graphics card is never fully free, even with no model loaded, and two setups sized close to the card's limit failed here, one of them only after it had passed every short test. The second entry matters if you use document search in a chat app: in our test, a chat still gave a normal reply, without the document and without an error, while its search service was out of reach.

Independent measurements. Not affiliated with, endorsed by, or connected to any maker or project named on this page.
01

The graphics card is never empty, and setups sized to its last gigabyte failed

What happenedThe card's memory (its VRAM) is shared by the driver, the desktop and every app that draws on screen. On the night of 1 to 2 November our test script stopped 102 model servers one after another and read the card's memory about five seconds after each had exited. With no model server running, the card still showed between 710 and 1,642 MiB in use (1,024 MiB is one GiB), and the figure rose and fell through the night. The card holds 32,607 MiB, so that is about 2 to 5 percent of it. Two setups then failed near the top of the card.
SetupResult
gpt-oss-120b, experts of 23 blocks in system RAM (--n-cpu-moe 23), 1 NovDid not load: allocating 1315.93 MiB on device 0: cudaMalloc failed: out of memory
gpt-oss-120b, experts of 24 blocks in system RAM, 1 NovLoaded, 30,627 MiB in use when ready
DeepSeek-V4.1-Flash-1017, batch 3072, 2 NovPassed short checks (a chat, a tool call, a two-token reply). A request of about 32,000 characters then failed after 53.2 s with HTTPError 502: 'Bad Gateway'; highest card reading 31,987 MiB
DeepSeek-V4.1-Flash-1017, batch 2560, 2 NovThree long requests (7,175, 7,175 and 26,781 prompt tokens) answered; highest card reading 30,771 MiB

gpt-oss-120b is a mixture-of-experts model: its "experts" are parts used by only some tokens, so they can live in system RAM. Both gpt-oss-120b starts used a 131,072-token window (how much text the model can hold in view at once). DeepSeek-V4.1-Flash-1017 ran as an MXFP4 file (a compressed format) on a community port of llama.cpp, also with a 131,072-token window. The batch is how many prompt tokens the server works on at once; the 2560 runs used a test copy of the same start script.

What it costOne setting that did not load, and one that passed every short test and then failed on its first long request. We did not measure how much of either failure came from the memory the desktop and driver held.
How it was caughtThe out-of-memory line in the server log, and a check script that read the card every quarter of a second during a long request.
The checkWith no model loaded, run nvidia-smi --query-gpu=memory.used --format=csv and note what the card already holds. Then test any new setup with a prompt as long as your real ones before you rely on it. Short prompts passed here and proved nothing.
02

Document search out of reach: the chat still answered, without the document and without an error

What happenedOpen WebUI (a self-hosted chat app) can search your documents before the model answers. To do that it first sends the question to an embedding model, which turns text into a list of numbers. On 2 November we tested a throwaway copy of Open WebUI (a locally built image tagged v0.12.5) with 20 made-up documents and 10 questions. The embedding model, qwen3-embedding-8b, ran on the laptop, behind a small forwarding service on the desktop.
TestResult
Embedding model reachableAll 10 questions found the right document first
App pointed at an address where nothing was listeningEach of 10 direct searches failed at once with HTTP 400 [ERROR: Error querying knowledge base]; all 20 files failed to index
A chat asking for a door code that is in only one documentHTTP 200 after 8.7 s and a normal-looking reply without the code, saying it needed more context
The same chat, app pointed straight at the laptopHTTP 200 after 5.8 s: The door code for the winter room at Kestrel Hut is **4471** [1].

The direct searches fail loudly. The chat does not. Our note written at the time of the test says the forwarding service had been stopped for that chat; the test log itself records the reply, not the service's state.

What it costNothing here, because it was a test. In daily use, answers that should have come from your documents would come from the model alone, with no sign that anything was wrong.
How it was caughtA test script that asked a question only one document could answer and checked the reply for the code.
The checkAfter you set up document search, take the embedding service down once and ask a question only your documents can answer, so you know what failure looks like on your setup. In daily use, a missing citation where you expect one is the warning sign. A fallback can work: in the same test, the same embedding model run on the desktop's processor also found the right document first for all 10 questions.
03

A request that times out without streaming keeps nothing

What happenedOn the evening of 31 October we asked Mistral-Large-4-1T-A52B six questions. That is a model of about a trillion parameters with about 52 billion used for each token, here as Unsloth's UD-IQ1_S file, a heavily compressed copy, split across the desktop and the laptop with a 32,768-token window. Our client sent each question without streaming (stream=False), so a reply arrives only when it is complete, and gave up after 1,800 seconds. Questions 1, 2 and 6 hit that limit at 1,800.1 seconds, and the client saved no text for any of them. Questions 3, 4 and 5 finished.
What was lostThe server log shows how far each one had got. Question 1 had generated 4,328 tokens (words or parts of words) when it was cancelled, and question 2 had reached 4,713. Question 6 was at 906 tokens on its last progress line when the server shut down.
What it costAbout 90 minutes of waiting across the three requests, with nothing saved.
How it was caughtThree empty answers in the client's results, and the token counts in the server log.
The checkFor long or slow answers, stream the reply ("stream": true in an OpenAI-style request) and write each piece to disk as it arrives. If you must wait for the whole reply, set the timeout from one measured long answer at your real speed, with room to spare.
04

The first answer after a start can crawl while the model is still coming off the drive

By default llama.cpp does not read the whole model file at start. It reads each part from the drive the first time a request needs it. On 1 November we started Beam-1.0-501B-A23B (about 501 billion parameters, 23 billion used for each token; Unsloth's UD-Q2_K_XL file; llama.cpp b11712; 131,072-token window) that way, and then with --load-mode dio, a setting in this build that reads the whole file into memory at start. Each run sent the same 66-token prompt twice and asked for 420 tokens.

StartReady afterRAM free when readyFirst replyRead from driveSecond reply
Default289 s164 GiB1.95 t/s, 289.7 s44.7 GB8.37 t/s, 57.2 s
--load-mode dio135 s11 GiB8.38 t/s, 54.5 s0.1 GB8.29 t/s, 54.3 s

t/s is tokens written per second. "Read from drive" is what the server process read from disk during that reply, rounded to 0.1 GB. A later start the same evening with the same dio setting gave its first reply at 3.62 tokens a second, so reading the file at start did not always remove the slow first answer.

The check. Before you judge a model's speed, send the same request twice and watch the drive during the first one. A much slower first reply while the drive is busy points to loading, not to your graphics card. Our llama.cpp expert-cache page has more of Beam's measurements on this machine, and our Mistral Large 4 page shows loading settings on a second model.

05

A model split across two machines wrote strings of symbols, with no error in the server log

What happenedOn 31 October we split Mistral Large 4 between the desktop and the ASUS ROG Flow Z13 laptop, joined over Thunderbolt by llama.cpp's RPC worker (a small server on the laptop that runs part of the model for the desktop). The desktop held 46 of the model's 72 layers and the laptop the other 26. The laptop's worker was built with both Vulkan (a graphics interface) and RPC support. In the first run, all six answers were strings of symbols and word fragments, for example schedul\"],\" });\':\huile, and the desktop server's log for that run has no error line. A second run with the same split, labelled as the run with the worker on the laptop's processor, gave readable text: two of six included a final answer, and the other four were still reasoning when they hit their length limit.
SpeedThe first run wrote 1.67 to 4.82 tokens a second and the second 2.10 to 3.98, so the speed column alone could not tell the broken run from the working one.
The deviceOur notes from the time say the first run's worker used the laptop's graphics chip through Vulkan and the second was told to use the processor (-d CPU). The worker's own log was not kept, so that cause is not shown here.
What it costOne test run, about 20 minutes, and a speed figure that meant nothing.
How it was caughtReading the answers.
The checkRead the first answers of every new setup before you record its speed. When a worker was built with GPU support, name the device it should use on its command line, and keep its log.
06

A GPU crash deep into a long prompt, with 1,372 MiB of the card unused

What happenedThis follows on from the first entry of our October field notes, which counted five GPU timeout faults in one week. On 3 November we tested Huihui-Qwen3.8-27B-abliterated, a community variant of Qwen3.8-27B with refusals removed, published by huihui-ai (UD-Q5_K_XL file, llama.cpp b11712). It ran with a 229,376-token window and two ways of guessing ahead to write faster: a small draft model and n-gram drafting. The card showed 31,094 MiB in use at idle and 31,235 MiB at its highest reading, 1,372 MiB below its 32,607 total. The server read the first long prompt, 205,741 tokens, at 1,185.6 tokens a second. On the second long prompt its last progress line was at 198,656 tokens, 97 percent of the way, and then the log ends with CUDA error: the launch timed out and was terminated.
Kernel logOur test script counts the lines containing NVRM: Xid (error reports from NVIDIA's driver) in the kernel log since each start. It does not keep the lines, so the code and the program each line names are not recorded.
WindowGuessing aheadHighest card readingXid lines counted
229,376draft model and n-gram31,235 MiB1
196,608draft model and n-gram29,963 MiB0
196,608none27,716 MiB1
196,608draft model and n-gram, second run30,111 MiB0

Runs in the order they ran. The run with no guessing ahead started at 20:14:16, the same second the run before it stopped, so its count may include a line from that stop.

What it costOne crashed server and the run it was in.
The checkAfter any crash on a long prompt, run journalctl -k --since "1 hour ago" | grep -E 'NVRM|Xid' and save the lines themselves, with their code and the program they name. We kept only a count, which is why the second line above cannot be placed.
07

A large model download that kept failing, and the downloader that finished it

What happenedOn 30 October we downloaded a 2-bit community build of DeepSeek-V4.1-Flash-1017 (ISTA-DASLab's GSQ-RCO IQ2_XXS files) from Hugging Face. The hf tool (huggingface_hub 1.3.4) stopped twice with RuntimeError: Data processing error: CAS service error : ReqwestMiddleware Error: Request failed after 5 retries. On the second try its progress bar had reached 1 of 8 files after 29 minutes 48 seconds.
The fixA short downloader of our own. It cuts each file into 128 MiB pieces, fetches them with 16 workers by byte range, retries a piece that fails, and records each finished piece so a restart can skip it. From 15:39:12 to 17:00:22 it fetched the five files on its list (four of the six 2-bit parts and one IQ4_NL Engram file) in 1,856 pieces. It logged 23 piece errors: 16 timeouts, 4 connection resets and 3 short reads. Each of the five files then matched the expected SHA-256 hash in the script's list, which is in the data package.
What it costAbout an hour from the first start of the hf tool at 14:37 to the start of our own downloader at 15:39, gaps included.
The checkIf a large download fails more than once, switch to a tool that resumes by byte range and remembers finished parts. Then hash every file and compare it with the SHA-256 the repository lists for it (on Hugging Face, the LFS hash on the file's page) before you load it.
08

More packet loss while the home line was idle than while it was busy

What happenedOn the evening of 30 October we pinged public DNS servers (the lookup services that turn site names into addresses) four times a second for about 110 seconds, with an upload and then a download in the middle. We ran this twice before changing anything, to two DNS servers the first time and three the second. Over whole runs, 6.1 to 8.9 percent of pings were lost. Splitting each log at the upload and download marks gives an estimate per stretch: the quiet stretches lost 3.8 to 19.3 percent and the busy stretches 0 to 2.6 percent. Our note from that evening records slow web pages while speed tests looked fast. A speed test keeps the line busy, so it can miss loss like this.
After a restartOur notes record that our provider's gateway (the box that connects the home network to the provider) was then restarted. The same test at 22:36 lost nothing: 0 of 446 pings to each of three DNS servers and 0 of 438 to the gateway. A five-minute quiet run on the normal route lost 0 of 597 to each of two DNS servers. A separate five-minute run forced over Wi-Fi, to the provider's DNS server, lost 21 of 597, with a slowest reply of 2,060.6 ms.
What it costAn evening of slow pages. The download in entry 07 kept failing earlier the same day; we have not shown that the two are linked.
The checkChoose one public DNS server and ping it four times a second for five minutes with nothing else using the line (ping -i 0.25 followed by its address), then again during a large download. Compare the loss figure each run prints at the end.

10

What this page does not show

These are single events on our machines, not tests of any product, and several of the mistakes were ours. Entry 01 does not show how much of either failure came from the memory the desktop and driver held. The GPU fault in entry 06 has no proven cause. The device behind the symbols in entry 05 rests on our notes, not a log. The network entry is one evening: the loss stopped after a restart, which is not proof that the restart fixed it or that it is gone.
