GLM-5.3-Flash on one RTX 5090 desktop: measured speeds

We hid three codes in a document of 230,039 tokens (word pieces) and GLM-5.3-Flash found all three after 870.5 seconds of reading (about 14 and a half minutes), on one RTX 5090 desktop with 188 GiB of system RAM, in a single run at the largest window tested.

In short
  • Long documents can work, but blank replies were frequent in one check. The 230,039-token read worked once, on current standard llama.cpp at its largest window (262,144 tokens), using a batch setting that has a known risk (-ub 2048, see What to do). A separate 40-prompt check on the earlier setup at the same window size (with -ub 1024) got 36 blank replies. Details
  • Ask for low or high reasoning effort (low, high). Any other word, including none, gives maximum effort. What to do
  • Read the prompt in bigger chunks at a 131,072-token window (-b 4096 -ub 4096). In September, on the modified llama.cpp, that read 48,168 tokens at 425.1 tokens a second. -ub 8192 did not load.

01

What to do

The current setup is standard (mainline) llama.cpp build b11552 with a 131,072-token default window. Older results ran in September on a modified copy (a GLM-specific fork).

Ask for low or high reasoning effort. The model's chat template (the format that turns a request into model input) turns every other word, including none, into max.

At a 131,072-token window (how much text the server holds at once), read the prompt in bigger chunks (-b 4096 -ub 4096). The micro-batch (-ub) is how many prompt tokens are read at a time. -ub 8192 failed to load.

At 262,144 tokens, use a smaller micro-batch (-ub 1024 or -ub 2048); -ub 4096 does not load. -ub 1024 leaves more memory free but was read only to 47,992 tokens. -ub 2048 made the 230,039-token read; the batch-size study explains a risk with it (llama.cpp issue 28282). The older September command at 262,144:

llama-server --ctx-size 262144 --parallel 1 \
  --batch-size 4096 --ubatch-size 1024 \
  --n-gpu-layers 999 --n-cpu-moe 42 \
  --threads 24 --threads-batch 24 --flash-attn auto

To stop stray reasoning text, try stop strings (text that ends a reply when it appears: --special plus these four). This passed one synthetic test and one tool call on one quantization and the September fork; it is not qualified for production use.

<|assistant|>
<|endoftext|>
<|user|>
<|observation|>
02

What we found

Current setup: standard llama.cpp, since October

On mainline build b11552, at 131,072 it read 16,160 tokens at 394.3 tokens a second and wrote a 707-token answer at 12.59 tokens a second; graphics memory peaked at 27,100 MiB, against 30,619 on the fork. At 262,144 with -ub 2048, it read 230,039 tokens at 264.3 tokens a second in 870.5 seconds and quoted all 3 hidden codes. A 339-word letter on that cached document followed at 12.46 tokens a second, where the fork returned no visible words.

Older runs: September, modified llama.cpp

Code reads asked the model to find codes hidden in a long document; letters were about a document held in memory (cached).

Thread pinning, one run, 29 September. taskset to cores 0 to 7, 8 threads and GOMP_SPINCOUNT=10000000 gave a letter 48,109 tokens deep at 12.18 tokens a second, against 9.77 without; the spin setting was not tested alone.

Older setup: blank and messy answers

Blank replies. A 40-prompt check on the shipped 262,144-token, -ub 1024 setting recorded 36 empty answers and 0 crashes: frequent empty output in that check, not a quality verdict. Hidden reasoning can use up the reply budget (Empty Answer).

Leaked reasoning, 17 September. One synthetic high-effort streaming request wrote a correct three-sentence answer, then more reasoning, a literal </think> tag and a second answer, all visible (689 tokens, finished normally). A second assistant control token came before the restarted reasoning. The tag was in the server's own delta.content, so the test client did not add it. The cause (model file, quantization or runtime) is not known, nor whether the installed launch script still reproduces it.

The guard. With the stop strings, the same test, a tool call and its result passed: one clean 254-character answer stopped on <|assistant|>, and the tool cycle returned the expected call and a visible result. The 26 September launch script used neither --special nor stop strings.

Coding scores

In the local coding trial, it scored 387 of 400 on four single-run tasks in 6,058 seconds of task wall time: 60 of 60 mechanical points each, blind judgment scores 34, 39, 37 and 37 of 40. A one-question judgment test scored 39 of 40 in 423 seconds from question to answer.

03

Limits

  • Single runs. One run per setup, no confidence intervals; the coding scores are no stable ranking.
  • Maximum effort only. Every long-window run, and so every long-window speed here, was at maximum effort. None was measured at low.
  • Not the full window. The file states 1,048,576 tokens; the deepest prompt measured is 230,039, and not on the -ub 1024 setting the September launch script used. Finding three codes once does not show reliable reasoning at that length.
  • No measured RAM floor. The launch script carries a 150 GB RAM availability check, a figure taken from another deployment, not measured for this model.
04

Corrections and updates

Correction, September 2026

The short-answer test called its 20.5 seconds a first-word time (first_word_s). The client did not stream, so this is whole-request time; no time to first token was measured. The 9.58 tokens a second server timing stands.

Correction, October 2026: there is no effort none

This card said the long-window runs used effort none. The template turns every word but low and high into max, so they ran at maximum effort; the short-answer request used low.

Update, 25 October 2026: what changed

29 September: the thread-pinning run. 8 October: the default window went from 262,144 to 131,072. 11 October: the model moved to mainline llama.cpp build b11552. The October list of local models tested has the runs.

How this was measured

ModelZ.ai mixture-of-experts model (only some parts, called experts, run per token). Header: architecture glm5next, 46 blocks, 288 experts with 8 selected, native context 1,048,576 tokens (file metadata, not measured).
FileUnsloth UD-Q3_K_XL (a compressed version), four GGUF shards, 147,535,921,955 bytes or 137.404 GiB. Header names Unsloth as quantizer, MIT license, file type 12.
MachineIntel Core Ultra 9 285K, 188 GiB RAM, one NVIDIA GeForce RTX 5090 with 32,607 MiB of memory.
RuntimeSeptember: a GLM-specific llama.cpp fork pinned at d94f44e79aa219d8057e8de21f95360a187ebf41. Since 11 October 2026: mainline build b11552.
Placement16 September: --n-gpu-layers 999 -cmoe, no expert-block count or batch flags (llama.cpp defaults). 21 and 26 September, and the installed launch script: --n-cpu-moe 42 (experts of 42 blocks in system memory), one request at a time.
RequestsShort answer: temperature 0, low effort, 400-token cap. Code reads: temperature 0, seed 1, 1,024-token cap. Letters: temperature 0.7, seed 7, 1,200-token cap. Temperature sets randomness; the seed makes it repeatable.
Launch script, 26 SeptemberTemperature 1.0, top-p 0.95 (how much of the likely-word list is sampled), and high as the reasoning-effort fallback.
