Kimi K3 on one desktop: about 0.2 tokens a second

On one desktop with a 32 GB RTX 5090 and 188 GiB of RAM, the current compressed build of Kimi K3, with 1-bit experts and every part kept, wrote about 0.2 tokens a second (tokens are pieces of text), far too slow for chat.

In short
  • Use it for one careful question answered overnight, not for chat. Send one complete prompt, allow 2,000 to 4,096 output tokens, keep the context at 8,192. What to do
  • On this desktop the disk, not the graphics card, set the speed (monitored on the earlier build). Plan for roughly 600 GB of free disk and as much RAM as you can get. What limits the speed
  • Use the settings tested here. Keep the 1-bit parts off the graphics card, skip the program's RAM copy of the experts, and place layers by name. The full command

By Grant Williams · Published 8 August 2026

01

What to do

Check your machine. You need roughly 600 GB of free disk for the weights, and as much RAM as you can get. This desktop had 188 GiB; with less, more of every token streams from disk, which should be slower and was not measured. A recent graphics card helps but does not decide it: some other K3 runs use none.

You can use a llama.cpp release instead of the support branch: build b10443 is the first release with Kimi K3 support. Every number on this page was measured on the branch; nothing was re-measured on a release (see Corrections and updates).

Download, then count the files. Get the UD-IQ1_S folder from Unsloth's Kimi-K3-GGUF repository. Count the files against the repository listing and check the checksums: one 14-file download here reported success with a file silently missing after a brief sign-in error.

Send one complete prompt and come back later. Reusing a cached conversation can corrupt this model's linear-attention state (a published caution, not tested here), so every request here was a fresh, single prompt. Using K3 at this speed is closer to posting a letter than to typing in a box.

Allow 2,000 to 4,096 output tokens. Every recorded answer began with a reasoning block, and the reasoning is paid from the same output budget (the cap on one reply's length). A small budget is spent on thinking and the visible answer comes back empty. At these speeds 4,096 tokens is about four to six hours.

Keep the context at 8,192 tokens. The context is how much text the server holds at once. The prompt is read no faster than the answer is written, so a large context costs hours before the first token. Nothing larger was tested here.

Wait for the health endpoint, not the process. The server reports itself started within about two seconds and can answer about fourteen minutes later.

Settings that cost hours if you miss them

  • Keep 1-bit tensors (the arrays of weights) off the card. The 1-bit CUDA kernels are reported broken on this card generation: silent wrong numbers, no error. The placement below sends only 8-bit and full-precision tensors to the card.
  • Always use --no-repack. Without it, the loader tries to build a RAM copy of the 495 GiB expert pool and dies.
  • Move layers by tensor name, not by layer count. If the first block lands on the CPU, the load aborts on a fused linear-attention operation; trailing blocks move freely (43 of them here). Auto-fit can lower the layer count into the same abort, so pin -ngl 99 --fit off and place layers with the override pattern.
  • Do not raise the prompt batch size (how many prompt tokens are read at a time). A batch of 8192 asked for 9,715 MiB of extra graphics memory and failed with out-of-memory twelve minutes into the load, on the previous build. Today's placement has only about 2.7 GiB free, so the same failure is expected; it has not been re-run.
  • Ignore the loader's advice to use --no-mmap. With the model three times the size of RAM, that would mean asking for 594 GB of memory. Streaming from disk is the entire method.
  • Read the file headers before you load. Every tensor's size and type is in the GGUF headers (GGUF is the file format llama.cpp reads), readable in seconds. The placement below came from header arithmetic, not failed loads.
  • One warning is noise. Every load prints special_eos_id is not in special_eog_ids; every recorded answer still ended cleanly with finish_reason: stop.

The full command

llama-server -ngl 99 --fit off -fa on --jinja --no-repack --no-warmup \
  -ot "exps=CPU,shexp=CPU,blk\.(5[0-9]|[6-8][0-9]|9[0-2])\.=CPU" \
  --ctx-size 8192 --parallel 1 --cache-reuse 0 --temp 1.0 --top-p 0.95
02

What we found

The model

Kimi K3 is Moonshot AI's open-weight flagship, a mixture-of-experts model: it holds many specialist sub-networks ("experts") and uses a few for each token, so it is enormous in total but small per token. Most rows were read straight from the model files; rows citing the card are the maker's claims.

MakerMoonshot AI
Total parameters2.78 trillion. We summed the shapes of all 2,573 tensors in the files: 2,779,483,135,584. Moonshot's card says 2.8T; our arithmetic agrees.
Active per tokenAbout 104 billion: 16 routed experts chosen from 896 (about 1.8 percent of the pool), plus 2 shared experts and the always-used core. Roughly 4 percent of the total. Matches the card's 104B.
Layout93 blocks: 1 leading dense block, then 92 mixture-of-experts blocks, each holding all 896 experts. Read from the file metadata.
AttentionOnly 24 of the 93 blocks keep a full memory of past tokens (card: Gated MLA). The other 69 are linear-attention blocks (card: Kimi Delta Attention) that carry a compact running summary instead. The file metadata confirms it: the key-value head count is zero in 69 of 93 blocks.

Vocabulary163,840 tokens

The amber row is a maker's stated value we did not measure.

The build: only the experts are 1-bit

A compressed build stores weights in fewer bits: a smaller file, at some cost to accuracy that this page does not score. This one is Unsloth's UD-IQ1_S: 14 files, 594.00 GB (553.20 GiB; the same bytes counted by thousands and by 1,024s). Only the routed experts are 1-bit: 276 IQ1_S tensors (495.26 GiB) against 1,116 eight-bit and 1,181 full-precision tensors for everything else. It is calibrated: an importance matrix guided which precision goes where. Unsloth's own quality analysis was not reproduced. This desktop ran two builds, kept apart:

Fitting it on a 32 GB card

The experts never go to the graphics card: 495 GiB of 1-bit experts plus 12 GiB of shared experts stay on the CPU side and stream from disk. The card holds the always-used core (attention, embeddings, norms, output head). The previous build's 4-bit core fit. The current build's 8-bit core is 45.91 GiB, larger than the entire card.

The core averages 0.469 GiB per block, so the card can hold the first 50 blocks plus the embeddings and output head, 26.24 GiB. Blocks 50 through 92 join the experts on the CPU side, in one override pattern:

-ot "exps=CPU,shexp=CPU,blk\.(5[0-9]|[6-8][0-9]|9[0-2])\.=CPU"

The first load with it was healthy: about 29.9 GiB of graphics memory in use as the load session recorded it (29,884 MiB; no monitoring capture survives), about 2.7 GiB of headroom. The card holds 453 eight-bit and 639 full-precision tensors and nothing else: no 1-bit tensor is ever on the GPU.

What limits the speed: the disk

On the previous build, two fully monitored runs showed the card nearly asleep while writing: GPU use held a median of 1 to 3 percent, never passed 7 percent, and never warmed past 52 degrees. The SSD did the work: a median of 463 to 490 MiB/s of reads, hour after hour, peaks near 2 GB/s, while the CPU spent a median 12 percent of its time waiting on the disk. RAM never ran short: about 167 GiB of page cache (RAM the system uses to hold recently read file data) held part of the model and the rest streamed from disk every token. With 188 GiB of RAM against 553 GiB of weights, it is a storage benchmark wearing a language model's clothes.

The current build was not monitored this way; its speed falls in the same band, consistent with the same bottleneck, and no more than that. The desktop stayed fully usable throughout, since the model uses disk bandwidth and page cache, not cores or the GPU.

From the server's per-token logs for both builds, the four recorded test prompts and one monitored 1,315-token coding answer. End to end, as a user would see it. Under ten recorded answers across both builds: a field measurement of one setup, not a benchmark.

Slow prompt reading hurts most: ordinary local models read hundreds of tokens per second, so here a long prompt costs minutes per hundred tokens before any output. On the previous build, one 1,315-token answer took 124.5 minutes end to end. Longer answers drift slower: that two-hour answer averaged 0.19, where short answers touch 0.28. The calibrated build cost nothing measurable in speed; what it buys in quality was not measured.

What it got right

On the previous build it followed a byte-exact instruction, reasoned a classic riddle to the correct answer with a correct explanation, and wrote a small function with tests that pass when executed. It suits one bounded question you can sleep on; not iteration, agents or a code-review loop. Running a model this size at home is gated less by owning a datacenter than by disk, RAM and patience.

03

Limits

  • The current build is lightly tested: three answers, the longest 120 tokens, plus its healthy load. The batch-size failure, a 4,096-token context run, the executed-code test and the two-hour answer come from the previous build and are assumed, not re-run.
  • No benchmarks and no quality verdict. The test prompts show coherent, task-correct text in those cases. They do not check Unsloth's quality claims, compare the two builds on quality, or rank K3.
  • Untested: tool calling (never attempted), multi-turn conversation (avoided; no evidence it breaks or works), and context above 8,192.
  • One setup: llama.cpp at branch commit 7b990cf5, one desktop, one request at a time. No other runtime, no concurrency, no power-draw measurement.
  • The storage limit is about this class of machine. With enough RAM for the whole expert pool, reports elsewhere show several times this speed (see other K3 runs).
