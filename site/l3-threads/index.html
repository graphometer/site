Measured study · one desktop, one model file, Intel Core Ultra 9 285K

Mistral Large 3 675B slow in llama.cpp: the thread default

On one desktop with a 24-core Intel Core Ultra 9 285K, llama.cpp's default chose 4 compute threads, and Mistral Large 3 675B wrote 3.56 and 3.57 tokens a second in two of three warm requests (the third dipped to 1.70), against 5.82 to 7.09 with 24 threads set by hand.

In short
  • Check how many threads llama.cpp really uses. llama-server --help shows only (default: -1), not the number it picks. How to check
  • Set the thread count yourself, then measure (--threads and --threads-batch). Here 24 roughly doubled warm writing speed; 24 is this machine's number, not advice. What to do
  • Keep the server running between chats if the model nearly fills your RAM. Turning warmup off alone did not change warm speed. On this machine, with warmup on, the first answer after a cold start still took 897 seconds.

01

What to do

For a very large mixture-of-experts model (only some parts, called experts, run for each token) with most of its weights in system RAM rather than on the graphics card:

  1. See the thread count llama.cpp actually uses. llama-server --help prints (default: -1), not the number the default will pick on your machine (checked on this build), and on this build's default logging the chosen count did not appear in the server log either. If your build logs it, search for n_threads. Without the log: watch each thread's CPU use while the model writes (top -H -p <pid>, or htop with threads shown); the threads that go busy while tokens stream are the compute threads. Or read the process's thread count (Threads: in /proc/<pid>/status, or ps -o nlwp <pid>) and compare it with a run that has --threads set (here 53 with 24 set, 33 with the default). The raw count alone proves nothing, because it includes the server's other threads.
  2. Know what the default picks. On hybrid Intel CPUs (fast performance cores, or P-cores, plus small efficiency cores, or E-cores) under x86-64 Linux, expect about your P-core count if the chip has hyperthreading (two logical CPUs sharing one core) and about half of it if not: 4 on the 285K. On other x86-64 CPUs, AMD included, this build uses the physical core count, with nothing halved. This is read from this build's source, not measured on other machines (why); read cpu_count_math_cpus in common/common.cpp on your build.
  3. Set the thread count yourself, then measure. Here --threads 24 --threads-batch 24 roughly doubled warm writing speed against the default. --threads covers writing; --threads-batch covers prompt reading and batches. Only writing was measured, with both set to the same value. Your best count depends on your memory bandwidth and your model; earlier reports show setups where fewer threads win. If the compute threads are not all busy while the model writes, threads are probably not your bottleneck. If they are, test: same prompt, same server, two thread settings, three warm requests each, compare writing speed in tokens a second.
  4. Keep the server running if the model nearly fills your RAM. Warmup cannot keep in memory a set of experts your RAM cannot hold. Loading once and leaving the server idle costs only memory you were already spending.
02

What we found

Three setups, one change at a time

Three versions of the standard serving setup ran one at a time on the same night, each with four test requests: the first answer after loading, then three warm ones. Writing speed (how fast the model produces its answer) is the measure.

SetupChange from standardLoad until readyFirst answerWarm writing speed (requests 2/3/4, t/s)Graphics memory (raw MiB)
Anone (warmup on, threads 24)6 m 50.9 s3.46 t/s (897.0 s wall)6.83 / 7.07 / 6.9624,420
B+ --no-warmup only2 m 06.1 s2.07 t/s (969.8 s wall)5.82 / 6.96 / 7.0924,420
C+ --no-warmup, threads left to the default1 m 59.7 s3.14 t/s (130.5 s wall)1.70 / 3.56 / 3.5724,375

t/s is tokens a second. Wall is the whole request. Two of the twelve requests are brief dips, published as they are: B's request 2 read 5.82 with a sag partway through, and C's request 2 read 1.70. In both, the requests either side agree with each other and with the clocks (200 tokens in ~28.5 s is 7.0 t/s; in ~56.3 s is 3.56 t/s).

Warmup did not set the speed. Turning warmup off alone left warm writing at 5.82–7.09 tokens a second, against 6.83–7.07 with it on. The thread default is the supported explanation in this setup. Leaving the thread count to llama.cpp reproduced the earlier slow reading to within 0.05 tokens a second: 3.56–3.57, against 3.58–3.61 on 2026-08-05.

The outcomes were written down before the first setup loaded: if B fell to about 3.6 (3.2–4.2) while A read about 6 (5.5–6.7), warmup was the cause; if B stayed about 6 and C fell to about 3.6, threads were. The result was the second. Two warm readings (7.07, 7.09) landed slightly above 6.7; that does not change the verdict, which turned on whether B fell into 3.2–4.2, and it did not.

The thread count, confirmed: setup C's server process ran 33 threads where A and B ran 53. The difference is 20, which is 24 minus 4: the 24 compute threads replaced by the default's 4, with the server's other threads unchanged.

The current measured warm range on the standard setup is 5.8–7.1 tokens a second across A and B; the 2026-08-05 test recorded 5.98–6.28. The two are compatible; with three warm requests per setup and no intervals, the difference is not a finding.

Why the default picks 4

llama.cpp turns --threads -1 (the default) into a number through common_cpu_get_num_math(). On x86-64 Linux with a hybrid CPU, that visits every logical CPU in turn and asks what kind of core it is. Two rules, quoted from the build we ran (common/common.cpp, cpu_count_math_cpus): E-cores are skipped, with the comment “efficiency cores harm lockstep threading”, and the counter moves two logical CPUs at a time, with the comment “hyperthreading isn't useful for linear algebra”.

On this CPU the two rules add up: the 16 E-cores are left out, and the skip halves the 8 P-cores even though the 285K has no hyperthreading, so every logical CPU is a physical core. The result is 4 compute threads on a 24-core machine. On a non-hybrid x86-64 CPU this path never runs: common_cpu_get_num_math() falls back to the physical core count, leaving out the second logical CPU on each core.

The rule has a sound origin. It arrived in April 2024 with the llamafile speed work (PR #6414, “ggml : add llamafile sgemm”, merged 2024-04-16), and answers a real finding from 2023: on hybrid Intel CPUs running dense models fully on the CPU, threads on E-cores slowed the whole group, and using P-cores only was measured up to 3x faster. This page's workload, a 675B mixture-of-experts held mostly in system RAM, wants more threads on this machine than the rule gives. Whether 8, 16 or 24 is best here was not measured; 24 roughly doubles the default's 4.

What warmup did

Warmup is a real llama.cpp step: at load time it touches the weights so the first answer does not have to read them from disk. Here it moved that cost at most:

  • Warmup on (A, nothing yet in the page cache, the RAM that holds recently read files): load took 6 m 50.9 s, and the first answer still took 897 s, the server waiting on the disk, reading expert pages at roughly 67 MB/s, and total reads passed 237 GB against a 190.80 GB file: the same data read more than once. The file plus the process's own memory plus the desktop exceeds the machine's RAM, consistent with the end of warmup pushing its start back out of memory.
  • Warmup off (B, some of the file already in memory): load took 2 m 06.1 s, and the disk cost reappeared in the first answer (969.8 s).
  • Third load of the night (C): the first answer took 130.5 s, with prompt reading at 8.35 t/s, consistent with the often-used experts having settled in memory.

The readings are consistent with warmup shifting some disk reading from the first answer into load time. Cache history was not controlled across the setups, so this does not isolate that effect. Warmup did not set warm writing speed. Each fresh start risks a first answer of several minutes while roughly 154 GiB of experts settle, warmup or not.

The earlier explanation

From 2026-08-05, this machine's notes said warmup was what lifted writing from about 3.6 tokens a second to about 6. Both speeds were real: 3.58–3.61 from the 2026-08-04/05 tuning runs, and 5.98–6.28 from a test of the standard serving script the same night. But the two runs differed in three settings, not one:

warmup--no-warmupdefault on
threadsnot set: build default--threads 24 --threads-batch 24
server slots (requests served at once)4 (llama-server's default)--parallel 1
03

Limits

  • Few readings. Four requests per setup, three warm, no confidence intervals. The test can show a factor of two; it would not show ten percent.
  • Two thread counts only, 4 and 24. No 8-thread P-cores-only setup was run, so whether E-cores help or hurt here is unknown. There was also no setup with warmup on and default threads: the thread finding rests on B clearing warmup and C reproducing the slow number.
  • Server slots were not varied. All three setups ran --parallel 1; the earlier tuning runs used 4 slots. The thread change alone reproduced the slow number at one slot, which shows it is enough, not that slots added nothing to the earlier gap. That part is unmeasured.
  • First answers are not a fair comparison. A ran on a cold page cache, C on the night's third load; the 897 s / 970 s / 130 s first answers measure what was already in memory as much as the setup. The disk-reading account comes from process state, disk counters and clocks, with no memory-bandwidth or per-core capture, and no account of why 24 threads lands where it does.
  • One model file (the UD-IQ1_S compressed version), one placement, one prompt, one CPU, one build. Nothing here carries over to a different placement; 2023 reports on dense CPU-only models show the thread answer with the opposite shape. What the default picks on other CPUs is read from this build's source, not measured, and a default like this one can change in later builds.

Corrections and updates

Correction, 11 August 2026: warmup was the wrong explanation

From 2026-08-05 to 2026-08-11, four of this site's own notes (a model summary card, a settings file, a model list and a machine status file) said warmup “is what unlocks ~6 t/s”. The numbers were real and were reproduced; the cause rested on two runs that differed in three settings. The thread default is the supported explanation for this tested setup. The old entries are marked as replaced rather than rewritten.

Correction, August 2026: graphics memory units

Every graphics-memory figure in those records written as “GiB” was a raw nvidia-smi MiB reading divided by 1000: the recorded “24.6 GiB” default profile is 24,627 MiB, which is 24.05 GiB; “27.6” is 27,624 MiB, which is 26.98 GiB; “15.1” is 15,082 MiB, which is 14.73 GiB. The same slip had been found in three other models' records on this machine. The corrected figure, measured on the one-slot standard setup: 24,420 MiB, which is 23.85 GiB used, and 8,187 MiB, which is 8.00 GiB free. The machine's rule of keeping at least 6 GiB of graphics memory free holds with more margin than the old figures said, so the slip erred on the safe side here; it does not always have to.

Data and sources

The data package holds the files the runs produced. data/README.md maps every file, its origin and the package's redactions; data/NUMBERS.md maps every figure on this page to its file.

  • The run log (data/ab_run/RUN_LOG.md): setups, request plan and expected outcomes, written before the first setup loaded, with results added as each ran.
  • The three setups: the llama-server command each ran (data/ab_run/arm_exec_blocks.txt), the diffs showing each copy differs from the standard script only in its stated flags (arm_scripts.diff), and SHA-256 hashes showing the standard script was not changed (arm_scripts.sha256). The full launcher scripts are not in the package; the README says why.
  • All twelve test-request JSONs, the script that sent them, and per-setup summaries (data/ab_run/arm_*_probe*.json, run_probes.sh, arm_*_probes_summary.txt), with llama.cpp's own timing fields.
  • Server logs and nvidia-smi captures per setup (data/ab_run/arm_*_server.log, arm_*_nvidia_smi.txt): load times, slot counts and raw MiB readings.
  • The 2026-08-05 tuning runs (data/ladder/l3_ladder_results.tsv, whose graphics-memory column is raw MiB, and the ladder_R*.log logs), plus the standard-script test log (l3_canonical_smoke.log).
  • The claims check that set up this test (data/REPORT_l3_claims_dossier.md) and the findings memo (data/FINDINGS_l3_warmup_ab.md).

Earlier public reports

The E-core effect has been public since early 2023. llama.cpp discussion #572 (2023-03-28, i7-12700H) found P-cores only ran 2.4x–3x faster than all cores on 7B and 65B dense models, the earliest report we located; issue #842 (2023-04-08, 13900K) saw only ~50% CPU use at high thread counts, E-cores busy while P-cores idled. The default rule itself came from llamafile: “LLaMA Now Goes Faster on CPUs” (2024-03-31) and PR #6414 (merged 2024-04-16). ramalama issue #934 (2025-03-10) is a user asking why CPU inference uses “only 4 cores”. The widely shared January 2026 MoE offload guide on Hugging Face passes an explicit -t in its example commands but does not discuss the default.

This page adds a controlled measurement of the default against a set thread count on a 675-billion-parameter mixture-of-experts held mostly in system RAM, a workload not covered by the sources we reviewed. The 2023 reports found all cores slower than P-cores only on dense CPU-only models; this page found 4 threads about half the speed of 24. Both can be true.

If a number on this page disagrees with a file in the package, the file is right and the page is wrong; tell us and we will fix the page.
