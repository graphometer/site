Running Letta Code locally: what it reached for, what stopped it

Never signed in and left at its factory settings, Letta Code 0.34.10 looked up Letta's API and the npm registry and then made 17 connection attempts during one agent turn on one laptop; with six settings passed to it at start, the same trace showed none of them.

In short
  • Set the engine's switches before it starts. Six environment switches (named settings passed to a program when it starts), tested together, removed the factory run's name lookups and its 17 connection attempts to port 443. The window (the desktop app that runs the engine) sets two more we added later. The switches
  • For no network at all, run the window in a sandbox that has none. The sealed setup runs inside bubblewrap (a Linux tool that runs a program in a walled-off box) with its own empty network, and reaches the local model through a door: a small program outside the sandbox that owns the only model socket the sandbox can see. A replay of the window's route check inside the sandbox found no network route out. The sandbox command
  • Know what stays open. A saved OpenAI or OpenRouter key lets the sealed setup reach that provider. The connected setup, which uses the laptop's network, blocks Letta's hosts by name only, which is not a firewall. Agents in one setup can read each other's files through shell commands you approve; this was found by reading the code and is still open. Our modified window app is not published. 01

The answer, in four parts

This page is for anyone who wants to run Letta Code, a framework for AI agents that keep a long-term memory, on their own computer without it calling out. You get the exact switches, the sandbox command, the traces we used to check what the engine and its window tried to reach, what broke in the open-source window app on the way, and what the setup costs in features. It was built and checked on one laptop between 12 and 17 October 2026.

  • What it reached for. At factory settings the engine looked up api.letta.com and registry.npmjs.org during one turn and made 17 connection attempts to port 443, with no account and no sign-in. The open-source window app's page links a Google Fonts stylesheet. The browser engine inside the window downloaded a spell-check dictionary from Google with spell-check turned off.
  • What stopped it. Six environment switches (named settings passed to a program when it starts) on the engine, tested together, plus two we added later. On the window: no web fonts, a strict content security policy, and switches for Chromium, the browser engine inside it. For the sealed setup: a bwrap sandbox (bubblewrap, a Linux tool that runs a program in a walled-off box) with its own empty network, and a Unix socket (a local connection between two programs on one computer) to the local model, served by a small program outside the sandbox.
  • How we know. Traces of three network-related system calls made by the engine and the window, name lookups run inside the connected sandbox, and a replay of the window's route check inside the sealed sandbox, which found no way out.
  • What is still open. Agents in one setup can read each other's files through shell commands you approve; this was found by reading the code, not shown with a live read. A saved provider key gives the sealed setup a deliberate path to that provider. An earlier hole, where any program in the sandbox could use that key, was fixed. The connected setup blocks Letta's hosts by name only, which is not a firewall.
02

What we ran, exactly

LaptopASUS ROG Flow Z13 GZ302EA, AMD Ryzen AI Max+ 395, Radeon 8060S, 128 GB unified memory, the same machine as on our study of this laptop on its own. Ubuntu with GNOME; the window draws through a Wayland display socket.
EngineLetta Code 0.34.10 (the npm package @letta-ai/letta-code), pinned, started by the window with --backend local. No Letta account and no Letta Cloud. On 14 October we applied our own patch to it (section 06): letta.js sha256 84a54eac… before, ae36456a… after.
Window appA fork of the open-source letta-oss-ui at upstream commit c01d155 (9 October 2026, Apache-2.0 licence, version 0.2.0). It runs on Electron 44.7.0, which turns a web page into a desktop app and also runs the engine. A separate copy of Node 24.21.0, the JavaScript runtime, runs only the model relay. The build installed on 17 October was bec10c2. The fork is kept locally and is not published.
Two setupsEach setup is its own folder with its own launcher, which we call a home. Sealed: a sandbox with no network. Connected: the laptop's network, with Letta's hosts blocked by name. One window per home; both can be open at once. The launcher sets the mode, and the window shows it in a permanent SEALED or CONNECTED band that nothing inside the window can change.
Local modelsllama.cpp on the same laptop. In the installed homes the window reaches it through a door program (section 05). In the 12 and 13 October traces the engine reached it through the laptop's own cable-link address instead (address redacted in the data). Test turns used Ornith-1.5-35B and Qwen3.6-35B-A3B.
How we tracedstrace -f, a Linux tool that logs a program's requests to the operating system (system calls), filtered to the connect, sendto and sendmmsg calls, without root. The first window test also saved Electron's own network log.

The upstream revision we used pinned engine 0.34.6 and @letta-ai/letta-agent-sdk 0.8.32. The window can run a different engine through the LETTA_CLI_PATH variable; our launchers point it at the pinned 0.34.10.

04

The engine's switches

The window starts the engine with a short allow-list of variables from its own environment (PATH, HOME, LANG, LC_*, USER, LOGNAME, SHELL, XDG_RUNTIME_DIR, TMPDIR, LETTA_LOCAL_BACKEND_DIR, LETTA_CLI_PATH, the local model addresses and the engine's local-service waiting times). Then it forces these, whatever it inherited:

LETTA_CODE_TELEM=0
DO_NOT_TRACK=1
DISABLE_AUTOUPDATER=1
LETTA_CODE_OFFLINE=1
LETTA_DISABLE_LSP_DOWNLOAD=1
LETTA_DISABLE_MODS=1
LETTA_DISABLE_CRON_SCHEDULER=1
LETTA_BASE_URL=http://127.0.0.1:9

The first six are named for usage reporting, do-not-track, automatic updates, an offline flag, language-server downloads and mods. Despite its name, a code review of version 0.34.13 found that LETTA_CODE_OFFLINE covers only one download. We tested the six only as a group, on 12 October, with the same trace as the factory run. With them set, the create and the turn made no name lookups and no connection attempts to port 443, and nothing went to a Letta host or to npm. The engine connected only to the model server we named, the two default local addresses and the local name-service socket. The switched run also set the engine's backend folder; the factory run did not.

The scheduler switch stops the engine's own timer for scheduled turns. Those turns would start no process the window can see, so the window could neither show nor stop them. The dead address points requests that use the engine's Letta API address at a port on this computer where nothing listens. It does not cover telemetry: in the code, telemetry and feedback go to api.letta.com whatever this says, and are stopped only by LETTA_CODE_TELEM and DO_NOT_TRACK. A full local turn ran with the dead address on the bundled 0.34.6 engine. For 0.34.10 we read the code; we did not run it.

Two more rules sit beside the switches. The window adds seven engine tools to the home's deny list before every start: Wake, Monitor, WatchPR, Workflow, SendAgentMessage, Task and Agent. And a sealed window refuses to start the engine with a model address that is not 127.0.0.1, localhost or ::1, and says why.

05

The sealed home: a sandbox with no network

Each window runs inside bubblewrap (bwrap). This is an excerpt of the command, with our folder names replaced. The full set of binds and settings is in the data package.

bwrap --unshare-user --unshare-ipc --unshare-uts --unshare-cgroup --unshare-pid \
  --unshare-net \
  --die-with-parent --new-session --clearenv --cap-drop ALL \
  --ro-bind /usr /usr  (plus /bin, /sbin, /lib, /lib64 as links into /usr) \
  --ro-bind <own passwd, group and hosts> /etc/... \
  --ro-bind /etc/nsswitch.conf, /etc/ld.so.cache, /etc/fonts, /etc/localtime \
  --proc /proc  --size 1073741824 --tmpfs /tmp \
  --tmpfs /dev  --dev-bind /dev/null, /dev/zero, /dev/urandom, /dev/dri \
  --size 536870912 --tmpfs /dev/shm \
  --bind <this home only> /home/<user> \
  --bind <this window's settings> /winconf \
  --ro-bind <window app> /app  --ro-bind <engine> /engine \
  --ro-bind <model door folder> /door \
  --ro-bind <Wayland socket> /run/user/1000/wayland-0 \
  --setenv LETTA_WINDOW_MODE sealed  (and a short fixed list of others)

The two sizes are 1 GiB for /tmp and 512 MiB for shared memory. The connected home uses the same command without --unshare-net, and adds read-only /etc/resolv.conf and the CA certificate folders.

Three details that mattered

  • Write your own two-line /etc/hosts. 127.0.0.1 localhost and ::1 localhost. Without it the engine asked a name server for localhost. With it, in the connected test, the trace showed no name questions at all.
  • Reach the model through a door, not the network. A program outside the sandbox owns the only model socket the sandbox can see. It passes on the model list, health, properties and chat completions, one request per connection. It refuses non-text media and a few request fields (id_slot, lora, chat_template and two more). Inside, a small Node relay joins a loopback port to that socket, so the engine sees an ordinary LLAMA_CPP_BASE_URL.
  • Electron needs --no-sandbox inside bwrap, and the engine's own file sandbox could not start there either, because AppArmor (the Linux system that limits what programs may do) refuses the nested sandbox the permissions it needs. So the outer sandbox is the only wall. Section 09 shows what that cost.

The deliberate doors

"Sealed" here means the sandbox has no network of its own. It still shares the display socket and the graphics device with the laptop. Its other ways out are named sockets, mounted read-only and served by programs outside. Besides the local model door there are four, each present only when installed: a model lent by our desktop over a direct cable (that path reaches the desktop), an API door, a speech helper and a robot helper. The API door holds your provider keys outside the sandbox. With no key saved it sends nothing to a provider. Once you save an OpenAI or OpenRouter key, it can reach that provider, including to list models while you use a local one.

06

The connected home, the window and the engine patch

The connected launcher writes 32 names into the sandbox's own /etc/hosts as 0.0.0.0 and ::, which point a blocked name back at the laptop itself, where nothing in this setup answers on those ports. They are Letta's hosts (letta.com, api.letta.com, app.letta.com, chat.letta.com, docs.letta.com, letta.ai and a few common variants), the Datadog site names found in the engine, three more service names the engine can call, and Sentry and PostHog names as a precaution. The launcher refuses to open the window if letta.com or api.letta.com is missing. The full list is in the data package.

This blocks names, not addresses, and only the names listed. A hosts file cannot block a whole family of names with one pattern. A program that knows a numeric address, or asks a name server itself, is not stopped. The connected sandbox shares the laptop's network, so a program an agent runs there can reach whatever the laptop's own network allows. The dead LETTA_BASE_URL covers only requests that use the engine's Letta API address.

The window app

The fork drops the web fonts for the system font stack and sets this content security policy (a list of what the page may load) on its page:

default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline';
font-src 'self'; script-src 'self';

It starts Chromium with switches including disable-background-networking, disable-component-update, disable-domain-reliability, disable-client-side-phishing-detection, disable-sync, disable-breakpad, disable-crash-reporter, no-pings, disable-quic, a disable-features list, force-webrtc-ip-handling-policy=disable_non_proxied_udp, host-resolver-rules="MAP localhost 127.0.0.1, MAP * ~NOTFOUND" and a proxy address on this computer where nothing listens. The spell checker is switched off, given no languages, and pointed at a dictionary address that goes nowhere: spellcheck: false on the page alone did not stop the download. Links in agent replies are never opened; clicking one copies the address. The engine's local socket needs a token made fresh at each start. The window is shown on its first paint, when it is ready, or after 3 seconds, whichever comes first.

The engine patch

We patched one file of the engine, letta.js, so that an agent with no model chosen stops instead of using the first listed model, and compaction (shrinking a long chat so it fits the model) never switches to another model. The patch also replaces saved provider keys with a marker in tool output and in the chat before a model sees them, and makes memory-folder git push, remote and config changes ask first. The key wipe has limits written down with the patch: a key read in very short pieces or re-encoded gets through, and chat history already on disk is not rewritten. The patch script accepts only the exact 0.34.10 file, by its hash.

An offline test ran both engines against a stand-in model, inside bwrap with no network, on our desktop rather than the laptop. Each check is one scenario: a fake key read in a set way, or a set git command. The patched engine passed 26 of 26. The unpatched engine passed 4 of 25, and those 4 were the git commands meant to stay automatic. With no model chosen, the unpatched engine tried to reach another model; the patched one stopped and sent nothing.

The red-warning fault: the window checks for a route out with a UDP connect, which sends nothing. Node calls the same function on failure as on success, so "network is unreachable" was counted as "route found". A replay inside the sealed sandbox showed the system call returning ENETUNREACH (network is unreachable) for both IPv4 and IPv6, which is also our check that the sealed sandbox had no route out.

08

What broke in the base app, and what was done

  • The window sometimes never appeared. On 12 October the tester reported launches where the page never painted, in both modes. The app creates its window hidden and shows it on first paint. The tester could not see the laptop's screen, ruled out a locked screen, and did not find the cause; the remote test launch may have played a part. No per-launch log was kept. The fork shows the window after 3 seconds whether or not a paint arrives. On 13 October, with the screen locked, 24 of 24 sampled launches of the fork returned a screenshot through the developer port. Whether the window was on screen was not seen.
  • The model picker was greyed out after connecting a provider and often after a normal start, until the page was reloaded. The fork lists models again by itself and has a "Look for models again" button.
  • "Default model" meant gpt-5.5, a cloud model, in a home with no cloud provider. The fork never creates an agent without a model the owner chose, and the engine patch stops a turn with no model.
  • Chats made elsewhere were hidden or untitled. The window did not list an agent's default conversation, where the old desktop app kept its chat, and chats made in the terminal showed as untitled "New chat" rows. The fork shows the default conversation.
  • Deleting an agent left its memory folder on disk without saying so. The fork moves it to a dated trash folder and says where.
  • No lockfile (a file that fixes exact package versions) in the upstream repository, so every install resolved the newest versions in range. The fork commits one, and builds on the laptop offline from it.
  • The engine's own file sandbox cannot run inside the launcher's sandbox. In the first window test an approved command wrote outside its work folder. We chose the launcher's walls as the boundary. An audit later showed the cost (below).

10

What it costs

  • No Letta account features. Provider features where you save a key still contact that provider. Subscription sign-ins live in the connected home only. Web search is not offered in the sealed home.
  • Seven engine tools are refused: scheduled turns, background monitors, pull-request watching, scripted workflows, messages between agents and helper agents. Background commands are off.
  • A pinned, patched engine. A code review of 0.34.13 found that it did not fix the defects we had worked around and added features an agent can start that the window does not watch, so we stayed on 0.34.10. The patch only applies to one exact file, so every engine update means patching and checking again.
  • One wall, not two. Chromium's own sandbox and the engine's file sandbox are both off inside bwrap. The outer sandbox separates the homes from the rest of the laptop, not one agent from another in the same home.
  • Your own fork to maintain. The upstream revision we used pinned engine 0.34.6, and our fork is not published.
11

Limits

  • Long-term use. This is the build and its checks over six days, not agents living in these homes over weeks.
  • Every path. The traces cover start, model lists, agent creation and a few turns per test, and only three kinds of system call. They do not cover every tool, memory workers or days of use.
  • Packets. The checks are system-call traces and name lookups, not a packet capture; UDP could not be captured without root. We do not know whether the 17 factory-setting attempts completed or what they carried.
  • Each switch alone. The six engine switches were tested only as a group.
  • The screen. On 12 October the tester could not see the screen; on 13 October it was locked. Whether the window was on screen was not seen.
  • The dead Letta address on 0.34.10, by a run. It was run on 0.34.6 and read in 0.34.10's code.
  • A firewall. Nothing here blocks addresses at the network level, and nothing has been certified against a hostile program.
