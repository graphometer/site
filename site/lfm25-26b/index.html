LFM2.5-2.6B: which file to download, how much context it can use, and how much room it needs to answer

On one 32 GB graphics card running llama.cpp, Liquid AI's small LFM2.5-2.6B model found 15 of 15 facts hidden in a long document in a 16K-token window (tokens are pieces of text), given enough room to answer, but 0 of 15 at its 128,000-token maximum. Short answers came back in all three repeat runs only when the room for the answer reached 1,024 tokens.

In short
  • Give short prose answers at least 1,024 tokens of output budget (room to answer), and check finish_reason. Smaller budgets can return an empty reply with no error. What to do
  • For finding details in long input, stay near 16K. At 32K it found 12 of 15 with extra output room; at 65K, 1 of 15. Treat 128,000 as the server's hard maximum, not a working size.
  • Download the mid-size 4-bit file (Q4_K_M). Of three official files tested, it matched the top score on a 90-run tool-use test (84 of 90) at ordinary size and speed.

By Grant Williams · Published 7 August 2026

01

What to do

Set the output budget to at least 1,024 tokens for prose. The output budget caps how many tokens (pieces of text) one reply may use, and the model's hidden reasoning comes out of it. Client defaults of 256 or 512 are exactly where replies go blank or depend on luck. This is for short answers; for about 500 words no tested budget up to 4,096 was reliable. The budget map

Always check finish_reason. An HTTP 200 can carry an empty string. An answer that finishes as length was cut off, even when it looks complete.

Keep long-input work near 16K. The context window is how much text the server holds at once. For retrieving details from long input, 16K is the conservative choice; 32K is plausible if you accept some misses and allow output headroom; 65K and beyond are not supported by these results. The retrieval tables

Pick Q4_K_M. It is the best-supported file from these runs. The file comparison

Send the repetition penalty as repeat_penalty. This llama.cpp build silently ignores repetition_penalty, the name many OpenAI-style clients use. Its defaults also differ from the card's recommended settings; apply the card's on purpose if their trade-offs fit your use. What each setting did

02

What we found

The context window: 128,000 at most, reliable far below that

The model card states a context window of 131,072 tokens; the configuration file in the same repository states 128,000. llama.cpp sides with the configuration file. Asked for 128,000 it starts cleanly; asked for 131,072, it warns that the model was trained for 128,000 and caps every serving slot:

llama_context: n_ctx_seq (131072) > n_ctx_train (128000) -- possible training context overflow
load_model: the slot context (131072) exceeds the training context of the model (128000) - capping
load_model: initializing, n_slots = 4, n_ctx_slot = 128000, kv_unified = 'true'

To see how much of the window the model can use, we hid short coded facts in filler documents filling about 95 percent of each window. Each window size got three sets; each set placed one true codeword near 5, 25, 50, 75 and 95 percent depth, plus two explicitly false, superseded codewords as decoys. That makes fifteen tries per size. This first table allowed 512 output tokens; each cell is exact retrievals out of three.

At 16K both misses were budget overruns: 15 of 15. At 32K one more cell recovered; the rest were real misses, two cells repeatedly choosing the marked wrong decoy. At 65K a 3,000-token allowance added no exact answer, and at 128K 4,096 added none: the model chose decoys, called present facts absent, gave unrelated filler terms, or spent everything on hidden reasoning. A test asking for two hidden facts at once passed only at 16K. Every tested depth is affected at 65K and 128K; the sharp change sits somewhere between 32K and 65K, not located by these runs.

Fluent output is not reliable reading. Asked to summarize the whole 128,000-token document, the model wrote a grammatical, on-topic summary in 878 output tokens, with no breakdown into repeated tokens, but it repeated topics, called randomly ordered archive entries systematically organized, and gave a nonsensical numeric range.

Memory is not the obstacle: the full 128,000-token window fit in under 6 GiB of observed GPU memory (whole-board readings, desktop included: 3,967 MiB at 16K, 4,087 MiB at 32K, 4,590 MiB at 65K, 5,781 MiB at 128K, and 5,868 MiB when 131,072 was requested and capped). Overflow fails loudly: a prompt about five percent over the window got an immediate HTTP 400 naming both counts, with no silent truncation:

request (17239 tokens) exceeds the available context size (16384 tokens), try increasing it

The output budget: why a working model can return an empty reply

The card says the model reasons before answering, and the chat template opens each assistant turn with a <think> tag. In the recorded runs the reasoning arrived in its own field, unseen, but it is paid from the output budget. In short-answer runs the visible answer averaged 181 and 203 characters across the two sampling setups (server defaults and card settings), while the hidden reasoning averaged 2,411 and 2,612, more than ten times the answer. When the budget runs out mid-reasoning, the reply is HTTP 200, no error, finish_reason length, and empty content. Three seeds per cell:

For short prose, 512 answered on some seeds and not others; 256 or less reliably came back blank. Tool calls are cheap: the model reasons far less before calling a tool. For about 500 words, the first complete answers appeared at 2,048, and even at 4,096 at least one seed in each setup came back blank or cut off; the threshold lies above 4,096. The last row is the agent case: the tool works, then the sentence to the user comes back empty. Several other answers carried real text and a finish_reason of length: cut off mid-answer.

Which file to download

Liquid publishes official GGUF files (the format llama.cpp reads) at several compression levels: smaller files trade a little fidelity for less memory. Three were tested on the same build: the smallest sensible one, the ordinary middle choice and the largest compressed one offered.

The 90-run test is described below. Writing speeds are tokens a second, end-to-end medians (completion tokens divided by wall time, nine fixed requests per file, request overhead included): a run diagnostic, not a benchmark. Reading one 479-token prompt ran roughly 23,950 to 26,520 tokens per second across the three files. Memory is whole-board, desktop included; the Q4_K_M range is from earlier runs, not a same-minute reload.

Q4_K_M matched the top score at ordinary size and speed. Every other number on this page was measured on it unless stated.

Q4_0 ties the score and saves only 80.6 MB, but the equal score hides weaker discipline. In the scenario with two lookalike tools, it repeated the same search to the test program's six-round cap in 6 of 6 records; Q4_K_M did so in 4 of 6 and twice stopped after one call and answered. The scenario passes either way, because its checker asks only whether the right tool was called.

Q8_0 scored worse, and the reason matters more than the number. All six added failures sit in the scenario where the request insists the model call some tool of its own choosing (tool_choice: "required"), not the named-tool scenario behind the six misses all three files share. Each time Q8_0 made no call and hit its length cap (every record that reports token usage shows the whole 4,096-token allowance used), repeating greeting text and leaking control tags into visible output. This llama.cpp build is known not to enforce that request shape robustly; Q8_0 shifted the model's token choices just enough to expose it, and the two Q4 files happened to walk past it. That is an interaction between this file and this backend, not evidence that Q8 generally damages the model.

The blank-reply boundary (same short question and seeds) did not move across files. It is coarse, not a promise about 512: the budget map above shows 1,024 is the reliable floor.

Sampling: what the server does versus what the card asks

Sampling settings shape how the model picks each token. llama.cpp gives its own defaults to any client that sends none, as most do, and they are not the card's:

temperature0.20.1
top_k8050
repetition penalty1.0 (off)1.1
top_p0.95not mentioned
min_p0.05not mentioned

The server's own settings listing carries only the name repeat_penalty. With that field, the card's settings against the server defaults, on the same seeds:

  • Hidden reasoning for short prose fell about 7.7 percent (a mean of 2,411 characters against 2,612 at stable budgets): real but modest.
  • Search looping eased. In a test conversation built to invite repeated searching, the penalty at 1.1 gave a final answer in 3 of 5 trials against 1 of 5 with it off, with fewer near-duplicate searches (28 of 45 against 33 of 49). Both still looped heavily: a mitigation, not a cure.
  • One threshold got worse. Prose right after a tool result went blank at 128 under the card's settings, raising that reliable threshold from 128 to 256.

Tool calls and the chat template

The chat template keeps earlier tool calls. The chat template formats the conversation history for the model's next turn; in a multi-step tool task the model needs to see the tools it already called. This template includes them, checked in the pinned template text and on the running server. Three older Liquid models first shipped without that (see Corrections and updates).

Three checks on Q4_K_M:

  • An automated check of the serving setup found it healthy: no intervention needed, two advisory warnings, neither attributed to the model.
  • 84 of 90 runs passed a fixed set of 15 scripted tool-use scenarios (single calls, four-step chains, parallel calls, error recovery and more), each run three times in both streaming modes over the same interface a chat app would use. All six misses come from one scenario testing a known llama.cpp defect: it silently ignores a request to force one specific named tool, as measured with other models in the same family on the same build. No miss was attributed to the model. The reasoning always arrived in its own field, never in the answer text.
  • A stricter three-task check passed when talking to the server directly, including a four-step tool chain completed in exact order with a correct, grounded final answer, with the shipped template and without any added fix-up code.

The call-some-tool scenario that tripped Q8_0 was also run on a larger sibling, LFM2.5-8B-A1B, on the same build and settings. The 8B made no tool call in any of six cases, spending its full 4,096-token allowance each time; the 2.6B passed six of six, calling a tool immediately with 58 completion tokens. The same backend weakness is present in both; whether it bites depends on the model's habits. It is not a quality ranking.

03

Limits

  • Other runtimes and files are untested: no Ollama, vLLM, LM Studio, several-requests-at-once or full-precision (safetensors) result, and the official BF16, F16, Q5_K_M and Q6_K files were not run. A runtime that ignores or overrides the 128,000 training limit recorded in the GGUF was not tested.
  • 84 of 90 is not a quality score. The 90-run test scores protocol and task structure; a run can pass with a poor answer.
  • The retrieval test is narrow. It checks whether facts can be found and told apart from planted fakes, not every kind of long-document reasoning, and passing it does not prove good synthesis. Because of the decoys, do not compare it with common needle-in-a-haystack scores, which plant no competing statements.
  • The maker's figures were not reproduced. None of Liquid's benchmark or speed figures from the card appear here.

Corrections and updates

Correction: the penalty field (runs of 2026-08-04)

The first budget-and-sampling sweep, 54 calls, sent the penalty as repetition_penalty, which llama.cpp ignores, so it never applied. That sweep had suggested the card's settings cut hidden reasoning by about a third. The 144-cell re-run with repeat_penalty measured about 7.7 percent and replaces that number; every sampling number on this page comes from the corrected re-run.

Update, 2026-08-05: older Liquid templates fixed at the source

In pinned versions of three older Liquid models, the shipped chat template left earlier tool calls out of the history, and multi-step tasks broke down on exactly those setups in recorded runs. We built a compatibility kit around it and on 2026-08-03 submitted public template changes for all three (1.2B-Instruct, 24B, 1.2B-Thinking). On 2026-08-05 the maintainers merged their own fix in all three repositories, which supersedes ours; our recorded failure cases, re-rendered against the updated templates, pass. Copies downloaded before the fix still carry the old template. The Droplet page is a snapshot from before that merge.
