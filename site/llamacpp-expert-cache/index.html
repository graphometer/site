Two llama.cpp settings for MoE models bigger than your GPU

We tested 19 large mixture-of-experts (MoE) models on one RTX 5090. Loading the weights into RAM once (--load-mode dio) read long prompts 2.0 to 3.1 times faster on the 12 large models that had been memory-mapped, and cost free RAM. Setups that added the expert cache wrote short replies 1.4 to 2.9 times faster on 11 of 16 large models, though most of them changed other settings too.

This page is for anyone who runs a large mixture-of-experts model with llama.cpp on one consumer graphics card, with most of the model's weights left in system RAM. (Weights are the numbers the model has learned. A mixture-of-experts model keeps most of them in many small parts called experts.) It gives the exact flags, which llama.cpp build had them, what each model gained, and what each setting cost. The first setting, --load-mode dio, reads the RAM-held weights once at start. Its cost is free RAM: on the biggest models as little as 5.1 GiB was left. The second, the expert cache (--moe-cache-mib), keeps copies of the most-used experts on the card. It helped writing, not reading, and the card stayed nearly full. Five models took the first setting only.

01

What the two settings are

The layout. A mixture-of-experts (MoE) model splits most of its weights into many small “experts” and uses only a few of them for each token. When the model file is bigger than the graphics card, a common llama.cpp layout keeps the experts in system RAM (--cpu-moe for all of them, or --n-cpu-moe N for the experts of N layers) and puts everything else on the card. Every model on this page kept some or all of its experts in RAM, either with those flags or with llama.cpp's automatic placement (--fit on, which decides the split from the card memory free at start).

Reading and writing. Reading is how fast the server takes in a prompt, in tokens per second (t/s). A token is a small chunk of text, often a word or part of one. Writing is how fast the server produces the reply, one token at a time. GiB and MiB are memory units close to a gigabyte and a megabyte. A long prompt is mostly reading; a long answer is mostly writing.

Setting one: --load-mode dio. By default llama.cpp memory-maps the model file: the operating system pulls pieces of it from the drive when they are first touched and keeps them in its page cache (spare RAM it can take back at any time). On a fresh start that means a slow first answer while pieces arrive. With dio (direct I/O) the server reads the RAM-held weights once at start, into pinned memory: RAM locked in place so the card can copy from it quickly and the system cannot reclaim it. The start logs confirm the switch: on GLM-5.3-Flash, 123.7 GiB of the file sat in the page cache before, and with dio 117.5 GiB sat in pinned memory instead. A cold load is a start with none of the file already in the page cache; every before command on this page was started that way.

Setting two: the expert cache, --moe-cache-mib N. It sets aside N MiB of card memory for copies of the experts that get used most. When a token needs an expert that is in the cache (a hit), the card computes it. When the expert is not there (a miss), it is uploaded. The cache's documentation (docs/moe-cache.md in the pull request 31286 source we built) says it is used for small batches, such as writing, where the model handles one token at a time, and that long prompts still upload the experts they use. On these models we paired it with --cpu-moe, usually with --fit off, which turns off the automatic placement. All experts then sit in RAM, and the cache decides which of them also live on the card. So on 13 of the 15 cached setups, the after command also moved experts that the before command had kept on the card into RAM. The value is in MiB: 18000 is 18,000 MiB, a little under 18 GiB.

Which build has them. A build is one numbered version of llama.cpp. Both flags are in the server's documented options (tools/server/README.md) of release b12015, and of an earlier build we had installed (it reports commit 23b0202); that is where we read them. Every cached model here ran on release b12015 or on a build we had installed that already had the cache (commits 23b0202, 10b8b75 and 184f653). Three models were on older builds without the cache (gpt-oss-120b, Ling-3.0-flash and Qwen3.5-397B-A17B) and moved to b12015 to get it; the three smaller models moved to b12015 as well. A related flag, --moe-cache-cpu-share, is not in release b12015. We ran it from a build of llama.cpp's development branch with pull request 31286 applied; a pull request is a proposed code change. Section 08 has what it did here.

llama-server -m MODEL.gguf --n-gpu-layers 99 --cpu-moe --fit off \
  --load-mode dio --moe-cache-mib 18000 \
  --ctx-size 262144 --batch-size 4096 --ubatch-size 2048 \
  --threads 8 --threads-batch 8

The cached Qwen3-Coder-Next command as it ran, shortened to the flags that matter here (sampling and chat-template flags left out). Its before command kept the experts of 28 layers in RAM (--n-cpu-moe 28) and the rest on the card. The full command lines for every run are in the data package.

What we ran, exactly

Every figure on this page was measured on this machine on the date given; ratios and percentages are worked out from two measured figures, and the data package says which two. A “setup” is one complete command line, with the model, build and window it ran on. The window is the context window: how much prompt and conversation the model can hold at once. A micro-batch is the number of prompt tokens the model processes at one time.

MachineOne desktop, as described on Two boxes: NVIDIA GeForce RTX 5090 (a 32 GB card), 188 GiB of system RAM, Intel Core Ultra 9 285K. Each server ran with --threads 8 --threads-batch 8, pinned to cores 0 to 7, one request at a time, one model at a time, with the server and the test program on the same computer.
BeforeEach model's usual command as our start scripts ran it on 1 November. We started it by hand, after dropping the model's file from the page cache, so a memory-mapped start read from the drive.
AfterThe changed command, started through a test copy of the model's start script, which runs its own checks before the server is ready, then the same speed screen. So the after load times include those checks (section 07).
The speed screenThe same requests for every model: two prose answers to a short prompt (22 to 162 tokens once each model's chat template was added) with replies capped at 420 tokens; a code rewrite of a 9,000-character Python file, capped at 700 tokens; a read of about 20,000 tokens of llama.cpp source with one made-up code word planted in the middle, to check the model read it; and a next turn on top of that read, capped at 300 tokens. Temperature 0.15 for prose and code and 0.2 for the read, with seed 42 in every request. Speeds are the server's own timings, and count any reasoning tokens a model wrote.
Writing speedTwo figures. “Short” is the second prose answer. The first answer is kept apart because a cold memory-mapped start slows it. “At 20K” is the next turn after the 20,000-token read.
DatesFrom the afternoon of 1 November 2026 into the early hours of 2 November (16 models); the morning of 2 November (Qwen3.6-35B-A3B and Qwen3-30B-A3B); the afternoon of 2 November (Ornith-1.5-35B).

Reading. On the 14 memory-mapped models, the 20,000-token read ran 1.60 to 3.13 times faster with dio. On the 12 large ones (all but Qwen3.6-35B-A3B and Ornith-1.5-35B) it ran 1.96 to 3.13 times faster.

Cold load. On all sixteen, the start took 29 to 63 percent of the time it took before: Beam 1.0 went from 289 seconds to 135, GLM-5.3-Flash from 213 to 103, Qwen3.6-35B-A3B from 48 to 14.

Writing. The second answer moved by between minus 3.4 percent (Ornith-1.5-35B) and plus 2.1 percent (Qwen3-235B-A22B). Within those few percent, dio does not change writing speed.

The slow first answer. On five mapped models the first answer after a cold start was much slower than the second, because pieces of the file were still arriving from the drive: Beam 1.0's first 420 tokens ran at 1.95 t/s, with 57.9 GB read from the drive across its screen. In these hand-started dio runs, four of those five wrote their first answer at about their second answer's speed. DeepSeek V4 Flash's first answer still ran at 9.87 t/s against 13.31 for its second; the logs do not show why. (One later start of Beam 1.0 stalled; see section 07.)

05

The five models that took only the first setting

Beam 1.0, Muse Spark Open, Inkling-Small, Qwen3-235B-A22B and Qwen3.5-122B-A10B took dio and no cache. For four of them the records show what was tried.

  • Qwen3.5-122B-A10B. A 12,000 MiB cache, on release b12015 with all experts in RAM, wrote faster on prose (41.49 t/s against 32.45 for the second answer). It wrote slower on code (40.54 against 42.79) and read about the same (498.2 against 518.2). It would also have meant moving the model to a newer build. A 17,000 MiB cache ran out of card memory at load.
  • Qwen3-235B-A22B. A 12,000 MiB cache with an 8-bit conversation cache ran out of card memory at load. The model already used 31,801 MiB of the card in its before command.
  • Muse Spark Open. A 7,000 MiB cache was tried only at half the window (65,536 tokens), and that run also moved to release b12015 and put every expert in RAM. There it wrote 11.47 t/s on the second answer and 8.43 t/s after the 20,000-token read. The hand-started dio run at the full 131,072 wrote 6.37 and 6.29 (the start-script run in the main table: 6.38 and 6.35). The model stayed at the full window without a cache.
  • Inkling-Small. It runs on a separate build made for that model, and that build's documented options have no expert cache.
  • Beam 1.0. No cached setup was run, and the records do not say why. With dio alone it left 5.1 GiB of RAM free at its lowest and used up to 31,273 MiB of the card.

The limit is card memory. Eleven cache setups we tried ran out of it at load or warm-up (section 07). On five models the start scripts use a cache 1,000 MiB smaller than a size that ran in testing, which had used 31,174 to 31,735 MiB of the card (Qwen3-Coder-Next, gpt-oss-120b, GLM-5.3-Flash, DeepSeek V4.1 Flash and MiMo-V2.6-Flash). The records do not say how close to the card's limit each of those came.

Too small can be slower than none, and it depends on the build. DeepSeek V4 Flash, at the same micro-batch of 8192:

The hit rate is the server's own count, printed in its log when it stops, for batches of 8 tokens or fewer (writing). For larger batches the same logs give 0.11 and 1.65 percent. On b12015 a 7,000 MiB cache with a micro-batch of 4096 had a small-batch hit rate of 46.07 percent and wrote 20.13. We have no dio-only run of this model on b12015.

The cache competes with the conversation for the card. The conversation cache is the memory that holds what the model has already read in this conversation, and it grows with the window. At its full 262,144 window, Qwen3-30B-A3B usually keeps that cache in 16-bit numbers. With it we tested 2,000 MiB of experts (release b12015, all experts in RAM), and the model wrote 23.68 t/s, slower than the 29.67 it wrote before. With an 8-bit conversation cache, which uses smaller numbers, 10,000 to 13,000 MiB of experts fitted and it wrote 130.8 to 160.76 t/s (hand-started, second answer). The setup that went into its start script uses the 8-bit cache with 11,500 MiB; section 09 has the quality check for that change.

At depth, the gain shrinks. Depth is how much text is already in the conversation. On the three smaller models we have replies after reads of 48,000, 97,000 and about 226,000 to 228,000 tokens, before and after. These runs were started by hand with the cached command. On Qwen3.6-35B-A3B that command lacks one flag of the start-script command (--no-reasoning-preserve, which changes how much of the model's earlier reasoning is kept in later turns); on Ornith-1.5-35B it has that flag and the start-script command does not.

Lowest free: the lowest available RAM seen during the after setup's screen and its listed checks. No other large program ran beside any model in these tests.

Card memory. The cached after setups used 29,629 to 31,289 MiB of the card in the runs we sampled, on a card sold as 32 GB. Most before commands were already close to that (25,900 to 31,800 MiB), because they kept as many experts on the card as would fit. Of the 15 cached setups, card use rose on nine and fell on six. It rose most on Ling-3.0-flash, from 9,764 to 29,629 MiB, and next on DeepSeek V4 Flash, from 25,921 to 31,289. We did not test running anything else on the card beside a model.

Warm restarts. With a memory map, a restart soon after a stop can find the file still in the page cache. Ornith-1.5-35B's before command restarted in 4 seconds that way, twice. Eight hand starts of its cached variants took 20 or 21 seconds each, because dio reads the file again each time. Every hand start of GLM-5.3-Flash with dio took 84 to 103 seconds. We have no warm memory-mapped restart of the large models to compare with that.

09

Quality checks: what ran and what did not

A changed command can change a model's output. These checks ran on the after setups. Two of them, on two models, score answers right or wrong by machine; none is a broad or human-judged comparison of answer quality.

  • Code words at depth. Three made-up code words were planted in a long read and asked back. The 14 large models that took the deep run on 1 November returned 3 of 3 at about 2,000 and 48,000 tokens and at their deepest read, 97,000 or 200,000 tokens depending on the model. All 16 large after setups returned 3 of 3 at 48,000 through their start scripts. The three smaller models returned 3 of 3 at every depth in section 06. On GLM-5.3-Flash, DeepSeek V4.1 Flash and MiMo-V2.6-Flash the deep run used a cache 1,000 MiB larger than the final one; the final size took the 48,000-token check.
  • Quick checks and tools. Five short questions and five tool round trips (the model calls a tool and uses the result), on the 14 deep runs that included them: 5 of 5 tool round trips on all, and 5 of 5 questions on all but Inkling-Small, which scored 4 of 5. Its miss answered a question about a function that does not exist with “does not contain”, which is right; our automatic check did not accept those words.
  • Boundary reads. 24 prompts, 19 of them sized just under, at and over the batch boundaries and 5 of random size, each asking for a few tokens, through the start script: on each of the 15 cached after setups, all 24 returned a reply with no server error. This checks that the server answers, not what it answers.
  • A known crash prompt. Ling-3.0-flash once crashed a server on one exact prompt (see the batch-size study). On the cached setup it took that prompt, rebuilt from its seed, and 40 more like it: the planted code word came back, and 40 of 40 got a reply. (The rebuilt prompt counted 2,999 tokens on the hand-started run and 3,007 through the start script.)
  • A tool turn and a four-turn conversation ran on every after setup; the replies are in the data package. Some turns ran out of their token cap while the model was still reasoning, so those replies are incomplete: in the 20 start-script runs of the main table, the first turn on Ling-3.0-flash and MiMo-V2.6-Flash, and the second turn on Ornith-1.5-122B and Qwen3.6-35B-A3B. On Ling-3.0-flash's hand-started run the first and second turns both did.

dio alone gave the same output, token for token, on all six models where we compared it. Of the 15 cached comparisons, 2 matched at every position (Nemotron 3.5 Bolt and Qwen3.5-397B-A17B), though their probabilities still moved slightly; the other 13 had differences. One possible cause: the cache runs the most-used experts on the card, and card and CPU round numbers differently, so near ties between two tokens can flip and the text runs on from a different word. Rows marked b12015 also changed build, and 13 of the 15 cached rows also changed where the experts sat, so placement is another possible cause. We did not test which. Two repeat runs give a sense of the noise: Ornith-1.5-35B's before command, run twice, gave 192 of 192. Muse Spark Open's before command, started twice, gave only 72 of 192. That command uses --fit on, which can place the model differently from one start to the next, so compare runs only when the placement is the same.

What this does not show

  • One machine. One RTX 5090 desktop with 188 GiB of RAM and eight threads. How fast experts cross from RAM to the card (the PCIe connection between them) decides much of the cache's value; we did not measure it. A different connection, less RAM or a different card will move every number.
  • These files. One quantization of each model (the file's compression level, shown as the name after the model in the table), at the windows in the table. Another file changes the size of the experts and what fits.
  • Single runs. Most speeds are one run of each setup. Beam 1.0's stall shows that one start can differ from the next.
  • One request at a time. Nothing here measures two users or batched requests.
  • Mixed changes. The after setups are not the settings alone. Thirteen cached rows also moved experts from the card into RAM, seven rows (six models) also changed build, four changed the micro-batch, and one changed the conversation cache.
  • A quiet desktop. No large program ran beside the models. On the setups that left 5.1 to 21.1 GiB free, we did not test what happens when one does.
  • No broad quality test. Section 09 lists what ran.
