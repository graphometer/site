Local models as reviewers

As agents the best score was 74.0; one script pipeline (one row per call, a different model checking, then a no-model fixer) scored 100.0 on this table.

This page is for anyone who wants a local model to review code or documents, and wants to know what setup actually worked. A local model is an open-weight model, one whose files you can download, running on your own computer. We tried them on real work: tidy a long document, review a code change, fix a bug. The finding: do not hand a local model the whole job as an agent, a model that works through a task on its own. Give it one small piece per call, meaning one request to the model, and let a different model check the result. In our test, one row per call alone scored 52.0; with a different model checking and a no-model fixer last, it scored 100.0. The other local pipeline scored 81.0, with one wrong archive, two open items lost, and one invented row when the file is scored again with the same scorer. On a different job, reviewing a code change as one plain request with no tools, some of these models were useful second reviewers: GLM-5.3-Flash and DeepSeek V4 Flash on their ordinary settings, and MiMo once its thinking was capped.

Independent measurements; no affiliation with any model maker or tool named on this page.
01

The job, and how it was scored

The job was real. A long status document had a table of 45 rows, one per project. Each row had to be sorted as still live, finished with an open item, or done. Kept rows had to be shortened to 300 characters or fewer without losing an open item or a link. Done rows had to move to an archive word for word. On our own reading only one row was done.

A script scored every attempt out of 100, then took points off:

  • 15 for each row wrongly archived (it still had open work);
  • 5 for each missing row; 3 for each invented or mangled row;
  • 2 for each row over 300 characters; 1.5 for each lost link;
  • 1 for each row kept that should have gone; 0.5 for each open item that could not be traced.

So 100.0 means no penalty, and a score can fall below zero. To test the scorer, we planted a bad draft. Thirteen defects were planted: 5 dropped open items, 3 invented facts, 3 lost links, and 2 wrong archives. The score 61.0 is 2 wrong archives, 2 invented rows, and 2 lost links. The 5 dropped open items did not change the score. One planted invented fact and one planted lost link did not either. One row can honestly be read two ways; several good drafts lost 15 points there.

An agent is a model running inside a harness: a program that lets it read files, run tools and write files in a loop. OpenCode and Claude Code are two harnesses. A step is one model reply inside that loop. A call is one request sent to a model, and a tool call is a request from the model to the harness to do something, such as write a file. A token is a short piece of a word; limits on a reply are counted in tokens. Thinking is the hidden reasoning some models write before their answer; on most local servers it can be switched on or off per request.

03

The same job, one row per call

On 10 October we stopped asking for the whole job at once. A plain script sent one row per call with the brief's rules, checked that the reply was valid JSON (a structured text format) of the right shape, and retried up to three times, telling the model exactly what was wrong. A row that still failed fell back: the last parsed answer, forced into the limits, or the original status cell, flagged. Two more steps followed:

  • A different model looks again. For each row marked done, it is asked to quote any open item word for word. A verbatim quote turns the row back to open, and the model that wrote the row redoes it.
  • A no-model fixer finishes. It is ordinary code, with no model in it. It restores a file path that was cut short, trims at a word boundary, and appends the row's record link.

05

What each model needed

  • Qwen3.8-27B: thinking off, in an agent harness. OpenCode asks for at most 32,000 output tokens per step. With thinking on, the model spent a whole step thinking and made no edit, in three runs across two jobs: two coder runs, and the 590-second trim-job run in section 02. The switch is one request field, chat_template_kwargs: {"enable_thinking": false}, plus the sampling settings for its non-thinking mode (temperature 0.7, top_p 0.8, top_k 20). Sampling settings control how varied the model's choice of words is. With those it fixed both of two real defects, and the test suite passed 53 of 53 checks. A review of that diff found defects the tests did not catch. A second round fixed five findings; the suite then passed 70 of 70. The note of that test says 20 minutes (102 steps, 34 edits). The second round's note says 24 minutes. No separate run timer is recorded.
  • Qwen3.8-Flash-Next as a checker: thinking off. One checking call ran past 10 minutes with no answer. With the same switch it took 6 to 30 seconds.
  • MiMo-V2.6-Flash-RL: a thinking budget. With no cap it thought through all 24,000 tokens it was given and wrote nothing. A thinking budget is a cap on how many tokens the model may spend thinking. With the server capping thinking at 14,000 tokens (--reasoning-budget 14000), out of 24,000 asked for in total, it wrote the 7-of-7 review above.
  • Claude Code: a system shim. A shim is a small program placed between two others to translate between them. Claude Code sends a system message (standing instructions for the model) inside the message list. The local server's chat template, the fixed format in which it expects messages, refused it with HTTP 500, "System message must be at the beginning". A small proxy that moves that message to the top-level system field fixed it: Claude Code then wrote a one-file task in 2 turns, 39 seconds, on Qwen3.8-Flash-Next. It wrote one tiny file, not the document job.
  • Gemma 4 31B and 26B-A4B: thinking on, switched on in the request itself. The Gemmas did not think until the request sent the switch. With thinking on, Gemma 4 31B fixed three of three defects on its first answer. With thinking off, Gemma 4 31B solved two of three eventually, and one of three on the first answer. The third was not solved. With thinking off, Gemma 4 26B-A4B solved one of three.
  • GLM-5.3-Flash has no thinking-off. Its effort setting, which sets how much it thinks, takes only low, high or max.

Harness limits that changed the run

  • OpenCode's read tool cuts any line over 2,000 characters. Nine of the 45 rows were longer. A cloud agent spent 214 tool calls recovering the cut text and timed out. A copy with the long lines wrapped, at most 1,500 characters a line, fixed it.
  • OpenCode sends no sampling settings, so a local model runs on whatever its server was started with.
  • A per-step output limit can be smaller than the answer. The OpenCode config capped Laguna S 2.1 at 8,192 output tokens. Raising that setting to 32,768 still hit the harness maximum of 32,000, and the answer was still unfinished. The other writers' answers needed about 14,000 output tokens.

Finding defects is the hard half. Fixing one from a precise finding is easier. Three real findings from past code reviews were given to local models with the source file and no tools. A harness then put the model's answer into the code, ran the tests and, if they failed, showed the model the test output once.

07

What this does not show

Most figures here are one run of one model on one job. Repeats and retries are named where they happen, for example: the Flash-Next repeat, the two GPT-OSS runs, Laguna's two attempts, Grok's first effort-high run and its retry, and the two Vibe runs at 85.0 and 83.0 (section 02); the two voided fixer runs and the later re-run (section 03); and three Qwen3.8-27B thinking-on runs across two jobs (section 05). The scoring weights are ours. The checker and the fixer in the one-row-per-call setup were built after we saw which rows failed, so that setup was tuned on the table it scored. So 100.0 means "works on this table". It has not been tried on a second job. 100.0 means no mechanical penalty. It is not a prose grade. Seven shortened rows were read: usable, sometimes choppy. On the security change, local reviewers saw the diff only. On the tool diffs, the comparison was the same diff. Nothing here rules a model out; a model that did badly on one job has only not been shown to do well.

08

What to set, if you try this

  • Split a long job into one item per call, from a script. Validate each reply and retry with the exact complaint.
  • Have a different model check, and ask it to quote evidence, not to give a verdict.
  • End with a deterministic fixer, plain code with no model, for the mechanical slips.
  • Switch thinking off for small per-item calls. Cap it for long reviews. Send the switch in the request itself; do not trust the server default.
  • Check your harness: line limits on reads, per-step output caps, and whether it sends sampling settings at all.
  • Treat a local "all clear" as not yet an all clear. Treat a local alarm as a lead to check.
