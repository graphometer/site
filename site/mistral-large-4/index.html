Mistral Large 4 at home: 6.6 tokens/s on an RTX 5090 and a laptop

We split a 217 GiB file of Mistral Large 4 across one desktop and one laptop. It generated about 6.6 tokens a second in short tests, counting its reasoning. Our runs on the desktop alone stayed under 3.

In short
  • Reading the weights into memory once at start-up made the biggest difference. On the two-machine setup, in a before and after on 1 November (other settings also differed), the first request went from 2.85 to 6.78 tokens a second and its drive reads from 74.0 GB to 0.0. The before and after
  • The setup that worked splits the model. 01

What it is

If you have a 32 GB graphics card and a lot of RAM and wonder whether a model this size is usable at home, this card shows the desktop-and-laptop setup that worked, the main setups that failed, what it takes to keep it running, and a small blind quality check. All Large 4 figures use one file: Unsloth's UD-IQ1_S quantization, run on llama.cpp (a program that runs language models on ordinary computers). A quantization stores a model's weights in fewer bits so the file is smaller, which can cost quality. Unsloth is a third party that publishes such files. A short section near the end covers Mistral Small 4 on the same desktop.

Mistral Large 4 is, by Mistral AI's own model card, its largest model to date, and its weights are public. The card states about 1 trillion parameters in total and 49 billion active for each token (52 billion counting the embeddings and output layers), in a mixture-of-experts design: 128 routed experts, 4 active per token, plus 1 shared expert. A mixture-of-experts model runs only a few of its sub-networks, the experts, for each token. That is why a model this large can run on home hardware at all: most of it sits idle on any given token.

The licence is the Mistral Ecosystem Open-Weight License, which its text calls a modified version of the MIT licence. Its section 2 requires a licensee, or an affiliate, that operates a Model as a Service business (as the licence defines it) to enter a separate commercial licence with Mistral before any commercial use. Section 3 lists exceptions. The full licence text is in the data package.

We ran Unsloth's UD-IQ1_S GGUF (the file format llama.cpp reads). It is six files totalling 233,009,564,322 bytes, which is 217.0 GiB (a GiB is 230 bytes, that is, 2 to the power of 30, about 7% more than a GB). Spread over about 1 trillion parameters, that is about 1.9 bits per weight on average. The file is bigger than the desktop's 188 GiB of RAM, and that one fact shapes everything below.

Two terms we use throughout. A token is a chunk of text, often part of a word. Writing speed is how many tokens a second the model generates. This model reasons before it answers, and writing speed counts that reasoning as well as the visible answer. Reading speed is how fast it processes your prompt before it starts generating. Labels in brackets say where a figure comes from: (vendor) is the maker's statement, (measured) is our run, (arithmetic) is our calculation from those. The figures in this section are vendor statements, except the file size and bits per weight, which are arithmetic.

02

The setup that worked

The model is a stack of 72 layers. On the RTX 5090: every layer's attention (the part that looks back over the conversation), the shared expert, and the conversation memory (the KV cache). In the desktop's RAM: the routed experts of the first 42 layers. On the laptop: the routed experts of the last 30 layers, run by a llama.cpp worker on the laptop's CPU and connected to the desktop by a Thunderbolt cable. Only expert work crosses the cable; the conversation memory stays on the desktop's card.

The setting that made the biggest difference is --load-mode dio: read the desktop's share of the weights into memory once at start-up, instead of mapping the file and fetching pieces from the drive as they are needed. Section 05 shows the before and after.

A schematic, not a script to paste: the layer lists are shortened, and paths and addresses are replaced. The scripts as they ran are in the data package.

# on the laptop (CPU backend)
GOMP_CPU_AFFINITY=0-15 taskset -c 0-15 ggml-rpc-server -H <laptop address> -p <port> -d CPU -t 16

# on the desktop (CUDA)
GOMP_SPINCOUNT=10000000 taskset -c 0-15 llama-server --model Mistral-Large-4-1T-A52B-UD-IQ1_S-00001-of-00006.gguf \
  --host 127.0.0.1 --port <port> --timeout 3600 \
  --rpc <laptop>:<port> --device CUDA0,RPC0 --tensor-split 72,0 --n-gpu-layers 999 \
  --override-tensor "blk\.(0|1|...|41)\.ffn_(up|down|gate)_exps=CPU,output\.weight=CUDA0,blk\.(42|...|71)\.ffn_(up|down|gate)_exps=RPC0[<laptop>:<port>]" \
  --load-mode dio --lazy-mode on --no-warmup --fit off --parallel 1 \
  --threads 16 --threads-batch 16 --ctx-size 131072 --batch-size 2048 --ubatch-size 1024 \
  --temp 1.0 --top-p 0.95 --top-k 0 --min-p 0 --jinja \
  --chat-template-kwargs '{"reasoning_effort":"low"}'

GOMP_SPINCOUNT keeps the desktop's worker threads spinning between steps instead of sleeping. On the desktop's Core Ultra 9 285K, cores 0 to 15 are its 8 performance cores and 8 of its efficiency cores. --timeout 3600 matters: the longest read below took over 22 minutes.

In that setup, on 1 November, three short tests generated 6.58, 6.62 and 6.67 tokens a second (measured), counting reasoning. Each stopped at its 300-token cap. One of them first read a 6,411-token prompt at 72.1 tokens a second. The first request after start-up was as fast as the later ones. In a 131,072-token window (the most text the model can keep in view at once), two long reads also worked: see section 04.

05

The finding: reading the weights in once cut the drive traffic

llama.cpp normally memory-maps a model file: the operating system treats the file as if it were in memory and reads each piece from the drive the first time it is touched. When the program needs a piece that is not in RAM and has to wait for the drive, that is a major page fault. When the file does not fit in RAM, Linux keeps dropping pieces and reading them again, which is called paging. On 31 October we took the slow writing for a limit of the hardware. On 1 November, removing the drive reads more than doubled the first request's speed.

Splitting the model is what made that possible. With 30 layers' experts on the laptop, the desktop's share fits in its RAM: in the read-once run below, the server held 114.1 GiB at start-up. Here are two runs from 1 November, one mapped and one with the weights read in once at start-up. They are an observed before and after, not a change of one setting: the note under the table lists what else differed.

What else differed. The mapped run had 30 layers' experts on the laptop and 3 whole layers on the card, as its script records. The read-once run's script defaults to 26 and 2, and the values it actually ran with were not logged. Its card memory at start-up (29,915 MiB) is close to the mapped run's (29,686 MiB) and far from a 26-and-2 run's (26,116 MiB), and its desktop memory (114.1 GiB) equals a later recorded 30-and-3 run's, so we believe it used 30 and 3; that is an inference. The read-once run also turned on huge pages (larger memory blocks that are cheaper to track) for the laptop's worker and requested them on the desktop, where only 0.4 GiB took. The mapped run pre-read the desktop's expert layers into the drive cache before the first request (112.4 GiB in 18 s); the read-once run skipped that step. Load took 275 s mapped and 251 s read once. Drive GB is one drive's read counter, rounded to 0.1.

Read once, the first request ran as fast as the later ones (6.78 against 6.76 to 6.87). We did not test a working read-once setup on the desktop alone: the 217 GiB file is larger than its 188 GiB of RAM.

Later, in the final setup, a laptop worker with huge pages and spinning threads generated 3.2%, 2.4% and 0.1% faster on three requests than a plain worker, and read the 6,411-token prompt slower (70.4 against 72.1 tokens a second). Both settings changed together. We kept the plain worker.

We also tried a second llama.cpp setting, a cache of frequently used experts on the card. On 31 October it looked worse, but that run was paging. With the weights read once, on a newer build, a 5,500 MiB cache with a 64K window generated about 9% faster than the plain 128K setup on three prompts, with little card memory to spare. The study of the two settings covers them across many models.

06

Three experts instead of four

llama.cpp can tell the model to use three routed experts per token instead of the default four (--override-kv mistral-large4.expert_used_count=int:3). In the final setup, three probes (short test requests) then generated 8.09 to 8.16 tokens a second, against 6.58 to 6.67 with four. All three probes were still reasoning when they reached their caps (800, 300 and 800 tokens), so they show speed, not answers. The probe's 1,940-token prompt was read at 82.6 tokens a second; the four-expert run used a 6,411-token prompt, so those two reading speeds are not comparable.

In the blind comparison below, three experts scored 15 of 18 and the four-expert set 18. On the statistics question, the three-expert answer said one hospital treated more severe cases, while the table in that same answer showed the opposite. On the probability question it generated 15,405 tokens, reasoning included, against 7,640 for four experts. Over all six questions, three experts generated 28,051 tokens and four experts 22,115.

07

A small blind quality check

Is the 1.9-bit file any good? We asked four local setups the same six questions, each with a known answer: a logic puzzle, an exact probability, a buggy function to fix, a statistics trap (Simpson's paradox, where a trend inside each group reverses when the groups are combined), a question about a treaty that does not exist, and a decision about backups that needs arithmetic. One hosted judge model, OpenAI's GPT-6 Astra at high reasoning effort, scored each answer 0 to 3 against a written answer key. For each question it saw the four answers labelled A to D in shuffled order, with no model names.

  • The made-up treaty. Both Large 4 setups said they could not verify it. DeepSeek and Large 3 described its contents as fact.
  • How the four-expert set was put together. On the night of 31 October, on the earlier two-machine setup with a 6,000-token cap, Large 4 answered the code, statistics and false-premise questions, writing at 0.88 to 1.72 tokens a second. Its logic, probability and decision answers ran out of time (30 minutes each) and were asked again on 1 November on the final setup, with a 10,000-token cap. Same model file and sampling.
  • Reruns with more room. Before the answers were blinded, three answers that hit their cap while still working were run again with a larger cap: Large 3 on logic and probability (4,000 tokens, rerun at 12,000) and three experts on probability (10,000, rerun at 20,000). A cap counts reasoning and the visible answer together. The cut answers are in the data package.
  • The answer key had a slip. It said all eight logic clues are needed. The judge flagged that clues 5 and 6 are not, and a brute-force check agrees. No score was changed.

Six questions and one judge: 18 against 15 is a hint, not a ranking.

09

What it takes to run Large 4 this way

  • The laptop is part of the model. It must be awake, on the cable, with its worker running. With the worker loaded, the laptop's total RAM in use was 88 GiB, and the worker takes 16 CPU threads. If the worker dies, the desktop server goes down too: when we killed the worker in the middle of an answer on 2 November, the desktop server aborted (its log records a core dump), no server process was left at the 10-second check, and the client got a closed connection.
  • Almost all of the card. 31,168 MiB at start-up and 31,246 MiB at the highest sampled point during the long reads, on a 32 GB card.
  • Most of the desktop's RAM. The server peaked at 126.0 GiB, and the desktop's available memory fell as low as 35.5 GiB.
  • Pinned cores. It is tied to cores 0 to 15 on both machines. In one run a reply slowed to 2.59 tokens a second while the desktop's load rose (section 04).
  • Start-up time. About 4 minutes: 216 s in our test script (timed from 4 s after launch) and 252 s on one start through our start scripts.
  • Long reads are slow. Processing a 96,325-token prompt took 1,347 s (22.5 minutes), before any writing began. On the next turn about the same document, the new prompt took 4.2 and 5.0 seconds, because the server had kept what it had already read.
  • It reasons first. In every request we logged on 1 November, at low effort, it produced reasoning before its answer, so short answers take longer than their length suggests.
10

What we got wrong

Our notes from the first trial on 31 October drew four conclusions that later runs did not support. Each heading paraphrases one of them.

Writing tops out at 2 to 3 tokens a second on this hardware

Our 31 October notes put warm writing at 2.2 to 2.8 tokens a second and estimated it would stop at about 4 even without paging. With the model split across two machines and the weights read in once, it generated about 6.6. On the desktop alone, the best runs ranged from 1.18 to 2.87 after their first requests, wider than the band we wrote down.

The hot-expert cache makes it slower

On 31 October an 8,000 MiB cache generated at 1.11 to 1.43 tokens a second and we wrote it off. That run read 17.7 to 362.2 GB from the drive per request, so it mostly measured paging. With the weights read once, on a newer build on 1 November, a 5,500 MiB cache with a 64K window generated 7.20 to 7.42 against 6.72 to 6.76 for the plain 128K setup on the same three prompts. Small, but a gain, and we did not judge its answers (section 11).

More threads make it worse

24 desktop threads were slower than 8 (later requests 1.45 to 3.20 against 3.22 to 3.96), but that test ran while the model was still paging. The final setup uses 16. We never ran a matched thread comparison without paging, so we cannot say what the extra threads add now.

The newer llama.cpp build is slower for Mistral Small 4

In an early 1 November comparison, b12015 generated prose at 19.37 and 13.29 tokens a second and the older build at 18.22 and 19.05. When we repeated it (section 08), b12015 gave 33.51 and 33.64 and the older build 34.73 and 27.81: the two pairs overlapped. The early pair should not have been read as a comparison. We have no record of what slowed it.

11

Limits

  • One quantization. Everything is the UD-IQ1_S file. We did not compare it with a larger quantization or the full model, so we cannot say how much quality the small file loses.
  • A small quality sample. Six questions, one selected answer per setup, one judge model, and the four-expert answers came from two setups (section 07). DeepSeek had its thinking on, Large 3 has no thinking mode, and Large 4 used low effort. Not a benchmark and not a ranking.
  • No full window. The deepest read was 96,325 tokens in a 131,072-token window. The model card states a 1M-token window (vendor); we did not test it.
  • One request at a time. No concurrency (several requests at once), and no guess at it.
  • The cached setup was never judged. On four fixed prompts, the single most likely token at each step (greedy decoding) with the 5,500 MiB cache matched the plain setup at all 48 positions on three prompts and at 25 of 48 on the fourth. Once one token differs, the rest of that output can differ too. We did not judge the cached setup's answers.
  • One pair of machines and one cable. A different laptop, a slower link, or a desktop with more RAM would change the best split.
  • Single runs. Most rows are one run each, and we did not measure run-to-run variation.

Sources and data

The data package holds the records behind the measured numbers here: the per-request result files from both nights, the server logs that show the failed loads, the long-read files, the token comparison files (the chosen token and the five most likely next tokens with their log-probabilities at each step), the six questions, the answer key, all 24 local model answers plus the cut ones, the letter map and the judge's scores, the Mistral Small 4 result files, and the launch and probe scripts. The number map ties each figure on this page to its file and field, or says where it comes from when that is outside the package.

Machine paths, network addresses, host names, process ids and request ids are replaced or removed, and so are port numbers outside the logs. The judge's identity and effort come from its run log, which is not shipped. Its written reasons are left out because they are a hosted model's text; its 24 scores are included. The Mistral Large 4 model card and licence are in data/vendor/, as read on 30 October 2026 at repository revision f12dabdc.
