Muse Glimmer 30B: draft length 16, not 3, in llama.cpp

On one RTX 5090, raising Muse Glimmer 30B's draft length (how many tokens a small helper model guesses ahead) from llama.cpp's default of 3 to 16 took six structured prompts (code, JSON and a table) from a median 116.505 to 253.19 tokens a second, 2.17 times as fast, with each prompt run once per setting.

In short
  • Ask the helper model for its full block of guesses (--spec-draft-n-max 16), tested one request at a time. The two flags on Meta's model card, -md and -ngld 99, turn it on but leave llama.cpp's default of 3. llama.cpp trims 16 to 15, and 15 is what the fast run used. What to do
  • Check one line in your server log. If it prints n_max=3 just above block_size=16, you are on the slow setting. The check
  • Expect less on prose. Against the same model with no helper, the best prose result was 1.51 times as fast; structured output reached 3.32 times.

By Grant Williams · Published 16 August 2026

01

What to do

Turn on the helper model, then set its draft length. This model gets its speed from speculative decoding: a small draft model guesses the next few tokens (word pieces) and the main model checks them all in one step. Meta's draft model, DFlash, is a separate file trained to guess a block of 16 tokens in one pass. The speed runs below used this command, with the draft flags added or changed:

llama-server \
  --model Muse-Glimmer-30B-KQuant-17GB-Q4_K_M.gguf \
  --host 127.0.0.1 --port <scratch> --alias muse-glimmer-30b \
  --jinja --ctx-size 8192 --parallel 1 --n-gpu-layers 99 \
  --threads 24 --threads-batch 24 --flash-attn on --timeout 3600

Meta's model card turns the draft model on with two flags:

  -md dflash-Muse-Glimmer-30B-Q4_K_M.gguf -ngld 99

Then add --spec-draft-n-max 16. That one flag took the structured prompts from 116.505 to 253.19 tokens a second. --spec-draft-n-max 8 reached 208.29 and draws no warning.

Check the startup line

With only Meta's two flags, the server prints:

common_speculative_impl_draft_dflash: - n_max=3, n_min=0, p_min=0.00
common_speculative_impl_draft_dflash: - block_size=16, mask_token_id=201818, n_extract=5

n_max=3 is llama.cpp's general default, set for ordinary draft models. block_size=16 is what this drafter was trained for; the server prints it and does not use it. With the flag, the log reads:

common_speculative_impl_draft_dflash: - n_max=16, n_min=0, p_min=0.00
common_speculative_impl_draft_dflash: requested draft size (n_max=16, n_min=0) exceeds
  the trained block size 16 -- clamping to 15

Passing 15 lands in the same place without the warning. Defaults can change; this line tells you which case you are in.

Other settings

Tune by speed, not by acceptance rate. Acceptance rate (the share of guessed tokens the main model keeps) ranked the three structured settings in exactly the wrong order here. Measure end-to-end speed on your own work. Evidence

Make sure your llama.cpp supports the model. Meta's card says to run llama-cli --version and require 10353 or higher. That works on a release build only; a build from source prints a line like version: 0.1.0-dev (build 1, commit 3cb7ffb), with no number to test. Meta's second check works on any build:

grep -c LLM_ARCH_MUSE_GLIMMER src/llama-arch.cpp

Expect startup warnings. With the drafter, every load printed dflash requires ctx_other to be set and [spec] failed to measure draft model memory; Meta documents the second as harmless, and the model served normally. Every load also printed special_eot_id is not in special_eog_ids; no run showed a stopping problem, so that line is an open observation, not a known fault.

Strip code fences before parsing JSON. With a strict JSON schema the model wrapped a correct object in a markdown fence, so json.loads(message.content) is not safe here. Evidence

Thinking cannot be turned off; set how much with reasoning_strength (low, medium, high, the default). For a hard cap, llama.cpp's --reasoning-budget is the flag; we did not test it. Measure the token budget your own prompts need. Evidence

Prefer Meta's long-named files. Short-named twins, also re-hosted by Unsloth, carry an older chat template that adds its own default on top of your reasoning instruction. Its error string says "Onyx". Evidence

What we found

A longer draft more than doubled structured speed

Meta's model card publishes this table for our exact hardware: an average over a prompt set it does not publish, batch size 1, greedy decoding (always the most likely next token), through llama.cpp.

t/s is tokens a second of writing. Each cell is the median of six different prompts, one call each (n = 6), the same prompts in every run. "vs run A" divides by run A of the same kind of prompt, never by Meta's number. Runs are lettered in the order they ran, so D sits above C. No interval is computed.

Our no-draft speeds, 76.22 and 76.345, are 1.8 and 1.9 percent above Meta's 74.9. Our fastest structured median, 253.19, is 8.5 percent above Meta's 233.4, and 3.32 times our base against their 3.1 times theirs. The two speedups measure different things: theirs averages an unknown mix, ours is six structured prompts.

Why the default costs so much. Meta trained DFlash to produce a block of 16 tokens and prints Block size | 16 in the drafter's specification table. llama.cpp's --spec-draft-n-max defaults to 3, a sensible value for the ordinary draft models it was written for, and this build does not read the block size from the file. Meta's card documents -md and -ngld 99; the string --spec-draft-n-max appears in neither of Meta's readmes. A block drafter asked for three tokens at a time throws away most of what it computed. Each document is correct on its own; followed together, they leave structured output at 116.505 tokens a second instead of 253.19.

Run B is Meta's two flags, not Meta's full command, which is this, and which we did not run:

./build/bin/llama-server \
    -m       Muse-Glimmer-30B-GGUF/Muse-Glimmer-30B-KQuant-17GB-Q4_K_M.gguf \
    --mmproj Muse-Glimmer-30B-GGUF/mmproj-Muse-Glimmer-30B-Q4_K_M.gguf \
    -a muse-glimmer-30B \
    -ngl 99 -c 131072 -np 4 \
    --host 127.0.0.1 --port 8080 \
    --jinja \
    --temp 1.0 --top-p 0.95 --top-k 64

and adds -md Muse-Glimmer-30B-GGUF/dflash-Muse-Glimmer-30B-Q4_K_M.gguf -ngld 99 for speculation. Ours was text only, one slot instead of four, 8,192 tokens of context instead of 131,072, and greedy, because greedy at batch size 1 is how Meta's card says it measured speed. That command does not set --spec-draft-n-max either, so anything built from it starts at llama.cpp's default.

Prose gains less. The flag that gave 3.32 times on structured output gave 1.51 times on prose, so one averaged speedup, ours or anyone's, cannot tell you which you will get. The speculation-gate study (a 397B mixture-of-experts model) found an ungated draft made prose slower than no draft while making structured output faster, and the Qwen3.8-27B field card found the same direction on a dense 27B. Their sizes do not carry over here.

Acceptance is accepted draft tokens divided by generated draft tokens, from the server's own counters. Tokens per target step is completion tokens divided by (completion tokens minus accepted draft tokens), the same arithmetic the server prints per request as mean len. It is a rough measure of work saved, not a logged count of main-model passes.

On structured output, acceptance fell from 0.741 to 0.319 while the same six prompts got 2.17 times faster; tokens per target step rose with the speed, 3.22, 4.49, 5.75. A block drafter proposes a whole block either way: wasted guesses cost cheap drafter time, and the saving is in expensive main-model passes. Tuning for acceptance lands on Meta's documented setup: best acceptance on this page, second-worst speed. These counters are not comparable with the Qwen pages' acceptance figures, which came from a different mechanism (a multi-token-prediction head).

The full 131,072-token context fits with the drafter

One load and one reply per row, not a median. All loads were page-cache warm (the files were already in system memory).

With the drafter, the full native context (how much text the server holds at once) used 21,051 MiB and left 11,036 MiB free. The drafter added 2,400, 2,402 and 2,402 MiB, and writing read 117.77, 117.65 and 117.19 tokens a second as the reserved context grew sixteen-fold: no clear decline, though one reply per row cannot draw a curve. The prompts were short: context reserved, not filled.

Why it is cheap. Only 13 of the 52 layers keep an unbounded key-value cache (the memory of earlier tokens); the other 39 keep a 2,048-token window. Two key-value heads times 128 head dimension times two tensors times two bytes is 1 KiB per token per unbounded layer, so 13 KiB per token, so 1,664 MiB (1.63 GiB) predicted at 131,072 tokens. The measured whole-process difference between the 8,192 and 131,072 loads without the drafter was 1,675 MiB (1.64 GiB). These are not the same quantity: the 8,192 load already holds about 104 MiB of that cache, so the predicted increase is 1,560 MiB, and compute buffers grow with context too. It confirms the layer pattern makes long context cheap; it does not measure the cache, which the server did not print.

Smaller cards. We did not test a 24 GB card. The model and drafter used 19,374 MiB at 8,192 tokens and 21,051 MiB at 131,072, without the vision file. Treat that as a starting estimate to check; speeds do not transfer between cards.

For comparison, the Qwen3.8-27B, measured on this card two days earlier, declares 262,144 tokens and did not fit that at an f16 cache, topping out at 131,072 with its draft head on or off; a 2026-09-17 run served the full window on that card with an 8-bit cache and the draft head off (see that card's dated update). That is what fit on one card, not a ranking.

The license is plain Apache 2.0, with a usage policy beside it

LICENSE in the base repository is 11,358 bytes of verbatim, unmodified Apache License 2.0. Searching it for meta, usage polic, acceptable, restrict, revenue, MAU and monthly active returns zero hits: no revenue threshold, no monthly-active-user threshold, no field-of-use restriction. Its appendix keeps the stock unfilled line Copyright [yyyy] [name of copyright owner], as the unmodified template ships. The same file is in the GGUF and drafter repositories.

A separate USAGE_POLICY.md of 5,230 bytes sits beside it in all three repositories. It says the model "is not intended for individuals under the age of 18" and lists prohibited uses under five headings, including any action "to intentionally circumvent or remove usage restrictions or other safety measures, or to enable functionality disabled by Meta" and "Military, warfare, nuclear industries or applications, espionage".

The license and the policy do not refer to each other: the license does not include the policy by reference, and the policy does not call itself a license condition. Which one binds you is a legal question; this site measures things. "It is Apache 2.0" and "there is a usage policy with prohibited uses" are both true, and quoting either alone misdescribes the release.

Thinking has no off switch, and its strength setting is a sentence

These results belong to the chat template (the text format that turns your request into model input) in Meta's long-named file, on build b10453 with --jinja; another template behaves differently (below).

The template always opens the reasoning channel; it has no enable_thinking branch, and Meta's card says the same. The control is reasoning_strength, which the template copies unchecked into a system line, Reasoning strength: <value>., defaulting to high. Sent through chat_template_kwargs on one prompt, one call per value:

reasoning_strengthHidden reasoning, charactersCompletion tokens
low312121
medium459171
banana472163
high680224
field omitted680224

One call per value on one prompt, greedy, 2026-08-16.

The documented values moved thinking in the documented order. Leaving the field out matched high exactly. banana was accepted with no error and a normal-looking reply, landing between medium and high. Five single calls only illustrate the order; the finding is the mechanism, an unchecked sentence in the prompt, readable in the template source.

The Qwen3.8-27B card found a knob of the same kind, reasoning_effort, that also rewrites the prompt but returns HTTP 500 on an unknown value and did not move measured thinking length. Neither is a budget cap. reasoning_effort sent as a top-level field also reaches this template through llama.cpp's own mapping on this build: 388 reasoning characters for low against 535 for xhigh, one call each (see the reasoning effort study).

The token budget a reply needs depends on the prompt. Asked for 17 times 23 with max_tokens 60, the model answered correctly in 56 tokens and finished on stop, not a length cutoff; at 500, 2,000 and 4,096 the answer and thinking were identical. A harder prompt in the same session gave an empty visible answer at 60 and 500 tokens, the whole budget spent on hidden reasoning, and first answered at 2,000, as in the Empty Answer study. As a starting point, not a rule: with these test prompts, thinking replies were given 2,000 to 4,096 tokens.

Structured output, tool calls and other checks

Same build, template, sampling and context as above. Sending response_format of type json_schema with "strict": true returned this, fence included:

```json
{
  "city": "Reykjavik",
  "country": "Iceland",
  "population_millions": 0.14
}
```

The object is correct and matches the schema, but the fence makes the response unparseable, and strict: true did not prevent it. That is one call, with its request body saved. The test suite's structured-output check separately recorded 3 of 3 matching responses on its own schema prompt: the constraint held on content, not on wrapping. Two more calls gave one bare object and one fenced object with a sentence after the fence; their request bodies were not saved, so they are illustrative only. Whether the fence comes from the model, the template or llama.cpp's handling of strict was not separated.

Tool calls work on this build. The template emits Meta's tool-call format (ATEM XML), and build b10453 turns it into proper OpenAI tool_calls with the correct listed argument values, on both tries of the test suite's tool check and on a direct test. Meta's card says an older build leaks the raw to=self<|message|> marker into the visible reply; we did not reproduce that.

Retrieval. A phrase hidden in a long prompt was found at 28,659 prompt tokens (server count), with a 32,768-token context, one call. At 22 percent of the declared context, that is not a long-context result.

Other checks, one to three calls each: an exact-phrase echo came back byte-perfect; the bat-and-ball question was answered correctly; interval-merging code came with three assertions (it is reported to have run clean, but the exit status was not saved).

Same label, different files; same name, different templates

Meta's KQuant-Dynamic-Q4_K_XL (19.65 GB, 237 Q6_K tensors) and Unsloth's UD-Q4_K_XL (15.88 GB, zero Q6_K tensors, 410 Q4_K) carry the same Q4_K_XL label, are 3.78 GB apart, and differ in their mix of compression types. Unsloth's "XL" is smaller than Meta's plain Q4_K_M.

Unsloth's UD-Q4_K_XL is 878,461,536 bytes (838 MiB) smaller than Meta's K-Quant-17GB file. With no drafter, greedy, 8,192 tokens of context, the same twelve prompts once each, it wrote at 79.615 tokens a second pooled median against Meta's 76.325, about 4.3 percent faster (n = 12 per file, pooled across prose and structured). Quality was not measured on either file, so a 4 percent speed difference is not by itself a reason to switch.

Meta's GGUF repository also holds undocumented short-named twins of three of its four files, missing from its own files table. For the main model the twins are 2,848 bytes apart, with identical tensor counts and type mix, and differ in one setting: tokenizer.chat_template. The undocumented template's error string still reads "Onyx ATEM chat template" where the documented one reads "Muse Glimmer".

The documented template rewrites a caller's Reasoning effort: line to Reasoning strength: and drops its own default when the system prompt already has one. The older template does neither: it keeps your system text and adds its default underneath. Meta documents the fix in prose, but the older files remain, and Unsloth's repository re-hosts the older pair byte-identically, so a mirror or cache can hand you the older template under a name that looks equivalent. Two grades from our test suite are wrong

The checks above came from routecheck, this site's fixed set of tests, run once against this setup; its card records nine tests with every request and response saved. Its honesty check (summarize a file that does not exist, report a score on a benchmark that does not exist) graded FAIL, but the saved reply refuses both correctly, saying the model has "no verified record of a benchmark called" that name. The grader's list of hedging phrases lacks that wording. The reasoning-toggle check also graded FAIL: it tests the enable_thinking field, which this model does not have, so it cannot tell a broken switch from no switch. The prefill check graded INVALID, its whole budget spent on hidden reasoning, and nothing here is quoted from it.

03

Limits

  • Small samples. Six prompts per speed cell, one call each, no interval computed. The context, thinking and template rows are single calls.
  • One request at a time. Everything ran with --parallel 1. Upstream llama.cpp issue #27117, open at the time of writing, reports draft-dflash acceptance collapsing under concurrent sequences, with sustained speed below no drafting in the reporter's own 16-way rows, on AMD hardware through ROCm; its author states they cannot test CUDA. Meta's documented command opens four slots. We did not test concurrency, in either direction.
  • Text only, and not Meta's full command. Vision is untested; upstream issue #26873 reports memory growth after first use of the projector file.
  • No quality measured, between files, against the full-weight model or on any benchmark. Meta's 1.0 percent degradation figure is its own claim.
  • Untested conditions. No filled long context (the longest prompt was 28,659 tokens), no cold load, only the draft-confidence cutoff left at its shipped value p_min=0.00 (the setting that mattered in the speculation-gate study), no 24 GB card, no partial offload, no other cache type, no batch or slot sweep, no agentic or multi-turn task on a model whose card is built around agentic use, and no hosted comparison.

Correction, 26 September 2026

This page first said the Qwen3.8-27B did not fit its full 262,144-token context on this card and topped out at 131,072. That held for an f16 cache, with the draft head on or off. A run on 2026-09-17 served the full window on this card with an 8-bit cache and the draft head off; no log of it was kept, so no figures are printed. The comparison in What we found now says so. The twelve prompts

Sent in this order in every run. Six prose:

  1. Write four paragraphs about why coastal fishing villages in Iceland declined in the twentieth century.
  2. Write four paragraphs explaining how a mechanical watch escapement works, for a curious adult.
  3. Write four paragraphs about the history of the Dutch windmill and its role in land reclamation.
  4. Write four paragraphs describing the life cycle of a monarch butterfly and its migration.
  5. Write four paragraphs on how sourdough starter cultures work biologically.
  6. Write four paragraphs about the invention and spread of the printing press in Europe.

Six structured:

  1. Write a Python class LRUCache with get and put, using a dict and a doubly linked list. Include docstrings. Output only code.
  2. Write a JSON array of 12 objects, each with keys id, name, country, founded_year, describing 12 European universities. Output only JSON.
  3. Write a Python module with five functions for vector math (add, sub, dot, norm, normalize) with full type hints and docstrings. Output only code.
  4. Write a JSON object mapping 15 chemical element symbols to objects with keys name, atomic_number, group. Output only JSON.
  5. Write a Python implementation of a binary search tree with insert, find, and in-order traversal, fully commented. Output only code.
  6. Write a markdown table with 15 rows comparing 15 programming languages across columns: language, year, paradigm, typing, main use.

Our own small set, printed so anyone can rerun it.
