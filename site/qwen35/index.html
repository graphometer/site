Field card · two Qwen3.5 models on one RTX 5090 desktop

Qwen3.5 122B and 397B speeds on one RTX 5090 desktop

On one desktop with an RTX 5090 graphics card and 188 GiB of system RAM, one compressed file of each model wrote about 26 to 38 tokens (word pieces) a second for the 122B and about 14 to 20 for the 397B, depending on the prompt, with the model's built-in guessing feature set up as described below, one request at a time.

In short
  • On these two models, use the built-in guessing feature, but set its confidence cutoff yourself. Without the cutoff, the 122B wrote two creative prompts slower than with the feature off. The full command is in What to do.
  • Make sure the model fits in system RAM, and copy it in rather than memory-mapping it. Memory mapping cut the 397B's prompt reading by 82 percent. Check that the model fits in system RAM
  • Give the thinking room. With too small an output-token cap, the request succeeds and the answer comes back empty. Thinking and empty answers

By Grant Williams · Published 8 August 2026

中文摘要 (Chinese summary, synced 2026-08-11)

01

What to do

  1. Check that the model fits in system RAM. Disk: about 75 GB for the 122B, about 151 GB for the 397B. RAM: enough for the weights (73 and 150 GB) plus the system; we had 188 GiB. With less, weights stream from disk and every number here changes, in ways we did not measure. Our setups use 23 to 28 GiB of a 32 GB graphics card; a smaller card means keeping more expert blocks on the CPU, which we did not measure.
  2. Turn on the guessing feature with a confidence cutoff (--spec-type draft-mtp --spec-draft-p-min 0.75). Each file carries a multi-token-prediction (MTP) head that guesses the next few tokens; the full model checks them in one batch and keeps only tokens it would have written anyway (speculative decoding). The cutoff drops unconfident guesses. In our llama.cpp build the cutoff defaults to 0.00, meaning none, and the quantizer's published command lines leave it out. Test it on open-ended prose, not only structured prompts.
  3. Copy the model into RAM instead of memory-mapping it (--no-mmap). Memory mapping reads the file from disk as needed and hurts prompt reading most. The flag currently prints a deprecation warning pointing at its replacement; it still works.
  4. Set a generous output-token cap when thinking is on. 2,000 to 4,096 output tokens is a starting range that worked for our jobs on these two models, not a safe number, because the floor depends on the task; hard problems need far more. No universal safe number exists. Measure the floor for your own task (Empty Answer carries the method). Short factual replies with thinking off are fine small.
  5. For long prompts, read the prompt in bigger chunks (-b 4096 -ub 4096 instead of the defaults -b 2048 -ub 512). At a 131,072-token context with no memory mapping, prompt reading rose on a 48,029-token prompt from 224.5 to 932.2 tokens a second on the 397B, and on a 48,027-token prompt from 520.2 to 2,101.7 on the 122B. The batch-size study carries the full sweep, including the 8,192 setting that did not load. The full command below uses 65,536.
  6. Use a current llama.cpp. The caching fixes this design needs postdate July mainline builds, by our account; on an old build multi-turn caching misbehaves. With the fixes, the second turn re-read only 4 to 37 tokens instead of the whole history.
  7. Leave graphics-memory headroom. --n-cpu-moe N keeps the routed experts of the first N blocks on the CPU. One block too many loads all its weights, then fails minutes later. The guessing head costs +2.6 GiB on the 122B and +3.8 on the 397B.
  8. Wait for the health check, not the start message. Load time is mostly cache state; do not read a 100-second load as a failure.
  9. Keep the checksum output, not just the checksums. Check file count and checksums against the repository listing and save the output. One of our two checks survives as a saved file; the other does not.

The full command

llama-server --jinja --ctx-size 65536 --parallel 1 --n-gpu-layers 999 \
  --no-mmap --spec-type draft-mtp --spec-draft-n-max 6 --spec-draft-p-min 0.75 \
  --threads 24 --threads-batch 24 --flash-attn on --min-p 0.0 --top-p 0.95 --top-k 20 \
  --n-cpu-moe 38 --temp 0.6

That is the 122B's command as we serve it. The 397B's is identical except --n-cpu-moe 57 and --temp 1.0. Both files suggest 0.6; the 397B's 1.0 is our choice, a departure from the file and from the maker's published thinking-mode settings, which also say 0.6.

02

What we found

Writing speed is how fast the answer comes out; prompt reading is how fast the prompt goes in. Both in tokens a second (t/s).

What122B397B
Real thinking replies, sustained27 to 29 t/s (four long recorded generations)14 to 17 t/s (twelve recorded tasks)
Structured test prompt, with the cutoff38.25 t/s19.5 t/s
No speculation at all24.5 t/s10.4 t/s
Prompt reading (no memory mapping, August)865 t/s short, 717 t/s across a 29.7K prompt374 to 417 t/s

Speeds are end to end. Prompt reading declines with depth. One configuration per model, not a benchmark of the models.

The guessing feature: faster with a cutoff, slower on creative text without one

At identical placements (the same blocks on the card), the guessing head took the 397B from 10.35 to 19.55 t/s on the structured test prompt, an 89 percent gain, and the 122B from 24.5 to 26.1 on prose and from 24.6 to 38.25 on structured output. The bigger model pays more per step, so saving steps pays more.

Without the cutoff, our placement tests (moving more or fewer blocks onto the card) accepted 82 to 90 percent of guesses and gave the fastest numbers. But on the 122B's set of fifteen test prompts, the two open-ended persona prompts accepted only 25 and 30 percent of drafted tokens, and writing fell to 16.1 and 18.2 t/s, below the 24.5 with speculation switched off. When three quarters of guesses are thrown away, checking them is pure overhead. The same server was fine on reasoning, lists and code.

With the cutoff at 0.75, acceptance rose to 88 to 95 percent on every shape measured. On the 122B, speculation with the cutoff beat no speculation on prose as well as structured output; on the 397B that win is measured on the structured prompt only. The cutoff cost almost nothing on predictable text (the 397B: 20.4 without it, 19.5 with it, same prompt).

Where the weights live decides whether guessing pays. On these two models, whose weights fit in RAM, speculation paid 7 to 89 percent. On GLM-5.2, a 744B model on the same machine whose CPU-side weights exceed RAM, the same flags were slower (1.5 to 3.7 t/s against 4.0 to 6.0 without): with weights partly on the SSD, checking a batch multiplies disk reads. On the dense Mistral Medium 3.5, the same idea with a separate draft model pays about fourfold.

Memory mapping and load time

Turning memory mapping back on cost the 397B 29 percent of writing speed and 82 percent of prompt reading (396 down to 69.5 t/s), and slowed its load. The 122B's prompt reading fell from 865 to the 330-to-400 range. A cooler cache made the 122B's load about five times as long.

Graphics memory

Only every fourth block keeps a key-value cache (the stored memory of past tokens), with 2 key-value heads, so a 65,536-token context costs 1.50 GiB of cache on the 122B and 1.88 GiB on the 397B, worked out from the file headers. The measured setups:

The file headers predict each block's cost on the card (1.27 GiB on the 122B, 2.16 on the 397B); the measured slopes were 1,296 and 2,313 MiB per block (1.27 and 2.26 GiB), within five percent. One more GPU block than our 397B maximum loaded all its weights, then died minutes in, failing to allocate a 1,862 MiB compute buffer.

Thinking and empty answers

Both models think before answering, and the thinking counts against the output-token cap the client sets. Overrun is not an error: the request succeeds and the visible answer is empty. The 122B hit a 700-token cap three times in one evening. The 397B used up a 4,096 cap on the puzzle below. In the 397B's installation check, a 2,500-token cap produced exactly 2,500 tokens of reasoning and an empty answer; the retry at 8,192 answered cleanly. In a separate, later measurement on a different hosted model (not one of these two), that model answered a short prompt from a 256-token budget and had produced nothing visible at 12,000 tokens on a harder prompt the same day: more than 46 times apart, and a lower bound, because the second floor was never located.

The two models on one hard puzzle

The puzzle: time 15 minutes with a 7-minute and an 11-minute hourglass (a 47-token prompt). The 397B failed at a 4,096-token cap and finished in 7,608 tokens under 8,192. The 122B failed at 8,192 and finished in 9,719 tokens under 16,384. The 397B's first workable cap was half the 122B's, and it used 7,608 tokens against 9,719 (a 0.78 ratio, not a clean half). The 122B writes about twice as fast (28.8 against 15.1 t/s on these runs), so the successful runs took 5.6 minutes on the 122B against 8.4. We judged both answers correct.

Neither model is our coding model. The 397B completed a hard coding test in a 7,704-token thinking reply, and we judged it a pass; a 32-billion-parameter local coding model passes the same kind of test without thinking and much faster, by an account with no saved file. Our roles: the 122B for fast daily deep conversation, the 397B for hard reasoning and synthesis.

Other public results

Unsloth's guide states the 397B reaches 25+ tokens a second on a single 24 GB GPU with 256 GB of RAM (their claim, their configuration); our 19.5 on a 32 GB card with 188 GiB is a result of the same kind, not a record. llama.cpp's MTP support landed in May. A 184-session report found roughly +20 percent from tuned speculation on a sibling-family model. Earlier measurements of the creative-text slowdown are in Corrections and updates.

03

Limits

  • The creative-text slowdown was measured on the 122B only. The 397B's own creative case without the cutoff was never run. The 122B server's exact flags are not in its log, so the slowdown is put down to the missing cutoff from the build's zero default and the contrast with the runs that had it.
  • One file per model, one runtime, one request at a time. No comparison of compressed versions and no benchmarks of our own; any benchmark number near these models is the vendor's. The files are different tiers (a 4-bit-class 122B, a 3-bit-class 397B), so the puzzle compares two setups, not two models at matched precision.
  • The puzzle is one puzzle, run once per cap per model; do not generalize it. The replies were not saved, so their correctness is our account; every token count is recorded.
  • Long context was tested only this far, and vision not at all. In August the longest prompts were 29,737 tokens on the 122B (64K setup; its 128K setup saw nothing over 2,617) and 4,367 on the 397B. On 2026-09-21 the 122B read a 48,027-token prompt and the 397B a 48,029-token prompt, at a 131,072 context. The maker's million-token claim was not attempted.
  • Some points have no saved file: the 397B's checksum check, client-side verdicts such as "byte-perfect" and "needle found", running the 122B beside a speech engine (not run for the 397B at all), and the coding comparison. No check that speculation leaves output unchanged was run. Fully cold-cache loads were never timed.

Update · 2026-08-10 · prior art, corrected

On publication this page cited a community measurement of MTP without a cutoff on a 27B Qwen3.5 coming out net negative, then said two things that were wrong: that as of 2026-08-08 we had found no published measurement with and without the cutoff on these two model sizes, and none anywhere isolating creative-shaped text. We were not first, and we did not search in the language the measurement was published in.

A benchmark published on 2026-05-12 measured this on a dense Qwen3.6-27B: creative writing fell from 15.1 to 13.7 tokens a second with the guessing head on (13.1 to 12.6 at the next quantization up), while coding rose 171 percent, with draft acceptance of 39 to 48 percent on creative text against 79 to 89 percent on code ("MTP 加速不是玄学", first posted to Zhihu, mirrored to juejin). A 2026-05-22 write-up measured a Qwen3.6-27B on a 24 GB card at 29.0 tokens a second with no speculation, slower with the head and no cutoff, and 48.9 with the same 0.75 cutoff (neoteric.no).

Our numbers confirm both effects in a different setting: large mixture-of-experts models with most expert blocks on the CPU, with prose and structured output kept apart on the same model, where the effect changes sign.

中文摘要：Qwen3.5 现场记录卡（122B 与 397B）

本文是英文原始记录的摘要，英文版为准（English is canonical）。对应英文记录：graphometer.ai/qwen35/，日期 2026-08-08（测试运行 2026-08-05 至 08-06，文件于 2026-08-08 复核，既有研究更正于 2026-08-10，预算建议修订于 2026-08-11）。本摘要同步日期：2026-08-11。英文页面若有任何改动，本摘要在重新同步之前即告失效。英文页面第 04 节现有一条 2026-09-21 的读取速度更新说明，本摘要尚未收录；截至 2026-09-26，本摘要落后于英文页面。

这是什么。Qwen3.5 是一组混合专家（MoE）模型：总参数量很大，但每个 token 只激活其中一小部分。我们在同一台工作站、同一张 32 GB 显卡上，用同一套方法，在两天里把其中两个模型分别投入使用：122B（26 到 38 tokens/秒）与 397B（14 到 20 tokens/秒）。本页的核心发现是速度旁边的那个陷阱（见下）。页面上的每个数字都可追溯到一份有日期的记录或模型文件本身；凡属厂商说法而非我们的测量，文中均已注明。

规格（读自文件头，而非引自模型卡）。参数总量由张量形状求和得出：122B 为 122,111,526,912，397B 为 396,346,350,336。每 token 激活量：122B 在 256 个专家中路由 8 个，另加 1 个常驻共享专家，约 9.8B；397B 在 512 中路由 10 个，另加 1 个共享专家，约 17.4B，与厂商 A10B / A17B 标签是同一套算术。架构在两个文件中一致：每第四个块为带 KV cache 的完整注意力块，其间为线性注意力块（122B 为 48 块中的 12 块，397B 为 60 块中的 15 块）。上下文：两个文件都声明 262,144，我们默认以 65,536 提供服务；厂商另称经扩展可达 1M，此项不在文件中，我们也从未测试。词表 248,320。两者默认都会先思考再回答。权重开放，许可证 Apache 2.0。

我们实际运行的东西。Unsloth 的 MTP-enabled GGUF 构建，版本已固定：unsloth/Qwen3.5-122B-A10B-MTP-GGUF 的 UD-Q4_K_S，pinned revision 907becb3，3 个文件，73.43 GB（68.38 GiB）；unsloth/Qwen3.5-397B-A17B-MTP-GGUF 的 UD-IQ3_XXS，4 个文件，149.84 GB（139.54 GiB）。一处诚实的标签说明：名为 IQ3_XXS 的构建中并不包含该类型的任何张量，这是量化档位标签，不是逐张量的描述。机器：一张 NVIDIA GeForce RTX 5090（32,607 MiB VRAM）、Intel Core Ultra 9 285K（24 核）、188 GiB 系统内存，权重存放在 4 TB NVMe SSD 上。本页最关键的一条事实：两个模型的权重都能完整装进系统内存（73 和 150 GB 对 188 GiB）。运行时：mainline llama.cpp，commit c8e03ce8，为这一对模型所需的架构修复而重新构建。

核心发现：猜测头（MTP）及其门限。两个文件都自带一个 multi-token-prediction 头：一个额外的块，用于低成本地起草接下来的几个 token，由完整模型一次性批量验证，只保留完整模型本来也会产生的 token。开启后的收益（在相同放置条件下测得）：397B 在结构化探针上从 10.35 提升到 19.55 tokens/秒，增幅 89%；122B 在结构化输出上从 24.6 提升到 38.25。

陷阱在于配套的置信度门限。命令行参数 --spec-draft-p-min 在我们使用的构建中默认值为 0.00，即不设门限。不设门限时，可预测的文本一切看起来都很好：我们不带该参数的逐级阶梯测试接受了 82% 到 90% 的草稿 token，并跑出全场最快的数字。但换成开放式创作型提示后，122B 记录在案的两个人格探针只接受了 25% 和 30% 的草稿 token，解码速度掉到 16.1 和 18.2 tokens/秒，低于完全关闭推测解码时的 24.5。每一个猜测都必须被验证；当四分之三被丢弃时，推测解码就是纯粹的开销，而创作型文本恰恰是下一个 token 最难预测的地方。这个陷阱在基准测试型的提示上完全看不出来。

修复只是一个参数：把门限设为 0.75，接受率在所测的每种形状上都回到 88% 到 95%。需要说明的不对称：创作型文本的崩塌只在 122B 上测过，397B 的门限沿用同族证据，它自己不设门限时的创作型表现从未测量。

关于既有研究（2026-08-10 更正）。发表之后的中文检索找到了更早的公开测量：2026-05-12 的一篇中文评测在稠密的 Qwen3.6-27B 上先测得了这一效应；另有一篇 2026-05-22 的文章在 27B 上公布了加上 0.75 门限之后反超无推测基线的结果。我们不是最早的；我们的结果是在另一种部署条件下的独立复现：大型 MoE，且大部分专家块放在 CPU 上。英文页第 04 节列出全部出处与更正日期。

这不是模型家族的属性，而是字节所在位置的属性。同一套参数在 GLM-5.2（744B MoE，同一台机器，但 CPU 侧权重超出内存）上被测得更慢（1.5 到 3.7 tokens/秒，对不开推测时的 4.0 到 6.0），因而弃用。权重部分留在 SSD 上时，批量验证放大的是磁盘读取，而不是摊薄内存读取。

思考的代价，以及静默失败。思考过程与可见答案共用客户端设定的同一个输出 token 上限。超出上限不会报错：请求成功，可见答案为空。工作规则：2,000 到 4,096 个输出 token 是在我们的任务上行之有效的起始范围，不是安全值，因为下限取决于任务本身；难题需要远高于此。在其后一次记录在案的测量中，同一个托管模型、同一天，对一个简短提示在 256 token 的预算内给出了可见回答，对另一个更难的提示在 12,000 token 时仍无任何可见输出：两个提示之间相差超过 46 倍，且这只是下界（第二个下限从未找到，我们在 12,000 处停止了测量）。不存在普适的安全数字；请为你自己的任务实测下限（方法见英文页 graphometer.ai/empty-answer/）。一次记录在案的对照（15 分钟沙漏难题，7 分钟与 11 分钟两个沙漏、47 token 的提示）：397B 在 4,096 上限下失败，在 8,192 上限下用 7,608 tokens 完成；122B 在 8,192 下失败，在 16,384 下用 9,719 tokens 完成（比值 0.78，不是干净的一半）。但按 wall-clock，成功的那两次运行是 122B 更快（28.8 对 15.1 tokens/秒，5.6 分钟对 8.4 分钟）。两个模型运行在不同的压缩档位上，因此这是两套部署的比较，不是两个模型在同等精度下的比较。一道题，每个上限每个模型各跑一次：一个生动的记录点，不是缩放定律。

其他要点。不要对能完整装进内存的模型使用 memory mapping：在 397B 上，开启后 prompt reading 损失 82%（从 396 降到 69.5 tokens/秒），解码损失 29%。VRAM 读数为整卡读数，含约 0.7 到 1.0 GiB 的桌面占用；我们的配置使用 32 GB 显卡中的 23 到 28 GiB。多放一个块不会立即报错，而是数分钟后才失败：权重全部载入之后数分钟才因计算缓冲区分配失败而退出，请在权重算术之外留出余量。

可复现的完整参数。两个模型的命令形状相同，差异值另注：

llama-server --jinja --ctx-size 65536 --parallel 1 --n-gpu-layers 999 \
  --no-mmap --spec-type draft-mtp --spec-draft-n-max 6 --spec-draft-p-min 0.75 \
  --threads 24 --threads-batch 24 --flash-attn on --min-p 0.0 --top-p 0.95 --top-k 20 \
  --n-cpu-moe 38 --temp 0.6

以上是 122B 的启动命令。397B 只有两处不同：--n-cpu-moe 57 与 --temp 1.0。放置参数 --n-cpu-moe N 的作用是把前 N 个块的路由专家留在 CPU 上。

独立测量。与 Qwen 团队、阿里巴巴集团（Alibaba Group）或 Unsloth 无任何隶属、认可或关联关系。Qwen、Qwen3.5 与通义为阿里巴巴集团控股有限公司的商标，此处仅用于识别。再次说明：本文为英文记录的摘要，英文版为准。英文记录日期 2026-08-08，本摘要同步日期 2026-08-11。
