Qwen3.8-27B measured on release day, one RTX 5090: its built-in drafter needs a cutoff

With thinking off, Qwen3.8-27B wrote prose at 72.4 tokens a second with its built-in drafter (a part that guesses a few words ahead) set to stop guessing when unsure, against 65.9 with no drafter (65,536-token window; median of three repeats of one prompt).

Two setups. This page is the 14 August test with the built-in drafter. Since 19 October this model runs here with a separate draft model instead: see that update.

In short
  • If you use the built-in drafter, turn it on and set its cutoff yourself (--spec-draft-p-min 0.75); llama.cpp does not use it unless asked. At a 65,536-token window, a cutoff of 0.75 made structured output 79.3% faster than no drafter, and a cutoff of 0 made prose 32.4% slower, at 44.5 tokens a second. What to do
  • Turn thinking off in the right place (inside chat_template_kwargs). On this llama.cpp build, enable_thinking sent at the top level was silently ignored: no error, and thinking stayed on. The client traps
  • Check the license of the exact repository you download. The 27B is Apache 2.0; Qwen3.8-2.4T-A95B, released the same week, is not. The two licenses

01

What to do

These are the settings from the 14 August test with the built-in drafter, using one compressed file of the model (Unsloth's UD-Q5_K_XL) in llama.cpp, the program that runs it. For the separate draft model used since 19 October, see that update.

  1. Turn the built-in drafter on, and set its cutoff yourself (--spec-type draft-mtp, --spec-draft-p-min 0.75). The drafter (also called the draft head, or MTP) is a small block inside the model file that guesses the next few tokens (word pieces) for the model to check. With no drafter flags you get about 66 tokens a second on both kinds of output. The cutoff stops a draft early once the drafter is no longer confident. Its default has changed twice: 0.9, then 0.75 for about fifteen months, then 0.0 from 2026-05-19, which our 2026-08-05 build follows. Pass it explicitly. The measurements
  2. If you use the ggml-org conversion, the drafter is not in its main file. That file was built with --no-mtp; the drafter ships as separate mtp-*.gguf files, so the main file alone cannot draft for itself.
  3. Turn thinking off in the request body, inside chat_template_kwargs. There it worked; as a top-level field it was ignored (below). A request body with the thinking switch in the right place (prose speed runs used max_tokens 400): 
    {"model": "qwen3.8-27b",
 "max_tokens": 400,
 "chat_template_kwargs": {"enable_thinking": false},
 "messages": [{"role": "user", "content": "..."}]}
  4. With thinking on, give the reply room, and measure your own floor. Thinking counts against the same max_tokens as the visible answer, so a small budget can come back empty. On one prompt the first budget tested that worked was 500; on another, 60 was enough. Do not copy 500 into your client. As a starting point, not a rule: we give thinking replies 2,000 to 4,096 tokens here, and structured or JSON work with thinking on starved even at 1,200. Details
  5. Spell reasoning_effort exactly: xhigh, medium or low. Any other value fails that request with HTTP 500. It also does not cap thinking: it adds a sentence to the prompt, and medium adds nothing.
  6. Choose the context window (how much text the model holds at once) by what else needs the card. 32,768 tokens was faster on both kinds of output and left more room than 65,536; if nothing else needs the card, start there. The 65,536 used here left about 7 GiB free for voice software on this desktop. With a 16-bit (f16) key-value cache (the memory that holds the text so far), 131,072 is the most this card holds; the full 262,144 needed an 8-bit cache and the drafter off (Updates).

The exact command for the release-day default. Every row of the speed table below is this command with --ctx-size changed, the three --spec-* flags present or absent, and --spec-draft-p-min set to the value shown:

llama-server --model Qwen3.8-27B-UD-Q5_K_XL.gguf \
  --host 127.0.0.1 --port 8198 --alias qwen3.8-27b \
  --jinja --ctx-size 65536 --parallel 1 --n-gpu-layers 999 \
  --threads 24 --threads-batch 24 --flash-attn on --timeout 3600 \
  --temp 1.0 --top-p 0.95 --top-k 20 --min-p 0.0 \
  --spec-type draft-mtp --spec-draft-n-max 6 --spec-draft-p-min 0.75

What we found

Speed by window and drafter

Seven server loads, same file, build and card. Writing speed is tokens a second (t/s), the median of three warm repeats of one prompt per kind of output, thinking off. Prompt reading (prefill) is one uncached send of a 5,792-token prompt. Memory is MiB after load, on a 32,607 MiB card.

One session per row. No interval is computed. A diagnostic set of runs, not a benchmark.

Prose speed did not fall steadily as the window grew: 78.25 at 32,768, 72.43 at 65,536, 77.46 at 131,072. With one session per row and no repeat, this could be run-to-run variation. Structured output did fall steadily, 131.21 to 118.69 to 111.60, about 15% from end to end.

A bigger window costs little memory. The model is dense (all of it runs for every token, unlike a mixture-of-experts model), and only 16 of its 64 layers keep a key-value cache, about 64 KiB per token. Quadrupling the window from 32,768 to 131,072 cost about 6,700 MiB. That is the cost of allocating the window, not filling it. What stops it at 131,072 is free space: 2,657 MiB. The full 262,144 tokens at an f16 cache would want roughly 16 GiB of cache on top of roughly 19 GiB of weights: a limit of this card, not the model.

Prompt reading is fast. About 3,240 t/s with the drafter off and about 2,900 with it on: the drafter costs a little prompt reading and buys a lot of writing. The prompt cache works: sent again, 5,788 of the 5,792 tokens came from cache, so the rate printed for repeat sends means nothing and only the first send is in the table.

On a smaller card. A 24 GB card holds about 24,576 MiB. On these readings the no-drafter 32,768 row (21,748 MiB) is the only one with real headroom, the drafter 32,768 row (23,250 MiB) leaves under 1.5 GiB before a desktop compositor and fragmentation are counted, and everything at 65,536 and above is out of reach at this compression. A 24 GB card, a smaller compressed file and a window below 32,768 were not tested.

Against the other Qwen models measured here. 72.43 prose t/s, against 26 to 38 on the Qwen3.5 122B and 14 to 20 on the 397B (pair field card). Not a benchmark; a smaller model on this card could plausibly be faster.

The drafter and its cutoff

Both cutoffs were set explicitly on the command line, not left to the build's default. At a 65,536-token window:

SettingProse t/svs no drafterStructured t/svs no drafter
No drafter65.87baseline66.21baseline
Cutoff 0.7572.43+9.9%118.69+79.3%
Cutoff 044.52-32.4%99.86+50.8%

Asking for the drafter with the cutoff set gave 1.79 times the structured speed of not asking. Asking with no cutoff made prose slower than not asking at all.

The server's own counters explain it. At 0.75, four repeats of one prose prompt kept 61% to 74% of their drafted tokens, drafting 110 to 130 tokens each, with a mean draft length of 2.15 to 2.45. With the cutoff at 0 the same prompt kept 17% to 22% and drafted 486 to 570 tokens per repeat, so about 78% to 83% of the drafting was thrown away, with mean draft length 2.04 to 2.34. The card spent real time drafting tokens the model then rejected.

How many drafts were kept moved with the kind of output. Four repeats of one structured prompt kept 84% to 96% of their drafts at mean draft lengths of 4.66 to 5.94; with the cutoff at 0 it still kept 59% to 78%. That fits the idea that structured output is more predictable, though two prompts on one evening cannot show it is the only cause. It is also why a setup with no cutoff can look excellent on a benchmark-shaped prompt while costing a third of the speed on prose.

The same direction as an earlier study. Our speculation-gate study, four days earlier on the same workstation, found the shipped default of 0.00 making prose slower than no drafting and structured output faster, on a 397B mixture-of-experts model mostly in system RAM, across 160 paired measurements. This is a dense 27B held entirely on the card, one session per setting. The sizes of the effects are not comparable; what this adds is a second setup pointing the same way.

Thinking: a real off-switch, and a budget floor that depends on the prompt

The off-switch works. Thinking is on by default and came back in its own field, with zero leakage into the visible answer on every probe we ran. With enable_thinking: false inside chat_template_kwargs, a question was answered in 4 completion tokens with zero reasoning characters. With thinking on, the same question took 29 completion tokens and 73 reasoning characters. Both replies ended on a stop reason, not a length cutoff (budgets 512 off, 4,096 on), so the counts are what the model spent. On a hosted route for the 2.4T model the day before, thinking could not be turned off at all (a different serving stack, so not a comparison of the models).

The budget floor belongs to the prompt, not the server. Asked for a two or three sentence explanation, a 60-token budget returned no visible answer (60 completion tokens spent, 295 reasoning characters, finish_reason: length). The first budget tested that returned a complete answer was 500. Nothing between 61 and 499 was tested, so 500 is the first tested success, not a measured threshold. In the same session, the product of 17 and 24 came back at a 60-token budget, using 58 tokens. Our Empty Answer study found the same.

Client traps (this chat template, this llama.cpp build)

The thinking switch was ignored as a top-level field. Sent in the request body outside chat_template_kwargs, enable_thinking was silently ignored: no error, no warning, a normal-looking reply. Our test tool got byte-identical replies with and without it: 104 visible characters, 289 reasoning characters, 140 completion tokens both times. We did not try every way a client might send it. A client that sets it the obvious way pays for thinking on every call.

An invalid reasoning_effort returns HTTP 500. The chat template raises an error on any value other than xhigh, medium and low, which comes back as a server error, not a fallback. Other requests in flight are unaffected and the server keeps serving.

reasoning_effort rewrites the prompt; it does not set a budget. The template adds a plain-language instruction to the prompt, and medium adds nothing (it has no branch of its own). Prompt length on one question: 33 tokens at medium, 63 at low, 75 at xhigh. Thinking length did not follow the setting: low 253 characters, medium 410, xhigh 197, one call each, so treat the order as an illustration. A hosted test of the 2.4T model the day before found the same: the setting moved style and the prompt while leaving thinking spend flat. A later study, Reasoning effort is a sentence, not a dial, showed on this same model file that the gaps above are the size of the added text, 42 tokens between medium and xhigh and 30 between medium and low, the same two numbers it measured on three other prompts.

Two licenses in one family

Qwen3.8-27BApache 2.0. The LICENSE file, read in full at the exact version (revision) used, on 2026-08-14: 11,544 bytes of the verbatim Apache License 2.0 text, appendix reading Copyright 2026 Alibaba Cloud. No user or revenue threshold. The copy in the official FP8 (8-bit) repository is byte-identical (same SHA-256).
Qwen3.8-2.4T-A95BNot Apache 2.0. Read at its own revision 207bd685 on 2026-08-13: a custom "Qwen3.8-Max License" of 3,390 bytes, an MIT-style grant with two added conditions. A product above 100 million monthly active users or US$20 million in monthly revenue must display the model's name prominently. A "Model as a Service" or "AI Work Assistant" business whose aggregate revenue exceeds US$50,000,000 in any consecutive twelve months must obtain a separate license from Qwen before using the software for any commercial purpose, with internal use exempt.

"Qwen3.8 is Apache 2.0" is wrong as a family statement and true of the 27B. That is a fact about those two files at those revisions, not about every 3.8 repository. The community GGUF file we served carries general.license: apache-2.0 in its header, but that is the converter's declaration, not the maker's: check the conversion you download. Neither reading is a legal opinion. The release watch carries the 2.4T side with its own dated readings.

Tools, retrieval and structured output

These are quick working checks of one to three calls each, not an evaluation, and they do not rank this model against any other.

  • Tool calls arrive as XML, and this build reads them. The template writes tool calls as XML, not the JSON of the previous generation, so a runtime needs a matching parser. Both tool tests passed with correct argument values and the tool_calls stop reason. A two-step round trip through the route other programs on this desktop use also worked: the model asked for a file, we returned five numbers, and it summed them correctly.
  • Retrieval. A fact hidden in a 153,842-character text was found at a server-reported 31,380 prompt tokens, at the 65,536-token window. That is about 12% of the declared context: not a long-context result.
  • Structured output. Three of three replies matched the requested schema.
  • Other checks. An exact-phrase echo was byte-perfect; interval-merging code passed its three assertions; a bat-and-ball question was answered correctly.
  • One automated grade was wrong. The honesty check came back FAIL, a false negative. Asked to summarize a file that does not exist and report a score on a benchmark that does not exist, the model refused both and wrote "I won't invent a numeric score." The grader did not count first-person refusals; read by a person, it is a pass. Two of the nine checks came back INVALID: their budgets came from the 500-token figure above, thinking used them up, and they measured nothing.
  • One coding-agent client check did not run. The client hung with zero requests reaching the server, a known client-side hang. The route was tested with a direct client instead; no pass is reported.
03

Limits

  • Small samples, one evening. Speed medians are three warm repeats of one prompt per kind of output in one server process; draft counts are four repeats; the other checks are one to three calls each. Only cutoffs 0.75 and 0 were tried, so 0.75 is not shown to be the best value. No interval or significance claim is made.
  • One file, one card, one placement. Only UD-Q5_K_XL, with no data on a smaller or larger compressed file, the official FP8 (8-bit) weights or the uncompressed model. No 24 GB card, no partial offload, no other cache type in the release-day runs, no batch or --parallel sweep. Sampling used the model card's thinking-mode values with thinking off; the card's suggested non-thinking values (0.7 / 0.80 / 20 with a presence penalty of 1.5) were not tried.
  • No filled long window. The longest prompt actually processed was 31,380 tokens. Writing speed with a full 128K prompt is untested, and nothing here speaks to behavior at 131,072 tokens, let alone 262,144.
  • Correctness not checked; vision untested. We did not compare outputs or logits against the reference implementation, and have no numerical-correctness check for the Gated DeltaNet layers or the drafter on this build. The model's configuration records end-of-sequence token 248044 and the GGUF header records 248046; we did not reconcile that, and did not hash the tokenizer against the Qwen3.5-397B or 2.4T files. The model also reads images and video; we served it text-only and never loaded the vision part.
  • Dated. Everything here except the updates below is dated 2026-08-14. Community files are re-cut and runtimes change defaults (the cutoff flag already has, twice); treat version-specific findings as unverified since that date.
04

Corrections and updates

Update · 2026-09-26 · a wider window was served here

This page gave 131,072 tokens as the ceiling at an f16 cache. On 2026-09-17 this same model was served at the full 262,144 tokens on this same card, with an 8-bit (q8_0) key-value cache and the built-in drafter (MTP) forced off, because the drafter's own context needs room that a 256K cache does not leave beside it. The record is a note written into the start script and a same-day lab note; no raw log survives, so no speed or memory figure from it is given here. At an f16 cache, 131,072 remains the ceiling on this card, drafter on or off. A new run on 2026-09-26, with its logs kept, is written up on Qwen3.8-27B at 256K.

Update · 2026-10-19 · a separate draft model

Since 19 October this model runs with a separate draft model, DFlash 2 for Qwen3.8-27B (a Q4_K_M file of 1.1 GB), plus n-gram drafting, instead of the built-in drafter. A draft model guesses a few tokens ahead and the main model keeps the guesses it agrees with. It runs the same UD-Q5_K_XL file on mainline llama.cpp, with an 8-bit cache, -ub 256 and a 229,376-token window. With thinking on, 3,500 tokens of reasoning with no visible answer came out at 186.61 tokens a second about 20,000 tokens deep, against 60.39 for the same kind of reasoning without the draft model at a 262,144 window. With the draft model at the full 262,144 window the same reasoning ran at 189.26, so the smaller window is not what made it faster. On a plain letter with thinking off the gain was smaller: 87.61 against 60.70 at 262,144. Reading was 10 to 15 percent slower. The window is 229,376 rather than 262,144 because the card peaked at 30,647 MiB there and at 31,992 MiB at the full window. These are single runs on 19 October 2026; Qwen3.8-27B at 256K and the October roster carry the detail.

How this was measured

DatesThe Qwen team published the model at about 11:00 EDT on 2026-08-14. Download 19:14 to 19:19 EDT; recorded runs 19:14 to 21:07 EDT the same evening.
MachineOne desktop: Core Ultra 9 285K, 188 GiB RAM, one RTX 5090 with 32,607 MiB of VRAM, driver 580.173.02, Pop!_OS.
RuntimeMainline llama.cpp llama-server, a build already on this machine from 2026-08-05, master c8e03ce, CUDA 12.8; the server reports itself as b1-c8e03ce. No rebuild was needed: the file declares the dense qwen35 architecture that build already implements, so a build older than the qwen35 work would not inherit it.
Weights servedunsloth/Qwen3.8-27B-GGUF at revision fe1e2a23d973adb629709749dc4f6756df66ef10, UD-Q5_K_XL: Unsloth's dynamic mix with an importance matrix, not a stock Q5_K. One file of 20,218,178,624 bytes (18.83 GiB), SHA-256 176a6a3f034e9cdc447c10cd00329fc9b31002e6589b9295f2ad4f1eefe0f6ab.
Integrity, and its limitThat SHA-256 equals the repository's own LFS object id at that revision, and the vision projector file (927,607,488 bytes, cbb841a9ee0636b2ec172f5bb8df2ea8dfeb01e90fe7c6126581d662a0b4e43e) matches too, both hashed before first load. That checks the files against the conversion, not the conversion against the official weights.
Placement-ngl 999: all 64 layers on the GPU. The model is dense, so the --n-cpu-moe setting used for mixture-of-experts models does not apply; the file fits the card whole or not at all. Only the window and the drafter were varied; --spec-draft-n-max was not.
SamplingTemperature 1.0, top-p 0.95, top-k 20, min-p 0: the model card's thinking-mode values, which match the sampling metadata in the GGUF header (general.sampling.temp 1.0, top_p 0.95, top_k 20), used with thinking off.
Speed methodThinking off, so the tokens counted are answer tokens. One discarded cold repeat, then three warm repeats of one prose prompt and one structured prompt per row, median of server-reported rates. Prompt reading is the first, uncached repeat only.
LoadsAll seven loads took 2.03 to 3.04 seconds, with the file still in the page cache because it had just been written and hashed. A cold load from disk was not measured.
Memory readingsRaw MiB from nvidia-smi. MiB is printed first because that is what the tool reports; a MiB reading is never divided by 1000 and called GiB.
NetworkServed on a loopback port for the study; not exposed to the local network at any point.

The model, as read from its files

Read from the model's own configuration and the GGUF file at the exact repository versions (revisions) named here, on 2026-08-14. Amber text marks the maker's claim rather than our reading.

MakerThe Qwen team (Alibaba).
WeightsQwen/Qwen3.8-27B at revision 1d4bf0f2ff6012fd82039f2fa52739d0dd7c60c0: 18 weight files in the maker's format (safetensors) plus an index, 32 files.
ShapeDense, 27B; no expert blocks anywhere in the configuration.
ArchitectureHybrid: 64 layers in 16 groups of three Gated DeltaNet blocks (layers that keep a running summary instead of a key-value cache) followed by one Gated Attention block, so only 16 of the 64 layers hold a key-value cache. We did not measure that running state.
DrafterA multi-token-prediction head inside the weights file, one extra block (block count 65).
Context262,144 tokens native, declared in the file. The maker also claims extension to 1,000,000; that claim is not in the file and we did not test it.
Vocabulary248,320 tokens, the same size as Qwen3.5-397B and the 2.4T. Configuration end-of-sequence 248044; served GGUF header BOS 248044 and EOS 248046, not reconciled, so no tokenizer-migration claim is made.
ModalityNatively multimodal by its configuration (images and video). Served text-only here.
VariantsOne post-trained model, no base model. An official FP8 repository (the weights stored in a compact 8-bit number format) exists at revision 017b9c7af6b5689d5dd426a76e0bc077eb5ca20a; not used.
GGUF filesNo official GGUF; every GGUF is a community conversion. The ggml-org main file of this revision reads 851 tensors and no nextn (drafter) tensors, against 866 including 4 nextn tensors in the Unsloth file served. Read from file headers over HTTP range requests before downloading.
