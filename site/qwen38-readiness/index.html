Qwen3.8 release: both open models verified, under two different licenses

Qwen3.8 comes as two downloads and one online model, and each got a different result. Checked 2026-08-09 to 2026-08-16; after that, treat this status as unverified.

The 27B downloadReal, on the official Qwen organization, under Apache 2.0. It ran on one desktop the day it shipped. Do: check who owns a repository (the official one is Qwen/Qwen3.8-27B); settings are on the Qwen3.8-27B field card.
The 2.4T download (the open Max-class weights)Real, on the official Qwen organization, under a custom license with revenue thresholds. The only community copy that fits this test desktop's free disk, 397.3 GB, would not load: the server program rejected it in 0.38 seconds because its compression type was not one any public build checked could read. Do: read the license; check a file's compression type before downloading.
Qwen3.8-Max online (the hosted model)Thinks by default, and the thinking counts against your token limit: a 2,000-token limit on a puzzle returned an empty answer. The 2.4T download, served online, did the same at small limits. Do: allow thousands of tokens of headroom.
In short
  • Read the license for each download, not the family. The 27B download is Apache 2.0. The 2.4T download adds a name-display duty for very large products and a separate license for some businesses above fifty million US dollars in revenue. The two conditions
  • Check who owns a repository before you download: a real Qwen release is on the official Qwen organization. If you use a community file, check its compression type against your software first.   • Allow thousands of tokens of headroom on Qwen3.8-Max online. Its hidden thinking counts against your token limit. The measurements

By Grant Williams · Published 9 August 2026

01

What to do

Tell a real release from a fake. Fake repositories (online folders of model files) using the Qwen3.8 name were still up when re-checked on 2026-08-13. Three questions settle almost every case without a download:

  • Who owns it? A release comes from the maker's own organization account. Anything else is that account's work, whatever the name says.
  • Is anything in it? Open the file list first. Weights (the model's learned numbers) come split into large pieces called shards: a 27B at four bits is tens of gigabytes, a 2.4-trillion-parameter model is hundreds. A readme and a small configuration file are no model.
  • Was this size announced? The 2026-08-03 announcement named exactly two open models, a 27B and the 2.4-trillion-parameter Max.

Then take the link from the Qwen team's announcement or the official organization page, confirm the license file and sensible shard sizes, and check the checksums (fingerprints of each file) after downloading. For the 27B, compare against Qwen/Qwen3.8-27B at the revision (saved version) under How this was measured; weights that are not the maker's files at a revision you can name are not the release. This took about five minutes.

Check the compression type before a big download. Community GGUF files (the format llama.cpp reads) store the weights compressed, which is called quantization. A familiar name is not a format: the 2.4T download's community file called Q1_0 is not mainline Q1_0, and only the per-tensor headers (the description of each block of weights) show its real type. Compare that type against the types your software can read. The check costs minutes; here the download cost an afternoon and 397 GB of disk.

Online, budget for thinking. Qwen3.8-Max online thinks by default, and the 2.4T download always thinks. Either way the thinking is billed as output tokens (word pieces) inside your max-tokens limit. Give it thousands of tokens of headroom, or try the reasoning_effort setting (on the one prompt tested with the 2.4T download online, it did not reduce thinking). An empty answer that ends with the length stop reason (the limit ran out) is a budget failure, not a refusal.

Put a JSON schema in the prompt, not only in the API's response_format field. On the 2.4T download, do not count on turning thinking off (the 27B has a working off-switch). Check each provider's terms behind an aggregator listing (an aggregator resells many companies' model services through one account). The evidence

The 2.4T download's license is not Apache 2.0

Qwen3.6, the previous open release, shipped under Apache 2.0. The 2.4T download does not. Both of their repositories hold the same Qwen3.8-Max License, 3,390 bytes, read on 2026-08-13: an MIT-style permission grant with two conditions.

  • Name display above consumer scale. Products or services built on the model with more than 100 million monthly active users, or more than twenty million US dollars in monthly revenue, must display the model name prominently. The revenue test is monthly, not annual.
  • A separate license above fifty million. Businesses offering the model as a service, or offering an "AI Work Assistant" product, whose aggregate revenue exceeds fifty million US dollars in any consecutive twelve months, must obtain a separate license from Qwen before commercial use. Internal use is exempt.
The operative clause, verbatim Such licensees "shall obtain a separate license from Qwen before Using the Software or its derivative works for any commercial purpose."

As we read it, the grant works like MIT for individuals, researchers and ordinary businesses. The file does not say what a separate license costs, and no percentage of anyone's revenue appears in it. For local research at the scale this site works (downloading, running, modifying and publishing measurements), far below every threshold, none of this appears to bite. This is our reading, not legal advice; read the license yourself.

The 27B has a different license. Its file is 11,544 bytes of verbatim Apache License 2.0 text with an appendix reading Copyright 2026 Alibaba Cloud: no monthly-active-user threshold, no revenue-share clause, no separate license at any revenue level. "Qwen3.8 is Apache 2.0" is true of the 27B and wrong for the family. Section 03 of the Qwen3.8-27B field card puts both side by side.

What the 2.4T download is

From the Qwen3.8-2.4T-A95B repository's configuration, tokenizer, chat template (the format that turns a request into model input) and model card, checked 2026-08-13. None of it describes the 27B, which has a different architecture, a working thinking off-switch and a vision part in its configuration (section 01 of the field card).

Release shapeOne post-trained assistant model; no base or separate instruct variant.
ThinkingAlways on. The chat template raises an error if asked to run with thinking off. A reasoning_effort setting has levels xhigh, medium and low; the default is xhigh. Thinking is kept across turns by default.
ModalityText only.
Context length262,144 tokens native in the configuration (how much text the model takes in at once). The model card calls it extensible to 1,010,000; that is the maker's claim, not tested here.
ArchitectureQwen3_5MoeForCausalLM, model type qwen3_5_moe_text: a scaled Qwen3.5, not a new design. A mixture of experts (many expert blocks, a few used per token). 92 layers as 23 repeats of three GatedDeltaNet linear-attention layers plus one gated-attention layer, hidden size 8192, 512 experts with 10 routed and one shared active per token, and a one-layer multi-token-prediction head.
Tokenizer and templateVocabulary 248,320 and end-of-sequence id 248044, both unchanged from Qwen3.5 397B. The template drops the vision parts and adds reasoning_effort.

Because the architecture already exists, llama.cpp and vLLM should load these weights in the formats they already read, without new support work. As of 2026-08-13, llama.cpp already carried the qwen35moe architecture, including in the build serving Qwen3.5 on this desktop; the community GGUF declares exactly that architecture and the native 262,144 context; and vLLM merged a change on 2026-08-07 that sends Qwen3.8 checkpoints through its existing Qwen3.5 path. The one related llama.cpp pull request, template support for reasoning_effort, never blocked loading and merged on 2026-08-14 (#26941). This is an expectation with evidence, not a tested result: the one load attempt here failed on the file's compression type before any architecture code ran.

The 2.4T download on a desktop

The Qwen organization shipped safetensors only; no official GGUF exists (checked 2026-08-13). The one real community conversion is unsloth/Qwen3.8-2.4T-A95B-GGUF. Its sizes, smallest compression level first:

As listed in the repository on 2026-08-13. Only UD-Q1_0 was downloaded here; the rest were neither downloaded nor run. The quantizer accounts bartowski and mradermacher had published nothing under the name at check time, and one more well-known quantizer account held only an empty placeholder.

The desktop here has 188 GB of system memory and one 32 GB graphics card. The 397.3 GB UD-Q1_0 is the only file that fits its free disk, and at more than twice system memory it could only run streamed from an NVMe drive. A 594 GB file of a different trillion-parameter mixture of experts once ran that way here at 0.19 to 0.28 tokens a second: proof it can run, not a tool. A machine this size should expect, at best, a model that loads and generates, not one worth recommending.

It did not load. On 2026-08-13 the 397.3 GB set downloaded through two interruptions, and all ten shards matched the repository's own SHA-256 checksums. The server then refused it in 0.38 seconds while reading the file header, before allocating anything. The cause was neither memory nor architecture: the 276 routed-expert tensors that hold most of the 2.4 trillion parameters are stored as quantization type number 66, and in every public build checked that day, llama.cpp mainline and the quantizer's own public fork alike, the type table ends at 42. The "Q1_0" in the name is branding, and the file's metadata label names a standard type found nowhere among its tensors. On 2026-08-16 no public llama.cpp build declared it and no open pull request added it. So this model has no local speed, memory or quality numbers here; the verified file gets a new load attempt when a public build can read it.

Fake repositories

Within days of the announcement, before any real weights, third-party repositories used the Qwen3.8 name in two shapes: placeholder cards that describe planned files but hold no weight tensors, and rebadges, small models distilled from or unrelated to the announced ones, under the 3.8 name. On 2026-08-13 every third-party 27B repository previously catalogued still held zero weight tensors, including some whose cards advertised Apache 2.0 for a model that had not then shipped under any license. Those placeholders did not become real when the real 27B appeared beside them on 2026-08-14. Accounts are not named here, because next week's fakes will have different names.

Qwen3.8-Max online: thinking can use the whole budget

On 2026-08-09 a fixed set of fifteen calls ran against Qwen3.8-Max online through one aggregator route (OpenRouter), with every raw request and response kept. Total cost: seven cents, at the listed two dollars per million input tokens and six per million output.

It called itself "Qwen, also known as Tongyi Qianwen," built by Alibaba's Tongyi Lab. It solved the bat-and-ball trap, wrote a correct interval-merging function with three test assertions, returned schema-conforming JSON on all three attempts, and, asked about a file never provided and a benchmark that does not exist, asked for the data instead of inventing either.

The model thinks by default, its thinking bills as output tokens inside your token cap, and it will spend the entire cap thinking and hand back an empty answer.

Qwen3.8-Max online, 2026-08-09. Token cap is the request's max-tokens value, which covers thinking plus the visible answer. "Thinking spent" is the reasoning-token count the API reported. Every empty row ended with the length stop reason: the cap ran out before the first visible word.

A medium puzzle used all of a 2,000-token cap without one visible word, and a simple story request spent 1,200 tokens thinking three times in a row and never wrote the story. Those three empty attempts cost more than the completed effort-controlled runs: you pay for the thinking either way. Time for a whole request on this route: about three to five seconds for a short factual answer, about twelve for the JSON asks, about twenty-five to forty-six seconds when thinking runs long.

This is not a Qwen fault. On 2026-08-09 one fixed reasoning prompt went across the same caps to a comparable hidden-reasoning model from another vendor. Both returned empty answers at small caps. Qwen gave its first visible words at a 256-token cap; the other still returned nothing at 256 and did not finish until 1,024. The full study is Empty Answer.

The 2.4T download, served online

Since 16:21 UTC on 2026-08-12 the 2.4T download has been listed on the same OpenRouter route at the same prices as Qwen3.8-Max online. On 2026-08-13 thirty-five calls against it cost thirty-nine cents. OpenRouter filled them from DeepInfra (20 of 35) and Together (15); DeepInfra lists its serving precision as fp4 and Together lists none. The empty-answer behavior is fully present on the 2.4T download. The marble prompt from Empty Answer, temperature zero, one call per cap:

Token capProviderThinking spentVisible answer
60DeepInfra73empty
256DeepInfra179first words, cut off
500Together223complete and correct
2,000DeepInfra188complete and correct

The 60 and 256 rows ended with the length stop reason; the 500 and 2,000 rows stopped on their own. On the marble prompt, Qwen3.8-Max online on 2026-08-09 matched at neighboring caps: empty at 64, first cut-off words at 256, clean by 512.

On one easy prompt, the effort setting changed the prompt and the style, not the amount of thinking. The marble prompt again, a 2,000-token cap, temperature zero, one call per level, requests byte-identical apart from the effort field:

Effort levelProviderThinking spentPrompt tokens, server countCost, server billedVisible answer
xhigh (default)DeepInfra184112$0.00236340 chars, terse, correct
mediumDeepInfra19770$0.00363720 chars, formatted, correct
lowTogether168100$0.00341527 chars, formatted, correct

The low call landed on the other provider.

Thinking stayed at 168 to 197 tokens and every answer was correct, but the server counted three prompt lengths for identical requests. That is consistent with the shipped template, which adds an instruction sentence for effort (one for xhigh, one for low, none for medium). Lower effort gave longer, more formatted answers, so medium cost the most and the default the least.

Thinking was not turned off by this request. A request with enable_thinking: false got a reply that still carried 626 tokens of hidden reasoning; the field was silently ignored. One request, 2026-08-13.

The listing is not the bill. Both providers ran the 262,144-token context; the listing's million-token context was only on a provider not used here. Together billed two dollars fifty per million input tokens and six twenty-five per million output, against the listed two and six, and the reported cost of every Together call matched that premium to the digit. It also billed 12,672 repeated identical prompt tokens at roughly a fifth of its input price on one test, a cache discount the listing does not mention, so the billed total came in just under the sum of list prices.

The rest passed. A code hidden in long prompts came back exactly at 31,380 and at 69,441 prompt tokens, as the server counted them. Tool calls had exactly the right arguments every time. JSON conformed on all three attempts with the schema written into the prompt. On this route (the 2.4T download through OpenRouter), a schema sent only through response_format never reached the model: the answer was empty and the kept reasoning complains that no schema was provided. Routecheck, the site's tool that runs the fixed tests in one recorded pass, put this route's thinking-budget floor at 500 tokens for its own prompts, where the marble prompt showed first words at 256: the floor depends on the prompt, so measure it on yours.

The 27B ran the day it shipped

The 27B went public at about 11:00 EDT on 2026-08-14. By evening a community GGUF conversion, checked against its repository's checksums, was serving on this desktop's existing llama.cpp build, which already implements its architecture. Its measurements are on the Qwen3.8-27B field card, with the exact launch command, three measured client traps and a data package; its draft head (a helper that guesses ahead) writes prose at 72.4 tokens a second gated and 44.5 with the gate removed; the card has the detail.

03

Limits

  • Hosted results are diagnostics, not a benchmark. One aggregator route, one to three calls per cell, on 2026-08-09 and 2026-08-13; the 2.4T download's numbers belong to that day's DeepInfra and Together mix.
  • The effort result is one easy prompt. One call per level, with the low call on the other provider. A harder prompt was not run, so nothing is generalized from it.
  • Loading in a supported format is untested. That existing Qwen3.5 paths in llama.cpp and vLLM load the 2.4T download in mainline formats is an expectation, not a result here.
  • Status is dated. The files were last checked on 2026-08-13 and 2026-08-14; only the pull request and the quantization type were rechecked on 2026-08-16. After 2026-08-16, treat the status table as unverified and check the official organization directly.
